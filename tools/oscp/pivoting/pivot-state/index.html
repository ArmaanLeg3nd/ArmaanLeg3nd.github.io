STAGE 07 / Reach internal services

Pivoting & tunnels

A tunnel moves traffic; it does not grant destination authorization. Draw listener location, connection initiator, remote destination, DNS resolution and return path separately.

Investigation sequence

Follow the steps that match what you found. Open a technique for its check, clue and next action.

  1. 1

    Map what the pivot can reach

    Discover pivot interfaces, routes and internal service context →
  2. 2

    Choose where the connection starts

    Relay a single TCP service through a fixed forward →Forward a selected service through an SSH client-side listener →Expose an SSH-client-side destination through a server-side remote listener →
  3. 3

    Choose a forward, proxy or route

    Provide SOCKS access through SSH dynamic forwarding →Use ProxyChains, native SOCKS clients and SSH jump paths appropriately →Route a selected internal subnet through Ligolo-ng →
  4. 4

    Check names and return connections

    Preserve DNS, Kerberos names and time across a pivot →Build the callback and delivery routes separately from the attack route →
  5. 5

    Verify each additional hop

    Compose multiple pivots and validate every connection leg →
Detailed scope & checks

Starting situation: Start from the pivot's current shell/process or accepted SSH access; another reachable subnet and an operational tunnel are not assumed.

Required access: A pivot identity/process or reachable SSH service and a drawn source-to-destination path

  1. Inspect pivot interfaces, routes, local listeners and destination reachability
  2. Draw listener location and connection initiator before fixed or SSH forwarding
  3. Choose proxy versus routed access according to the real client/protocol requirements
  4. Validate names, KDC access and the separately required delivery/callback route
  5. For additional hops test each leg before chaining the final application

Why it works & worked example

Mechanics

A dual-homed host can connect networks without forwarding packets for arbitrary clients. Select fixed forward, application proxy or routed tunnel according to the required protocol and permissions.

Hypothetical example

Observation: a foothold can reach an internal service absent from Kali's route. Test: verify the destination from that host and draw the connection direction. Illustrative output: the pivot reaches TCP/445. Interpretation: choose the smallest compatible route for the intended client.

# Run on Kali when Kali can SSH to the pivot:

ssh -N \
  -L 127.0.0.1:LOCAL_PORT:INTERNAL_HOST:INTERNAL_PORT \
  -p SSH_PORT USER@PIVOT \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3

# Use the listener as though it were the internal service:

nc -nvz 127.0.0.1 LOCAL_PORT
curl -v http://127.0.0.1:LOCAL_PORT/

# The SSH server/pivot resolves and connects to INTERNAL_HOST. Bind to 127.0.0.1 unless
# another authorized local host must use the forward; -g or a non-loopback bind expands
# exposure.

# Add reliability and attributable failure to transport-only sessions:

-N
-o ExitOnForwardFailure=yes
-o ServerAliveInterval=30
-o ServerAliveCountMax=3

# ExitOnForwardFailure proves requested listening sockets were established. It does not
# prove the final destination is reachable through them.

If it fails: Administrative-prohibited indicates SSH forwarding policy; address-in-use is a local bind problem; timeout can be the remote leg.

Why it works & worked example

Mechanics

With -L the listener is on the SSH client and the remote destination is reached from the SSH server. localhost in the destination therefore means the server's loopback.

Hypothetical example

Observation: a database listens only on the SSH server's loopback. Test: use the documented local forward to that loopback port. Illustrative output: the client-side database connection works. Interpretation: authenticate using database-specific credentials.
