STAGE 02 / Extract opportunities from services

Services

A service can disclose names, files, rights or execution. Test authentication, read, write and execution separately. A write becomes an execution path only when a useful consumer and trigger exist.

START HERE

Use the matching protocol client and establish which identity the service accepts

FTP →SMB / RPC →SSH →
Full investigation sequence 4 steps

Starting situation: Start with application evidence from discovery; anonymous access, valid credentials and useful rights are separate questions.

Required access: A confirmed reachable application; anonymous context or one identified credential

START WITH
A confirmed reachable application; anonymous context or one identified credential

Anonymous login allowed or a valid FTP identity; data-channel connectivity and object-specific read/write rights
CAN PRODUCE
Retrieved files, configuration or a verified writable location
First checkCommands & variantsNext steps (3) ↓

Investigate this first

After identifying FTP, test the allowed anonymous context or one known credential and inspect its directory namespace.

curl -v ftp://TARGET/
curl -v --user 'USER:PASSWORD' ftp://TARGET/

Confirm: Validate the account context, file contents, data-channel reachability and any separate write/consumer conditions.

What the clue looks like SYNTHETIC OUTPUT
230 Login successful
LIST: application.conf; backups/
RETR application.conf: 226 Transfer complete

A listing identifies candidate artifacts; a completed RETR with recognizable bytes establishes read access.

Verify: Retrieve recognizable bytes or independently verify an uploaded canary; distinguish listing, read and write rights.

What did you find?

Useful finding

The relevant file is readable and contains a current typed secret: follow credential classification.

Ruled out here

Anonymous login is denied: rule out anonymous access, retaining authenticated FTP as a separate possibility.

Inconclusive

Login works but data transfer hangs: inspect active/passive data routing before concluding file access is denied.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: FTP usually appears on TCP/21, but trust an FTP banner or protocol response on any port. Goal: determine authentication, listable/readable content and effective write locations.

Baseline: anonymous access
ftp TARGET

At the prompts, try user anonymous and an email-like password. Then:

status
pwd
ls -la
binary
get FILE
quit

If login succeeds but listing/transfer fails, use the client's passive command to toggle data-channel mode and retry once before changing credentials.

Decisive output: code 230 accepts the login; directory listings and successful RETR establish read access. Inspect downloaded backups, configuration, keys and source locally. Store target artifacts outside this public repository.

Variant — authenticated FTP 
ftp TARGET

Enter USER and the password when prompted. Enumerate from the authenticated root again; it may expose a different namespace than anonymous access.

Variant — curl listing, download and bounded write test 
curl --list-only ftp://TARGET/
curl -o FILE ftp://TARGET/path/FILE
curl --user USER ftp://TARGET/
curl --user USER -o FILE ftp://TARGET/path/FILE
curl --user USER --upload-file ./probe.txt ftp://TARGET/path/probe.txt

Omit --user for anonymous access. Let curl prompt for an authenticated password instead of placing it in shell history. Upload only a harmless uniquely named probe when write validation is necessary and authorized; remove it through the FTP client after the test.

Variant — focused Nmap helpers 
nmap -sV -p PORT --script ftp-anon,ftp-syst TARGET

ftp-anon checks anonymous login and may flag writable entries; ftp-syst asks for server/system information. Manually confirm useful access with a protocol client.

Failure cues: 530 means that login was rejected, not that FTP has no other usable identity. A listing failure after 230 may be a data-channel/passive-mode or authorization problem. A successful upload proves write access only; it does not prove that a web server, scheduled task or privileged process consumes that file.

Next action: inspect recovered files; record exact read/write boundaries; validate any new credential once against its likely service; send a writable-consumer hypothesis to the appropriate web, execution or privilege-escalation block.

Failure signals & fallback checks

Login succeeds but transfers hang: diagnose the data path. A writable upload directory alone does not establish command execution.

Mechanics & hypothetical worked example

Why it works

FTP authentication and directory listing do not guarantee downloads or uploads. Passive/active data channels can fail independently of the control connection; uploaded bytes need a separate execution consumer.

Worked example — hypothetical

Observation: anonymous login succeeds. Test: list and download one relevant readable configuration. Illustrative output: an application username is present. Interpretation: classify its credential context and test only a compatible service.

SMB / RPC+ Enumerate SMB/RPC shares, files and identities RECOGNIZE SMB/RPC endpoints, domain clues or new credentials
START WITH
A confirmed reachable application; anonymous context or one identified credential
APPLIES WHEN
Reachable SMB/RPC; anonymous, guest, local or domain context must be explicit; share and filesystem ACLs both matter
CAN PRODUCE
Domain/user clues, readable files or object-specific writable access
First checkCommands & variantsNext steps (3) ↓

Investigate this first

Start from confirmed SMB and explicitly compare anonymous versus a known authenticated context, then open a relevant named share.

smbclient -L //TARGET -N
smbclient -L //TARGET -U 'DOMAIN/USER'

Confirm: Test the exact share/object operation under the recorded local/domain identity.

What the clue looks like SYNTHETIC OUTPUT
Sharename       Type
SHARE           Disk
NETLOGON        Disk

A share name supplies a filesystem investigation target; listing it does not prove read, write or service creation.

Verify: Prove the specific share/object action; a successful login or administrative indicator does not establish every remote-execution route.

What did you find?

Useful finding

A relevant configuration can be retrieved: inspect its account/secret context.

Ruled out here

The authenticated account cannot read that object: discard the read path for this identity, not all SMB opportunities.

Inconclusive

Login succeeds but listing fails: check a justified known share path and separate share/NTFS authorization.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: direct-hosted SMB commonly uses TCP/445; NetBIOS session service commonly uses TCP/139; MS-RPC endpoint mapping commonly uses TCP/135. They are related Windows surfaces but not interchangeable. Goal: distinguish null, guest and authenticated contexts; enumerate shares, files, users, groups, domain/workgroup clues and actual permissions.

Baseline: list shares without credentials
smbclient -N -L //TARGET

Decisive output: a share list proves that this access context can enumerate names. It does not prove access to share contents. NT_STATUS_ACCESS_DENIED means this context was denied; repeat after obtaining a legitimate credential.

Variant — authenticated share listing and connection 
smbclient -L //TARGET -U 'DOMAIN/USER'
smbclient //TARGET/SHARE -U 'DOMAIN/USER'
smbclient -L //TARGET -U 'TARGET/USER'
smbclient -L //TARGET -U 'guest%'

The first two forms use a domain identity, the third makes a local target account explicit, and the fourth tests a guest account with an empty password. Let the client prompt for non-empty passwords. Inside the share:

pwd
ls
allinfo FILE
get FILE
mkdir probe-dir
rmdir probe-dir
exit

Use a harmless uniquely named directory only when write permission must be verified. A successful create/remove establishes share-level write access, not code execution.

Variant — recursive retrieval 
smbclient //TARGET/SHARE -U 'DOMAIN/USER' -c 'recurse ON;prompt OFF;mget *'

Run from a dedicated local evidence directory and review expected volume first. Search downloaded configuration, scripts, backups, keys and unattended-install files locally; never publish recovered data.

Variant — RPC null or authenticated session 
rpcclient -U '' -N TARGET
rpcclient -U 'DOMAIN/USER' TARGET

Useful interactive queries:

srvinfo
enumdomains
enumdomusers
enumdomgroups
queryuser RID
netshareenumall
quit

Null-session denial is common on modern systems. Authenticated output must be labelled with the identity that produced it.

Variant — fast permission summary and consolidated candidates 
nxc smb TARGET -u USER -p PASSWORD --shares
enum4linux-ng -A TARGET

NetExec (nxc) is the current command name on recent Kali releases; older material may use crackmapexec. These tools consolidate candidates. Confirm useful shares and files with smbclient or native access.

Variant — protocol, signing and time clues 
nmap -p 139,445 --script smb-protocols,smb2-security-mode,smb2-time TARGET

Signing and dialect results affect later relay/exploit decisions but are not vulnerabilities by themselves. The older smb-os-discovery script depends on SMBv1 behavior and may not identify modern hosts reliably.

Variant — Windows built-ins 
net view \\TARGET /all
Get-ChildItem \\TARGET\SHARE
Get-Content \\TARGET\SHARE\FILE

These use the current Windows logon context unless alternate credentials or mappings are established. An existing connection to the same server under another identity can cause credential-conflict errors.

Failure cues: distinguish connection failure, authentication failure, share enumeration denial and file authorization denial. A share named IPC$ is not a general file share. Guest acceptance may look like success while returning a restricted namespace. A share marked writable still needs a consumer/trigger before it becomes an execution path.

Next action: inspect readable content, record per-share rights, validate names/domain clues, and re-run authenticated enumeration whenever identity changes. Move file-consumer hypotheses to web/execution/escalation and signing/relay hypotheses to the later credential/AD blocks.

Failure signals & fallback checks

Access denied after login usually means authorization/context. Test local/domain qualification and the exact object rather than repeating passwords.

Mechanics & hypothetical worked example

Why it works

Session establishment, share enumeration, filesystem rights and remote execution are separate authorization layers. A credential change can reveal entirely new shares and files.

Worked example — hypothetical

Observation: anonymous share listing is denied but a recovered domain credential works. Test: open one relevant share and retrieve a configuration. Illustrative output: a service account secret appears. Interpretation: record its identity and re-enter credential validation.

NFS / RPC+ Inspect RPC/NFS exports and effective file identity RECOGNIZE RPC/NFS listeners or export information
START WITH
A confirmed reachable application; anonymous context or one identified credential
APPLIES WHEN
Reachable RPC/NFS transports, permitted client address and an export whose UID/GID mapping grants relevant access
CAN PRODUCE
Readable files or a controlled write with established identity semantics
First checkCommands & variantsNext steps (3) ↓

Investigate this first

Follow RPC/NFS discovery with export inspection, then examine actual ownership/mapping on an allowed mount.

rpcinfo -p TARGET
showmount -e TARGET

Confirm: Use the owning procedure to verify NFS version, allowed client, numeric identity mapping, read/write and squash/mount policy.

What the clue looks like SYNTHETIC OUTPUT
100003  3  tcp  NFS_PORT  nfs
Export list for TARGET:
/EXPORT CLIENT_SCOPE

An export lists a filesystem candidate and client policy; it does not establish file access or trusted UID 0.

Verify: Verify the export, mapped identity, actual bytes and any created file's server-side ownership.

What did you find?

Useful finding

The relevant mapped identity can read configuration: retrieve and classify its useful artifacts.

Ruled out here

The export permits a different client scope: rule out this source's mount route.

Inconclusive

Empty showmount can miss NFSv4 context; confirm version/export behavior before declaring no NFS access.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: rpcbind commonly appears on TCP/UDP 111 and NFS on TCP/UDP 2049, with additional dynamically assigned RPC ports. Goal: find exports, allowed client ranges and effective UID/GID-based permissions.

Baseline: list RPC services and exports
rpcinfo -p TARGET
showmount -e TARGET

Decisive output: rpcinfo maps RPC programs to versions/transports/ports. showmount -e returns exports and apparent allowed clients, but NFSv4-only servers may not expose the mount service and showmount completeness varies by implementation.

Variant — Nmap without mounting 
nmap -sV -p 111,2049 --script nfs-showmount,nfs-ls,nfs-statfs TARGET

The scripts can list exports, file attributes and access flags. Confirm access manually when a finding matters.

Variant — mount read-only first 
sudo mkdir -p /mnt/nfs-audit
sudo mount -t nfs -o ro,vers=3,nolock TARGET:/EXPORT /mnt/nfs-audit
find /mnt/nfs-audit -maxdepth 3 -ls
sudo umount /mnt/nfs-audit

If version 3 fails and version 4 is advertised, retry with -o ro,vers=4. NFSv4 may present a pseudo-filesystem whose export path differs from showmount output.

Variant — inspect numeric ownership 
ls -lan /mnt/nfs-audit
find /mnt/nfs-audit -maxdepth 3 -type f -readable -ls

NFS commonly authorizes Unix identities by numeric UID/GID. A matching local username is irrelevant if its number differs. root_squash usually maps remote UID 0 to an unprivileged identity; no_root_squash is dangerous but still requires a useful writable object and privileged consumption path.

Variant — bounded write verification 
sudo mount -t nfs -o rw,vers=3,nolock TARGET:/EXPORT /mnt/nfs-audit
touch /mnt/nfs-audit/probe-file
ls -ln /mnt/nfs-audit/probe-file
rm /mnt/nfs-audit/probe-file
sudo umount /mnt/nfs-audit

Use a unique harmless name only when write validation is needed and authorized. Record the resulting numeric owner/group. Success proves write in that directory, not execution or privileged ownership.

Failure cues: showmount failure does not rule out NFSv4. access denied by server can mean export client restrictions or wrong path/version. permission denied after mounting is file authorization, not network failure. Do not change local UIDs or write to an export during concept study.

Next action: inspect readable backups, home data, keys and configuration; record numeric ownership and actual write boundaries; send a writable/privileged-consumer hypothesis to the escalation block.

Failure signals & fallback checks

An empty showmount response does not rule out NFSv4. Mount failure may be transport/export/client-policy rather than absence of files.

Mechanics & hypothetical worked example

Why it works

NFS authorization can depend on numeric IDs and export options. root_squash prevents remote UID 0 from automatically becoming server root; no_root_squash alone still needs a useful consumer or execution path.

Worked example — hypothetical

Observation: an export permits the assessment client. Test: inspect ownership and a scoped read. Illustrative output: a backup configuration is readable under a matching numeric UID. Interpretation: recover its secrets; assess writes separately.

SSH+ Use SSH passwords, keys and forwarding-capable access RECOGNIZE An SSH service and a known password, private key or agent context
START WITH
A confirmed reachable application; anonymous context or one identified credential
APPLIES WHEN
Compatible authentication method, correct user, accepted key policy and the requested shell/subsystem permission
CAN PRODUCE
An authenticated shell, subsystem or forwarding capability with verified identity
First checkCommands & variantsNext steps (3) ↓

Investigate this first

Find SSH in service discovery, then trace a candidate password/key back to its recorded user before a bounded authentication attempt.

ssh -v -p PORT USER@TARGET
ssh -v -i KEY -p PORT USER@TARGET

Confirm: Check actual account/shell/subsystem and separately inspect forwarding policy if a tunnel is needed.

What the clue looks like SYNTHETIC OUTPUT
Authenticated to TARGET using publickey
uid=USER_ID(USER) gid=GROUP_ID(GROUP)

Accepted key authentication plus a verified shell identity establishes that specific login, not root or unrestricted forwarding.

Verify: Run hostname and id in the resulting context; retain whether a shell, SFTP or only forwarding was actually granted.

What did you find?

Useful finding

The intended user can run commands: establish host/privilege/network state.

Ruled out here

The same valid key is not authorized for this user: rule out that username/key pairing.

Inconclusive

A passphrase prompt or host policy rejection requires key/context diagnosis; it is not evidence that all SSH access is unavailable.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: SSH commonly uses TCP/22. Prerequisite for access: an accepted authentication method plus a permitted account/session context.

Baseline: validate one known identity
ssh -v -p PORT USER@TARGET

Decisive output: the debug trace separates connection, host-key negotiation, offered authentication methods and account acceptance. A shell prompt establishes session access as that identity.

Variant — private key 
chmod 600 KEY
ssh -v -i KEY -p PORT USER@TARGET

The key must correspond to an authorized public key for that account. Permission denied (publickey) can mean wrong user, wrong key, server policy or account restrictions.

Variant — discover methods for a known username 
nmap -p PORT --script ssh-auth-methods --script-args "ssh.user=USER" TARGET

This starts an authentication exchange and is logged; Nmap classifies it as intrusive. Use it only when the supported methods change the next decision.

Variant — non-interactive key check 
ssh -o BatchMode=yes -o ConnectTimeout=5 -i KEY -p PORT USER@TARGET 'id'

Batch mode will not prompt for passwords or key passphrases. It is useful only when the key is already usable non-interactively.

Failure cues: timeout suggests route/filtering/service issues; refusal means no accepting listener in that context; host-key failure occurs before user authentication; Permission denied proves that the attempted method/context failed, not that every credential is invalid. A valid account may still have no shell or be restricted by server policy.

Next action: after a shell, verify whoami, groups, hostname and addresses, then re-enumerate locally. Password spraying and key-passphrase cracking belong to the credential-attack block, not this procedure.

Failure signals & fallback checks

Permission denied may be username, key, passphrase, policy or method mismatch. A successful banner exchange proves none of these.

Mechanics & hypothetical worked example

Why it works

SSH authentication can succeed while shell access is restricted. Key ownership, passphrase and server authorization matter independently; forwarding is a separately controlled feature.

Worked example — hypothetical

Observation: a disclosed private key names a local user. Test: inspect the key and authenticate to that user. Illustrative output: a shell returns with a non-root UID. Interpretation: establish Linux state and inspect allowed forwarding.

DNS+ Expand names through DNS records and zone transfers RECOGNIZE A DNS server, domain name or host aliases
START WITH
A confirmed reachable application; anonymous context or one identified credential
APPLIES WHEN
Reachable DNS transport and relevant authoritative zone; AXFR requires an allowed TCP zone transfer
CAN PRODUCE
Hostnames, address relationships and possibly a zone inventory
First checkCommands & variantsNext steps (3) ↓

Investigate this first

Use DNS-server evidence and discovered domain names to query authority and specific records before considering a transfer.

dig @TARGET DOMAIN SOA
dig @TARGET DOMAIN NS
dig @TARGET DOMAIN AXFR

Confirm: Check each new name's scope/address and verify host/virtual-host behavior.

What the clue looks like SYNTHETIC OUTPUT
DOMAIN. SOA DC_HOST. HOSTMASTER.
HOSTNAME.DOMAIN. A TARGET
Transfer completed

An authoritative zone and returned records can expose hostnames, aliases and applications needing separate enumeration.

Verify: Identify responding server, record type, answer and zone authority; transfer refusal disproves only that transfer/context.

What did you find?

Useful finding

A permitted transfer returns a relevant new host: validate it through discovery.

Ruled out here

Transfer refused rules out AXFR on this server/zone/context; ordinary records may remain useful.

Inconclusive

A timeout or non-authoritative response requires authority/transport checks before any zone conclusion.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: DNS uses UDP/53 for most queries and TCP/53 for operations including conventional zone transfers and oversized responses. Prerequisite: a known or inferred domain for meaningful record and name enumeration.

Baseline: query the target DNS server directly
dig @TARGET DOMAIN SOA
dig @TARGET DOMAIN NS
dig @TARGET DOMAIN A
dig @TARGET DOMAIN MX
dig @TARGET DOMAIN TXT

Decisive output: ANSWER records disclose names, addresses, mail exchangers or text. The aa flag supports an authoritative answer. Record status separately from the answer count.

Variant — reverse lookup and zone transfer 
dig @TARGET -x IP
dig @TARGET DOMAIN AXFR

A successful AXFR returns the zone records and closing SOA. Transfer failed, REFUSED or NOTAUTH only disproves an unauthenticated transfer from this source; continue ordinary queries.

Variant — name guessing after the domain is known 
dnsrecon -d DOMAIN -n TARGET -t std
dnsrecon -d DOMAIN -n TARGET -D WORDLIST -t brt
dnsenum --dnsserver TARGET DOMAIN

Check wildcard behavior before trusting large result sets. Every resolved in-scope name becomes a new discovery/service-enumeration input.

Variant — reverse sweep of an explicitly assigned range 
dnsrecon -r SUBNET -n TARGET

Use this only when the entire SUBNET is assigned. PTR names are clues; resolve/scan only in-scope results.

Variant — host and Windows nslookup 
host -t mx DOMAIN TARGET
host -t txt DOMAIN TARGET

nslookup HOST.DOMAIN TARGET
nslookup -type=TXT HOST.DOMAIN TARGET
nslookup -type=MX DOMAIN TARGET

Failure cues: NXDOMAIN means that queried name does not exist in that view; NOERROR with no answer can mean the name exists but lacks that record type. Timeout can be filtering, loss or a silent/unreachable server. A recursive answer does not establish that the server is authoritative.

Next action: add new hostnames/IPs to the scoped queue, correlate naming roles with observed services, and repeat discovery/service identification for those in-scope endpoints.

Failure signals & fallback checks

No answer may mean wrong server, recursion policy, transport or zone. Resolve authoritative context before retrying AXFR.

Mechanics & hypothetical worked example

Why it works

A DNS answer belongs to a server and zone context. AXFR exposes zone records only when the server is authoritative and permits the transfer; names become discovery or virtual-host inputs.

Worked example — hypothetical

Observation: the authoritative server permits AXFR. Test: inspect the returned A/CNAME records. Illustrative output: a previously unknown application hostname. Interpretation: confirm scope/address reachability and request that virtual host.

SNMP+ Extract configuration and process information through SNMP RECOGNIZE UDP/161 evidence or an exposed management plane
START WITH
A confirmed reachable application; anonymous context or one identified credential
APPLIES WHEN
An accepted read community or SNMPv3 identity/security level; transport and view permissions
CAN PRODUCE
Host, interface, software or process/configuration clues from permitted OID branches
First checkCommands & variantsNext steps (3) ↓

Investigate this first

Take UDP/161 evidence and a justified management credential/community, then request a small known OID branch before a broad walk.

snmpwalk -v2c -c COMMUNITY TARGET 1.3.6.1.2.1.1

Confirm: Determine which useful views/branches are actually readable; process data and write rights are separate.

What the clue looks like SYNTHETIC OUTPUT
SNMPv2-MIB::sysDescr.0 = STRING: OS_AND_BUILD
SNMPv2-MIB::sysName.0 = STRING: HOSTNAME

A real OID response confirms the accepted read context and supplies software/name clues.

Verify: Preserve the OID, accepted security context and returned value; empty branches can reflect view restrictions.

What did you find?

Useful finding

A relevant interface/process branch returns useful data: follow the named subnet/application/credential.

Ruled out here

An explicit authorization failure rules out that security context/view.

Inconclusive

UDP silence can be routing, version, community or view policy; a timeout cannot choose between them.

Execution procedure & complete variants COMMANDS

Use the baseline when the conditions above match. Choose variants by their access, credentials and transport requirements.

Recognize: SNMP queries commonly use UDP/161. Versions 1 and 2c authenticate with a community string sent without modern transport protection; version 3 can provide user-based authentication and privacy. Goal: turn a valid read context into host, interface, route, process, software, user and listener clues.

Recognize: RDP commonly uses TCP/3389; WinRM commonly uses 5985/HTTP and 5986/HTTPS. Goal: determine whether one known credential is accepted in the correct local/domain context and whether it is authorized for a usable session.

RDP baseline: authentication-only check
xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /auth-only /cert:ignore

Some distributions expose the binary as xfreerdp. Omit /d:DOMAIN for the intended local-account context; use /u:TARGET\\USER if needed to make that context explicit.

Decisive output: successful authentication-only validation supports that the credential is accepted for RDP/NLA. It does not prove an interactive desktop will be granted under every policy/session condition.

Variant — open an RDP desktop 
xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /dynamic-resolution /cert:ignore

Let FreeRDP prompt for the password. /cert:ignore suppresses certificate validation and is suitable only in the controlled lab context; it removes server-identity protection.

Variant — identify RDP security requirements 
nmap -p 3389 --script rdp-enum-encryption,rdp-ntlm-info TARGET

This can disclose supported security layers, NLA and NTLM host/domain clues. It does not validate a credential.

WinRM baseline: interactive session
evil-winrm -i TARGET -u USER

evil-winrm -i TARGET -u 'DOMAIN\\USER'

Omitting -p makes the established Ruby client prompt for the password.

Decisive output: an interactive PowerShell prompt establishes WinRM authorization. Immediately verify identity and host context with whoami, hostname and Get-NetIPAddress.

Variant — WinRM over HTTPS 
evil-winrm -i TARGET -u USER -S -P 5986

Check evil-winrm -h because the established Ruby client and newer evil-winrm-py use different long-option spelling. Do not assume a copied command matches the installed implementation.

Variant — Windows PowerShell remoting 
$cred = Get-Credential
Enter-PSSession -ComputerName TARGET -Credential $cred

PowerShell remoting uses the configured WinRM endpoint. Local trusted-host, Kerberos/name-resolution and endpoint authorization settings can fail independently of password validity.

Failure cues: certificate warnings are different from authentication failure. RDP errors can reflect NLA, account context, expired/locked accounts or missing logon rights. WinRM 401 supports authentication/authorization failure; WinRM cannot process the request can be name resolution, trusted-host, listener or transport context. Valid SMB credentials do not guarantee RDP or WinRM rights.

Next action: after a session, re-enumerate identity, groups, privileges, files, local services/listeners and routes. Password spraying, pass-the-hash and ticket use belong to later credential/AD blocks.
