Integrated Attack and Reporting Cheatsheet

← Cheatsheet index | Full procedure | Strategy map | Study methods: Complete attacks and retain reproducible evidence

State map

HOSTS: host/IP | role | reachable from | services | evidence
IDENTITIES: local/domain | credential type | validated access | privilege | source
ROUTES: source -> tunnel/pivot -> destination | DNS | callback path
HYPOTHESES: observation | prerequisite | test | status
TRANSITIONS: old state -> action -> new state | decisive evidence
EVIDENCE: objective | reproduction | identity/IP proof | screenshot | submission/task state

Core attack loop

Observe → Enumerate → Interpret → Hypothesize → Validate prerequisite
→ Exploit → Verify new state → Re-enumerate → Escalate/Move → Document

Keep two queues:

COVERAGE: source position → host → endpoint → application → enumeration state
HYPOTHESIS: observation → desired transition → prerequisite → next test → status

State-change router

New evidence/stateRe-enter
Host/address/interface/listener/routeDiscovery and service identification from the reachable source
Credential/key/hash/ticketClassification, compatible validation and authenticated enumeration
Application role/sessionApplication mapping through the new authorization view
Execution/shellHost/identity/network verification, session repair and local enumeration
Root/Administrator/SYSTEMProtected credentials, services, sessions, routes and domain context
Domain identity/group/rightAD objects/rights plus reachable host/service paths
Pivot/proxyDiscovery from new vantage; separate delivery/callback route design

Standalone sequence

scope/objective
→ TCP + bounded UDP coverage
→ service/web enumeration
→ files/config/identity opportunities
→ credential, manual weakness or exact exploit prerequisite
→ bounded effect
→ verified session
→ initial-access evidence
→ local enumeration
→ controlled object + privileged consumer + trigger
→ verified elevated identity
→ final evidence + cleanup + reproduction path

Assumed-breach AD sequence

starting credential
→ identity + DNS/time/DC + route
→ hosts/services + directory objects/rights
→ ranked identity/host transition
→ compatible password/hash/ticket use
→ verified session/new identity
→ authenticated re-enumeration
→ route/lateral movement
→ final domain objective and evidence

For every edge keep identity → effective group/right → target → protocol/route → resulting state together.

Save output

mkdir -p evidence/nmap evidence/web evidence/loot evidence/screenshots
nmap -Pn -sV -sC -p PORTS TARGET -oA evidence/nmap/TARGET-services
script -q -f evidence/session.txt
sha256sum FILE | tee FILE.sha256

Run exit to close/flush the script transcript.

Start-Transcript -Path .\evidence\powershell-session.txt
# commands
Stop-Transcript

Verify state

date -Is; hostname; id; ip addr; ip route

echo %DATE% %TIME%
hostname
whoami /all
ipconfig /all
route print

Transition record

observation -> prerequisite -> exact action -> decisive output -> host/identity -> new capability -> cleanup -> re-enumeration

Dead-end recovery

freeze current state
→ mark last decisive result per path
→ check coverage and authenticated views
→ separate tool/environment failure from attack evidence
→ choose one test that can change the decision
→ switch to the strongest supported branch
→ return only when new evidence changes a prerequisite
ResultLabel/action
Test did not exercise prerequisiteInconclusive; redesign test
Exact prerequisite absentDisproven; close path
Authentication succeeds, action deniedAuthorization boundary; enumerate rights
New identity/route, old results reusedStale state; re-enumerate
No decisive candidatesCoverage gap; return to enumeration

Exploit modifications

git diff --no-index original.py modified.py > exploit-changes.diff
sha256sum original.py modified.py

Record original URL/commit, changed lines, why, build/payload command, execution and result.

Before final export

  • Evidence appears next to each claim.
  • Target sections follow the control-panel/grading order.
  • Proof is read with cat/type from its original location in an interactive target shell.
  • Each proof screenshot includes the target IP; the control-panel submission is tracked separately before practical time ends.
  • Screenshots show required host/identity/IP/objective context.
  • Steps are ordered and reproducible.
  • Required scripts/PoCs are included as text inside the PDF, not as extra archive members.
  • Secrets are absent from public notes.
  • PDF is visually checked after export.
  • Archive/upload naming, size and hash follow the current official guide.
  • No AI is used on actual exam targets, proofs or reporting.

Package rehearsal

7z a OSCP-OS-XXXXX-Exam-Report.7z OSCP-OS-XXXXX-Exam-Report.pdf
7z l OSCP-OS-XXXXX-Exam-Report.7z
7z t OSCP-OS-XXXXX-Exam-Report.7z
md5sum OSCP-OS-XXXXX-Exam-Report.7z

Get-FileHash -Algorithm MD5 -LiteralPath '.\OSCP-OS-XXXXX-Exam-Report.7z'

Current baseline: exact case-sensitive names, one PDF in a non-password-protected .7z, no larger than 200 MB. Visually inspect every PDF page, compare local/upload MD5, complete the final submission action and retain acknowledgement. Recheck the official guide immediately before use.

Use the official Word/LibreOffice template unless a Markdown/Pandoc pipeline has already passed a complete dummy export and archive rehearsal.

Discover and recognize candidates

Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

Find: Maintain state and select the next evidence-producing test

Inspect the current private host/identity/route notes and compare each proposed action with a named unresolved question.

For each candidate record:
HOST | IDENTITY | ROUTE | OBSERVED CAPABILITY | MISSING CONDITION | NEXT DISCRIMINATING TEST

Recognize: The ledger distinguishes an unvalidated hypothesis from an enabled candidate and a missing coverage question.

Validate next: Verify the next test resolves a stated uncertainty and its expected outcomes change the decision.

Find: Integrate a standalone or assumed-breach AD attack

Take the current verified capability and compare it with the receiving method's starting access and missing conditions.

CURRENT RESULT -> CANDIDATE NEXT METHOD -> REQUIRED INPUT -> MISSING PROOF

Recognize: A file read does not itself create a shell; the chain needs an actual credential/identity transition.

Validate next: Verify every produced material type, account, route and service-specific right before connecting the next step.

Find: Recover from dead ends without repeating disproven paths

Compare recent attempts with the last saved working state and classify the first newly introduced boundary.

LAST VERIFIED STATE | FIRST NEW FAILURE | EXACT ERROR | CHANGED CONDITION | NEXT CONTROL

Recognize: Repeated payload changes are not testing the first missing transfer/route condition.

Validate next: Reproduce the last proof and isolate one new condition at a time; preserve rejected paths and return conditions.
