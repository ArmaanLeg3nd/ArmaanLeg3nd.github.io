    10.12.0 Choose a starting check from your current access Quick use

    Windows directory queries use the current network identity. Run only the selected check; a result is a lead until its next prerequisite is verified.

    10.12.0.1 Define LDAPSearch once in this PowerShell session

    Requires Windows PowerShell/.NET directory access, domain DNS and an authenticated directory context. No RSAT or PDC-specific connection is required. Paste the complete definition once; subsequent calls reuse it.

    function LDAPSearch {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory=$true)][ValidateNotNullOrEmpty()][string]$LDAPQuery,
        [string]$Server,
        [string]$SearchBase,
        [string[]]$Properties = @('samaccountname','distinguishedname','memberof','serviceprincipalname','description')
    )
    $root = $entry = $searcher = $results = $null
    try {
        $prefix = if ($Server) { "LDAP://$Server/" } else { 'LDAP://' }
        if (-not $SearchBase) {
            $root = New-Object System.DirectoryServices.DirectoryEntry($prefix + 'RootDSE')
            $SearchBase = [string]$root.Properties['defaultNamingContext'][0]
            if (-not $SearchBase) { throw 'No default naming context; specify Server and SearchBase.' }
        }
        $entry = New-Object System.DirectoryServices.DirectoryEntry($prefix + $SearchBase)
        $searcher = New-Object System.DirectoryServices.DirectorySearcher($entry)
        $searcher.Filter = $LDAPQuery
        $searcher.PageSize = 1000
        $searcher.PropertiesToLoad.AddRange($Properties)
        $results = $searcher.FindAll()
        foreach ($result in $results) {
            $values = @{}
            foreach ($name in $result.Properties.PropertyNames) {
                $values[$name] = @($result.Properties[$name])
            }
            [pscustomobject]@{ Path = $result.Path; Properties = $values }
        }
    }
    finally {
        foreach ($resource in @($results,$searcher,$entry,$root)) {
            if ($null -ne $resource) { $resource.Dispose() }
        }
    }
}

    Results expose .Path and .Properties; property values remain arrays. Paging handles result pages, not ranged retrieval of very large group membership attributes. memberOf is direct membership and omits primary-group membership; it is not effective authorization.

    Function missing: define it in this session. Discovery/bind failure: fix identity, DNS, server and route. Empty query: verify base/filter against a known object before concluding absence. Do not suppress exceptions as empty results. -Server DC_HOST -SearchBase 'DC=example,DC=test' selects a directory explicitly; it does not supply different credentials.

    10.12.8 Find and validate a useful domain attack path BloodHound collection and decision

    10.12.8.1 Directory-only first pass; avoids workstation contact.

    # Directory-only first pass; avoids workstation contact.
.\SharpHound.exe --CollectionMethods DCOnly --OutputDirectory .\bh --ZipFileName domain-dconly.zip

    10.12.8.2 Add only when the selected host question needs it.

    # Add only when the selected host question needs it.
.\SharpHound.exe --CollectionMethods LocalGroup --ComputerFile .\candidate-hosts.txt --OutputDirectory .\bh --ZipFileName candidate-localgroups.zip
.\SharpHound.exe --CollectionMethods Session --ComputerFile .\candidate-hosts.txt --Loop --LoopDuration 00:10:00 --OutputDirectory .\bh --ZipFileName candidate-sessions.zip

    # Linux collector alternative; confirm release/deployment compatibility.
bloodhound-python --help
bloodhound-python -u USER -p 'PASSWORD' -d DOMAIN -ns DC_IP -dc DC_HOST -c All --zip

    SharpHound with no flags uses its broader default; All runs every supported collection method and is not the automatic first pass. After import:

    1. mark only principals/hosts actually controlled;

    Enumerate GPO/OU links, then inspect the relevant directory object and SYSVOL policy component's effective control and target applicability.

Get-DomainOU | Select-Object name,gplink

    Recognize: A linked policy supplies a potential privileged consumer only for hosts to which it actually applies.

    Validate next: Check both needed policy components, effective ACEs, security/WMI filtering, target scope and refresh trigger.

    Conditional: trace GPO control to privileged policy consumption.

    10.12.18.2.16 Find: Conditional: use a validated delegation or RBCD relationship

    Inspect directory delegation flags/attributes and map the service principals before considering any impersonation request.

    Get-DomainComputer -TrustedToAuth
Get-DomainComputer -Unconstrained

    Recognize: A delegation flag opens a configuration investigation; unconstrained, constrained and RBCD require different relationships.

    Validate next: Identify exact delegation type, controlled service/machine key, target SPN, relevant account flags and KDC acceptance.

    Conditional: use a validated delegation or RBCD relationship.

    10.12.18.2.17 Find: Conditional: validate an AD CS enrollment-to-authentication path

    Enumerate the CA and enabled templates with the known directory identity, then read rights and settings rather than acting on an ESC label.

    certipy find -u 'USER@DOMAIN' -p 'PASSWORD' -dc-ip DC_IP -enabled

    Recognize: The conjunction of purpose, subject control and effective enrollment rights is a candidate; issuance and identity mapping are separate gates.

    Validate next: Check exact template/CA rights/settings, approval/signatures, required key, current mapping and authenticatable identity.

    Conditional: validate an AD CS enrollment-to-authentication path.

    10.12.18.2.18 Find: Conditional: understand a realm-wide TGT forgery from KRBTGT material

    Begin only after protected private evidence establishes the actual domain KRBTGT key and SID; inspect account/source metadata rather than assuming any domain hash suffices.

    klist
whoami /user

    Recognize: KRBTGT key exposure is the enabling post-compromise condition; an ordinary NT hash or unrelated ticket cannot substitute.

    Validate next: Verify current cryptographic material/version, realm/SID/principal, time and actual service validation; retain recovery/cleanup scope.

    Conditional: understand a realm-wide TGT forgery from KRBTGT material.

    10.12.18.3 Check which other hosts your current identity can access Move to another host

    10.12.18.3.1 Find: Match route, destination service and effective authorization

    Use the discovered destination name/address and known credential record, then inspect the selected service ports from the actual direct or established pivot source.

    nmap -Pn -sT -p 135,445,3389,5985,5986 TARGET
getent hosts TARGET_HOST

    Recognize: SMB/RPC are transport candidates while WinRM is not yet reachable; dynamic RPC and authorization are still untested.

    Validate next: Probe the destination from the real source. Check DNS/service names and each required SMB/RPC/WinRM endpoint, then test effective service authorization. An open port and an accepted password do not establish a working remote execution method.

    Match route, destination service and effective authorization.

    10.12.18.3.2 Find: Execute through uploaded service creation using PsExec

    From an accepted SMB identity inspect the required administrative share and the separate ability to create/start services on that host.

    nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares

    Recognize: Administrative-share control is one PsExec prerequisite, not proof of every service/pipe operation.

    Validate next: Validate actual SCM rights, binary compatibility, service start and named-pipe path; check the final execution identity.

    Execute through uploaded service creation using PsExec.

    10.12.18.3.3 Find: Execute commands through service command lines and SMB output

    Inspect known administrative SMB/SCM context and the output-share path when a service-command mechanism is preferable to binary upload.

    nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares

    Recognize: A share and possible service rights suggest the command-line service route, whose output still has its own access path.

    Validate next: Confirm service create/start, exact output mode/share and command effect independently from retrieved stdout.

    Execute commands through service command lines and SMB output.

    10.12.18.3.4 Find: Execute through remote Task Scheduler

    Use destination RPC/SMB evidence and effective administrative/task rights to investigate Task Scheduler as a one-shot execution consumer.

    Test-NetConnection TARGET -Port 135
Test-NetConnection TARGET -Port 445

    Recognize: The required network services are candidates; a task cannot be assumed creatable from port results.

    Validate next: Check negotiated RPC reachability, task-create permission, actual principal and administrative output channel.

    Execute through remote Task Scheduler.

    10.12.18.3.5 Find: Execute through WMI or native CIM over DCOM

    Investigate WMI from RPC/service inventory and exact account rights; keep process creation and SMB-based output retrieval as separate legs.

    Test-NetConnection TARGET -Port 135
Test-NetConnection TARGET -Port 445

    Recognize: Port 135 and an output route justify further checks but do not prove a WMI process can be created.

    Validate next: Validate dynamic ports, DCOM/WMI authorization, native CIM transport choice and actual effect.

    Execute through WMI or native CIM over DCOM.

    10.12.18.3.6 Find: Execute through an authorized DCOM application object

    Use the target's RPC and administration evidence to investigate a specific supported COM application, rather than treating DCOM as a universal shell.

    Test-NetConnection TARGET -Port 135

    Recognize: A named application and route form a candidate; component availability and allowed activation/method remain separate.

    Validate next: Check dynamic RPC, actual class/rights, authentication/tool support, method and verifiable output/effect.

    Execute through an authorized DCOM application object.

    10.12.18.3.7 Find: Use WinRM, WinRS or PowerShell remoting

    Check observed WinRM listeners from the real source and relate the identity to the configured endpoint/session authorization.

    Test-NetConnection TARGET -Port 5985
Test-NetConnection TARGET -Port 5986

    Recognize: A reachable endpoint plus a known credential is a candidate, not proof the account may enter that remoting session.

    Validate next: Verify accepted authentication, correct name/TLS context, endpoint rights and any second-hop requirements.

    Use WinRM, WinRS or PowerShell remoting.

    10.12.18.3.8 Find: Obtain an authorized RDP interactive session

    Check the destination RDP endpoint and use actual group/logon-policy evidence for the candidate identity; determine whether password or Restricted Admin is intended.

    Test-NetConnection TARGET -Port 3389

    Recognize: RDP transport does not grant desktop access; Restricted Admin/hash use has additional requirements.

    Validate next: Check NLA/TLS, identity qualification, logon authorization and the chosen authentication mode.

    Obtain an authorized RDP interactive session.

    10.12.18.3.9 Find: Select password, NT hash, key-to-ticket or ticket authentication

    Return to the credential source and inspect format, identity and ticket service scope before selecting a remote protocol.

    klist
getent hosts TARGET_HOST
date -u

    Recognize: The cache permits investigating a matching CIFS action, not arbitrary WinRM or a new TGS without a TGT/KDC route.

    Validate next: Match NTLM versus Kerberos support, account/domain, key/encryption policy, name/time and destination rights.

    Select password, NT hash, key-to-ticket or ticket authentication.
