Escalate privileges on Windows

Strategy map | Master Notes | Operational index | Cheatsheets

An administrator-group membership, enabled token privilege, writable object and effective privileged execution are different claims. Establish the precise right, consumer identity and available trigger before choosing a route.

Speedrun blocks: 9. Documented methods: 13.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Record the token and host context

Check the current token before choosing an exploit or collector build.

hostname
whoami /all
systeminfo
ipconfig /all
  • If SeImpersonatePrivilege: Check its enabled state and the operation/access needed by that specific technique. → Select a privilege-backed impersonation or object-control route.
  • If SeBackupPrivilege: Inspect the permitted backup operation and the exact source it can read. → Use backup privilege to obtain protected local credential material.
  • If Service/task activity or a useful group membership: Inspect the actual objects and ACLs. → Prove effective file, registry and service-object permissions.
  • Otherwise: No immediate token route: run the broad collector, then verify its service/file findings. → Turn automated Windows findings into manually verified candidates.

Run winPEAS early and save its report

Transfer a reviewed binary matching the host architecture. The log option writes out.txt; inspect it before selecting a route. Native checks remain available if execution is blocked.

winPEASx64.exe log
  • If Modifiable service or writable service binary: Check sc qc/sdshow and the actual binary/parent ACL, service account and restart rights. → Change a privileged service's executable configuration.
  • If Unquoted service path: Check the exact executable prefixes for write access and a privileged restartable consumer. → Exploit an unquoted service path with a writable earlier prefix.
  • If A saved credential/config finding: Read the named source and classify the account/material. → Recover Windows application, history and stored-credential artifacts.
  • Otherwise: The collector is blocked or reports no useful candidate: continue native ACL/service/task inspection. → Prove effective file, registry and service-object permissions.

Verify the specific service/task route

Configuration write, binary replacement, unquoted-prefix write and dependency loading require different rights.

whoami /all
icacls "C:\Path\To\OBJECT"
icacls "C:\Path\To"
sc.exe sdshow SERVICE
  • If Service configuration can be changed: Confirm the service runs as a stronger identity and you can cause a start/restart. → Change a privileged service's executable configuration.
  • If Only the binary or its parent is writable: Check replacement semantics, the consumer identity and a trigger. → Replace a privileged service binary or consumed file.
  • If A scheduled task consumes a writable file: Inspect the task principal, action and schedule. → Control scheduled tasks, startup files or autostart consumers.
  • Otherwise: The highlighted path is not effectively writable: reject that candidate and inspect another actual object. → Prove effective file, registry and service-object permissions.

Discovery workflow

Start with a Windows foothold. Administrator-group membership, a high-integrity token and a working privileged trigger are separate facts.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Inspect whoami /all and host/process state before choosing a privilege route: Establish Windows token, host and process context.
  2. Inventory real services/tasks and inspect exact object and parent ACLs: Prove effective file, registry and service-object permissions; Change a privileged service's executable configuration; Control scheduled tasks, startup files or autostart consumers.
  3. Separate writable service configuration, replaceable binaries, unquoted prefixes and dependency loads: Replace a privileged service binary or consumed file; Exploit an unquoted service path with a writable earlier prefix; Control a privileged DLL, helper or configuration load.
  4. Follow application/history/saved-credential artifacts and exact token privileges: Recover Windows application, history and stored-credential artifacts; Select a privilege-backed impersonation or object-control route; Use backup privilege to obtain protected local credential material.
  5. Match software/driver/build evidence only after validating simpler permission routes: Select a matching application, driver or kernel exploit.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Token, ACL and credential state: Establish Windows token, host and process context, Prove effective file, registry and service-object permissions, Recover Windows application, history and stored-credential artifacts.
  • Services and privileged consumers: Change a privileged service's executable configuration, Replace a privileged service binary or consumed file, Exploit an unquoted service path with a writable earlier prefix, Control a privileged DLL, helper or configuration load, Control scheduled tasks, startup files or autostart consumers.
  • Installer and token-backed operations: Validate elevated installer policy and administrative-token context, Select a privilege-backed impersonation or object-control route, Use backup privilege to obtain protected local credential material.
  • Software and candidate generation: Select a matching application, driver or kernel exploit, Turn automated Windows findings into manually verified candidates.

Establish Windows token, host and process context

Blocks: 9. Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A verified identity, integrity, privilege and host state for candidate selection.

2. Recognition clues

A new Windows session or claimed administrator/SYSTEM transition.

Find the clue from your starting access

Where to investigate: At a new foothold inspect the complete token and host/service inventory before classifying the session as an administrator.

Discovery action — reference example:

whoami /all
systeminfo
tasklist /svc

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

BUILTIN\Administrators: Group used for deny only
Mandatory Label\Medium Mandatory Level

Recognize this detail: An Administrators SID exists but this effective process is filtered/medium-integrity.

Still missing before method selection: Check actual enabled privileges and object operations in the process that will perform the action.

Outcome after checkingExample and next decision
Enabled after validationA higher-integrity/SYSTEM token and intended operation are verified: record that privilege state.
Ruled out in this contextA medium filtered token cannot perform the assumed administrative action: reject that privilege assumption.
InconclusiveUsername/group membership alone leaves token state unknown; inspect whoami /all.

If you do not yet have this clue: start with Verify command execution, host and represented identity.

3. Prerequisites

Starting access: A verified Windows foothold with a known token, integrity level and groups. Required conditions: A functioning command channel and the actual effective token/process context.

4. Discover and verify prerequisites

hostname
whoami /all
systeminfo
ipconfig /all

5. Why it works

Group membership can be filtered in a token, and a network logon context can differ from interactive access. Check privileges and integrity where the intended operation runs.

7. Worked example — hypothetical

Observation: the username belongs to Administrators. Test: inspect token groups/integrity and effective privileges. Illustrative output: the administrator SID is deny-only in a medium token. Interpretation: do not assume high-integrity service-control rights.

8. Verify the result

Verify represented user/SID, enabled group/privilege state and actual privileged operation.

9. Failure and fallback

A prompt title or account name is insufficient. WMIC may be absent; use the documented CIM/PowerShell alternatives.

Prove effective file, registry and service-object permissions

Blocks: 9. Operational procedure | Quick sheet

1. Purpose and result

A specific confirmed control primitive for a privileged consumer.

2. Recognition clues

A privileged object appears writable or an ACL tool reports a useful right.

Find the clue from your starting access

Where to investigate: Take a real service/task/application path from inventory, then inspect its file, parent and separate service-object permissions.

Discovery action — reference example:

icacls "C:\Path\To\OBJECT"
icacls "C:\Path\To"
sc.exe sdshow SERVICE

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

File: BUILTIN\Users:(RX)
Parent: DOMAIN\GROUP:(M)
Service-object rights: separate DACL

Recognize this detail: A modifiable parent can differ from a read-only file; service configuration rights are another control plane.

Still missing before method selection: Use icacls/Get-Acl on the reported object and parents. For a service also inspect sc qc/sc sdshow; for a task inspect its action/principal. Check the specific write/replace/configuration operation and its trigger.

Outcome after checkingExample and next decision
Enabled after validationThe intended effective operation and higher consumer are proved: select that object-control method.
Ruled out in this contextOnly read/execute applies to the current token: reject the proposed modification.
InconclusiveAn ACL for an inactive or ambiguous group leaves effective access unresolved.

If you do not yet have this clue: start with Establish Windows token, host and process context.

3. Prerequisites

Starting access: A verified Windows foothold with a known token, integrity level and groups. Required conditions: Correct trustee/token, object type and effective rights including parents and deny entries.

4. Discover and verify prerequisites

whoami /all
icacls "C:\Path\To\OBJECT"
icacls "C:\Path\To"
sc.exe sdshow SERVICE

5. Why it works

A service-object DACL controls operations such as configuration changes; the executable's filesystem ACL is separate. Parent delete/create rights can allow replacement without direct file modification.

6. Execute and choose variants

icacls "C:\Path\To\OBJECT"
sc.exe sdshow SERVICE
accesschk.exe -accepteula -nobanner -v -w "USER" "C:\Path\To\OBJECT"
accesschk.exe -accepteula -nobanner -v -w -c "USER" SERVICE

icacls common rights: F full, M modify, RX read/execute, R read, W write, D delete. Common inheritance markers: I, OI, CI, IO, NP.

File, directory, registry, service-object, task and process permissions are separate. Check whether the ACE applies to the current user or an enabled group and grants the exact required operation. Mandatory Integrity Control can still block a lower-integrity write.

7. Worked example — hypothetical

Observation: a service executable is read-only but its directory grants replacement rights. Test: inspect the effective token and parent permissions. Illustrative output: replacement is possible but service restart is denied. Interpretation: the control primitive is valid; the trigger remains missing.

8. Verify the result

Name the exact allowed operation on the exact object and independently check a privileged consumer/trigger.

9. Failure and fallback

Generic write labels can refer to another object or an inactive group. Resolve actual effective rights before modifying anything.

10. Next transitions

Replace a privileged service binary or consumed file; Control scheduled tasks, startup files or autostart consumers; Control a privileged DLL, helper or configuration load.

Recover Windows application, history and stored-credential artifacts

Blocks: 9. Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

Typed secret material or a verified saved-credential consumer transition.

2. Recognition clues

Readable application configuration, unattended setup, PowerShell trails or Credential Manager entries.

Find the clue from your starting access

Where to investigate: Follow actual application/configuration paths, PSReadLine history and saved-credential targets under the current readable user context.

Discovery action — reference example:

cmdkey /list
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v DefaultUserName

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

cmdkey target: Domain:target=TARGET_HOST
User: DOMAIN\USER
Password: not displayed

Recognize this detail: A target-bound saved credential is a possible consumer capability, not a plaintext password.

Still missing before method selection: Establish protecting user/context, intended logon type and an actually permitted saved-credential or decryption route.

Outcome after checkingExample and next decision
Enabled after validationThe matching consumer accepts the credential and the resulting token is checked: use that access.
Ruled out in this contextThe stored entry belongs to another context/target and cannot be used here: reject that transition.
InconclusiveA protected blob/listing without keys or consumer evidence leaves usable credentials unproved.

If you do not yet have this clue: start with Establish Windows token, host and process context.

3. Prerequisites

Starting access: A verified Windows foothold with a known token, integrity level and groups. Required conditions: Artifact read permission and exact protecting identity/context for saved or DPAPI material.

4. Discover and verify prerequisites

cmdkey /list
whoami /all

5. Why it works

A cmdkey entry proves a target-bound stored credential, not plaintext disclosure. Saved-credential use and DPAPI decryption require matching contexts; runas does not inherently bypass UAC.

6. Execute and choose variants

Stored credentials and PowerShell trails
cmdkey /list
vaultcmd /list
vaultcmd /listcreds:"Windows Credentials" /all

$history = (Get-PSReadLineOption).HistorySavePath
$history
Get-Content -LiteralPath $history -ErrorAction SilentlyContinue
Get-ItemProperty 'HKLM:\Software\Policies\Microsoft\Windows\PowerShell\Transcription' -ErrorAction SilentlyContinue
Get-ItemProperty 'HKCU:\Software\Policies\Microsoft\Windows\PowerShell\Transcription' -ErrorAction SilentlyContinue
Get-WinEvent -LogName 'Microsoft-Windows-PowerShell/Operational' -ErrorAction SilentlyContinue |
  Where-Object Id -in 4103,4104 | Select-Object -First 50 TimeCreated,Id,Message

A cmdkey entry is target/context-bound and does not reveal a password. DPAPI-protected data needs the protecting user/machine context and keys. Clear-History does not necessarily clear PSReadLine's saved file.

Targeted application/file/registry search 
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v DefaultUserName

InconclusiveOrdinary copy denial does not settle a backup-semantic operation; verify the API rather than inferring absence.

If you do not yet have this clue: start with Establish Windows token, host and process context.

3. Prerequisites

Starting access: A verified Windows foothold with a known token, integrity level and groups. Required conditions: Usable backup privilege, compatible backup API/command and a matched protected source set with a writable destination.

4. Discover and verify prerequisites

whoami /priv
reg query HKLM\SYSTEM\CurrentControlSet\Control\Lsa

5. Why it works

Backup-mode read access can bypass ordinary read ACLs through supporting APIs; it does not grant arbitrary execution. Matched registry hives supply the key material required for credential parsing.

6. Execute and choose variants

Backup privilege to local credential material 
reg save HKLM\SAM C:\Windows\Temp\SAM.hive
reg save HKLM\SYSTEM C:\Windows\Temp\SYSTEM.hive

impacket-secretsdump -sam SAM.hive -system SYSTEM.hive LOCAL

Use the matched hive pair. Output is local credential material, not automatic SYSTEM/domain/remote authorization; classify and validate it through the credential procedure.

7. Worked example — hypothetical

Observation: a backup-capable account cannot directly read a protected file. Test: use the documented privilege-aware hive-save route. Illustrative output: matched SAM/SYSTEM files are obtained. Interpretation: parse offline and classify the resulting local hashes.

8. Verify the result

Verify complete matched source artifacts and exact account mapping after parsing.

9. Failure and fallback

Ordinary file-copy denial does not disprove backup semantics; missing required hives or protection can still prevent useful extraction.

10. Next transitions

Extract local account hashes from matched SAM and SYSTEM; Recover or reuse an NT password hash; Classify the artifact and its identity context.

3. Prerequisites

Starting access: A verified Windows foothold with a known token, integrity level and groups. Required conditions: Verified current token and architecture, a compatible reviewed executable or allowed PowerShell runtime, and a writable report location.

4. Discover and verify prerequisites

whoami /all
$PSVersionTable
$ExecutionContext.SessionState.LanguageMode

5. Why it works

winPEAS, PrivescCheck, Seatbelt and PowerUp collect different evidence. Highlighted services or privileges still require exact ACL, token, identity and trigger checks.

6. Execute and choose variants

winPEASx64.exe log
Seatbelt.exe -group=system -outputfile="C:\Windows\Temp\seatbelt-system.txt"
Seatbelt.exe -group=user -q -outputfile="C:\Windows\Temp\seatbelt-user.json"

powershell.exe -ExecutionPolicy Bypass -Command ". .\PrivescCheck.ps1; Invoke-PrivescCheck -Report TXT,HTML"
Import-Module .\PowerUp.ps1
Invoke-AllChecks

winPEAS is broad; Seatbelt is a targeted survey and publishes source rather than official binaries; PrivescCheck evaluates the current token and skips some checks when elevated; PowerUp is useful but its upstream repository was archived. AV/script-policy failure is a tooling limitation—use native checks.

Convert every highlight into:

CANDIDATE | CURRENT TOKEN | CONTROLLED INPUT | EFFECTIVE RIGHT | CONSUMER | RUN-AS | TRIGGER | EXPECTED EFFECT | STATUS

7. Worked example — hypothetical

Observation: a scanner flags an unquoted path. Test: inspect the earlier path prefixes and trigger. Illustrative output: none is writable. Interpretation: discard the exploit hypothesis and retain the configuration fact.

8. Verify the result

Read out.txt or the helper report. Use sc.exe qc/sdshow plus icacls for a service, inspect task XML/run-as for a scheduled task, or check whoami /priv for a token finding

9. Failure and fallback

Binary/script blocked or report empty: check architecture and PowerShell language/policy, then use native service/task/ACL checks. A blocked helper does not disprove the finding

10. Next transitions

Prove effective file, registry and service-object permissions; Change a privileged service's executable configuration; Select a privilege-backed impersonation or object-control route.
