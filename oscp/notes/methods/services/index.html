Extract opportunities from services

Strategy map | Master Notes | Operational index | Cheatsheets

A service can disclose names, files, rights or execution. Test authentication, read, write and execution separately. A write becomes an execution path only when a useful consumer and trigger exist.

Speedrun blocks: 2; authenticated re-enumeration throughout. Documented methods: 15.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Try SMB with the actual access context

Use the anonymous form first when no credentials exist; use the authenticated variant when an identity is available.

smbclient -N -L //TARGET
  • If A readable share contains config, backups or keys: Read the exact file and record its source before testing any recovered value. → Classify the artifact and its identity context.
  • If A working domain identity: Enumerate domain shares with that identity; share listing alone is not file access. → Read domain shares, SYSVOL and NETLOGON for useful artifacts.
  • Otherwise: SMB is denied: inspect another discovered protocol, not repeated guesses against the same identity. → Identify applications and validate selected NSE checks.

Query exposed names and configuration

Use only an observed/assigned community and the correct SNMP version; preserve the returned OIDs.

snmpwalk -v2c -c COMMUNITY TARGET 1.3.6.1.2.1.1
  • If Process arguments or configuration contain an account value: Classify its account scope and format. → Classify the artifact and its identity context.
  • If A hostname or directory-service clue: Resolve it through the relevant name service. → Expand names through DNS records and zone transfers.
  • Otherwise: No useful SNMP response: return to the confirmed service list and choose its native client. → Identify applications and validate selected NSE checks.

Inspect database identity and grants

Use this branch only for confirmed SQL Server with an accepted login. Other database clients are separate procedures.

SELECT SYSTEM_USER, ORIGINAL_LOGIN(), @@VERSION;
SELECT IS_SRVROLEMEMBER('sysadmin');
  • If A permitted impersonation or command facility: Check the effective login and the exact enabled operation before attempting an OS effect. → Use SQL Server rights, impersonation and command facilities.
  • If MySQL/MariaDB identified instead of SQL Server: Use the MySQL/MariaDB grants and file rules rather than SQL Server syntax. → Use MySQL/MariaDB data and file primitives.
  • Otherwise: Login succeeds but the action is denied: inspect grants under the same identity. → Use SQL Server rights, impersonation and command facilities.

Discovery workflow

Start with application evidence from discovery; anonymous access, valid credentials and useful rights are separate questions.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Use the matching protocol client and establish which identity the service accepts: Use anonymous or authenticated FTP file access; Enumerate SMB/RPC shares, files and identities; Use SSH passwords, keys and forwarding-capable access.
  2. Investigate names, account clues and configuration with the available service context: Expand names through DNS records and zone transfers; Extract configuration and process information through SNMP; Enumerate SMTP identities and accessible mailbox protocols; Discover LDAP naming contexts and authenticated search.
  3. For databases inspect the current identity and grants before file or execution hypotheses: Use MySQL/MariaDB data and file primitives; Use SQL Server rights, impersonation and command facilities; Use PostgreSQL data and privileged program execution.
  4. Retrieve relevant artifacts, classify credentials, and re-enumerate with any new accepted identity: Classify the artifact and its identity context; Validate known passwords and context-specific reuse.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • File and shell access: Use anonymous or authenticated FTP file access, Enumerate SMB/RPC shares, files and identities, Inspect RPC/NFS exports and effective file identity, Use SSH passwords, keys and forwarding-capable access.
  • Identity and configuration disclosure: Expand names through DNS records and zone transfers, Extract configuration and process information through SNMP, Enumerate SMTP identities and accessible mailbox protocols, Discover LDAP naming contexts and authenticated search.
  • Database privileges and primitives: Use MySQL/MariaDB data and file primitives, Use SQL Server rights, impersonation and command facilities, Use PostgreSQL data and privileged program execution, Inspect Redis access and persistence boundaries, Triage Oracle listener and database identity.
  • Remote access and uncommon applications: Validate RDP, WinRM, VNC and Telnet access contexts, Investigate SIP/IRC identity and configuration clues.

Use anonymous or authenticated FTP file access

Blocks: 2; authenticated re-enumeration throughout. Operational procedure | Quick sheet

1. Purpose and result

Retrieved files, configuration or a verified writable location.

2. Recognition clues

An FTP banner or accessible listing.

Find the clue from your starting access

Where to investigate: After identifying FTP, test the allowed anonymous context or one known credential and inspect its directory namespace.

Discovery action — reference example:

curl -v ftp://TARGET/
curl -v --user 'USER:PASSWORD' ftp://TARGET/

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

230 Login successful
LIST: application.conf; backups/
RETR application.conf: 226 Transfer complete

Recognize this detail: A listing identifies candidate artifacts; a completed RETR with recognizable bytes establishes read access.

Still missing before method selection: Validate the account context, file contents, data-channel reachability and any separate write/consumer conditions.

Outcome after checkingExample and next decision
Enabled after validationThe relevant file is readable and contains a current typed secret: follow credential classification.
Ruled out in this contextAnonymous login is denied: rule out anonymous access, retaining authenticated FTP as a separate possibility.
InconclusiveLogin works but data transfer hangs: inspect active/passive data routing before concluding file access is denied.

If you do not yet have this clue: start with Identify applications and validate selected NSE checks.

3. Prerequisites

Starting access: A confirmed reachable application; anonymous context or one identified credential. Required conditions: Anonymous login allowed or a valid FTP identity; data-channel connectivity and object-specific read/write rights.

4. Discover and verify prerequisites

curl -v ftp://TARGET/
curl -v --user 'USER:PASSWORD' ftp://TARGET/

5. Why it works

FTP authentication and directory listing do not guarantee downloads or uploads. Passive/active data channels can fail independently of the control connection; uploaded bytes need a separate execution consumer.

6. Execute and choose variants

Recognize: FTP usually appears on TCP/21, but trust an FTP banner or protocol response on any port. Goal: determine authentication, listable/readable content and effective write locations.

Baseline: anonymous access
ftp TARGET

At the prompts, try user anonymous and an email-like password. Then:

status
pwd
ls -la
binary
get FILE
quit

If login succeeds but listing/transfer fails, use the client's passive command to toggle data-channel mode and retry once before changing credentials.

Decisive output: code 230 accepts the login; directory listings and successful RETR establish read access. Inspect downloaded backups, configuration, keys and source locally. Store target artifacts outside this public repository.

Variant — authenticated FTP 
ftp TARGET

Enter USER and the password when prompted. Enumerate from the authenticated root again; it may expose a different namespace than anonymous access.

Variant — curl listing, download and bounded write test 
curl --list-only ftp://TARGET/
curl -o FILE ftp://TARGET/path/FILE
curl --user USER ftp://TARGET/
curl --user USER -o FILE ftp://TARGET/path/FILE
curl --user USER --upload-file ./probe.txt ftp://TARGET/path/probe.txt

Omit --user for anonymous access. Let curl prompt for an authenticated password instead of placing it in shell history. Upload only a harmless uniquely named probe when write validation is necessary and authorized; remove it through the FTP client after the test.

Variant — focused Nmap helpers 
nmap -sV -p PORT --script ftp-anon,ftp-syst TARGET

ftp-anon checks anonymous login and may flag writable entries; ftp-syst asks for server/system information. Manually confirm useful access with a protocol client.

Failure cues: 530 means that login was rejected, not that FTP has no other usable identity. A listing failure after 230 may be a data-channel/passive-mode or authorization problem. A successful upload proves write access only; it does not prove that a web server, scheduled task or privileged process consumes that file.

Next action: inspect recovered files; record exact read/write boundaries; validate any new credential once against its likely service; send a writable-consumer hypothesis to the appropriate web, execution or privilege-escalation block.

7. Worked example — hypothetical

Observation: anonymous login succeeds. Test: list and download one relevant readable configuration. Illustrative output: an application username is present. Interpretation: classify its credential context and test only a compatible service.

8. Verify the result

Retrieve recognizable bytes or independently verify an uploaded canary; distinguish listing, read and write rights.

9. Failure and fallback

Login succeeds but transfers hang: diagnose the data path. A writable upload directory alone does not establish command execution.

10. Next transitions

Classify the artifact and its identity context; Inspect source, backups, configuration and repository artifacts; Validate known passwords and context-specific reuse.

Enumerate SMB/RPC shares, files and identities

Blocks: 2; authenticated re-enumeration throughout. Operational procedure | Quick sheet

1. Purpose and result

Domain/user clues, readable files or object-specific writable access.

2. Recognition clues

SMB/RPC endpoints, domain clues or new credentials.

Find the clue from your starting access

Where to investigate: Start from confirmed SMB and explicitly compare anonymous versus a known authenticated context, then open a relevant named share.

Discovery action — reference example:

smbclient -L //TARGET -N
smbclient -L //TARGET -U 'DOMAIN/USER'

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Sharename       Type
SHARE           Disk
NETLOGON        Disk

Recognize this detail: A share name supplies a filesystem investigation target; listing it does not prove read, write or service creation.

Still missing before method selection: Connect to the named share under the identity that listed it, then ls/get the exact object. Listing a share does not prove read or write. For a write candidate, verify the path operation and identify a separate execution consumer before treating it as access.

Outcome after checkingExample and next decision
Enabled after validationA relevant configuration can be retrieved: inspect its account/secret context.
Ruled out in this contextThe authenticated account cannot read that object: discard the read path for this identity, not all SMB opportunities.
InconclusiveLogin succeeds but listing fails: check a justified known share path and separate share/NTFS authorization.

If you do not yet have this clue: start with Identify applications and validate selected NSE checks.

3. Prerequisites

Starting access: A confirmed reachable application; anonymous context or one identified credential. Required conditions: Reachable SMB/RPC; anonymous, guest, local or domain context must be explicit; share and filesystem ACLs both matter.

4. Discover and verify prerequisites

smbclient -L //TARGET -N
smbclient -L //TARGET -U 'DOMAIN/USER'

5. Why it works

Session establishment, share enumeration, filesystem rights and remote execution are separate authorization layers. A credential change can reveal entirely new shares and files.

6. Execute and choose variants

Recognize: direct-hosted SMB commonly uses TCP/445; NetBIOS session service commonly uses TCP/139; MS-RPC endpoint mapping commonly uses TCP/135. They are related Windows surfaces but not interchangeable. Goal: distinguish null, guest and authenticated contexts; enumerate shares, files, users, groups, domain/workgroup clues and actual permissions.

Baseline: list shares without credentials
smbclient -N -L //TARGET

Decisive output: a share list proves that this access context can enumerate names. It does not prove access to share contents. NT_STATUS_ACCESS_DENIED means this context was denied; repeat after obtaining a legitimate credential.

Variant — authenticated share listing and connection 
smbclient -L //TARGET -U 'DOMAIN/USER'
smbclient //TARGET/SHARE -U 'DOMAIN/USER'
smbclient -L //TARGET -U 'TARGET/USER'
smbclient -L //TARGET -U 'guest%'

The first two forms use a domain identity, the third makes a local target account explicit, and the fourth tests a guest account with an empty password. Let the client prompt for non-empty passwords. Inside the share:

pwd
ls
allinfo FILE
get FILE
mkdir probe-dir
rmdir probe-dir
exit

Use a harmless uniquely named directory only when write permission must be verified. A successful create/remove establishes share-level write access, not code execution.

Variant — recursive retrieval 
smbclient //TARGET/SHARE -U 'DOMAIN/USER' -c 'recurse ON;prompt OFF;mget *'

Run from a dedicated local evidence directory and review expected volume first. Search downloaded configuration, scripts, backups, keys and unattended-install files locally; never publish recovered data.

Variant — RPC null or authenticated session 
rpcclient -U '' -N TARGET
rpcclient -U 'DOMAIN/USER' TARGET

Useful interactive queries:

srvinfo
enumdomains
enumdomusers
enumdomgroups
queryuser RID
netshareenumall
quit

Null-session denial is common on modern systems. Authenticated output must be labelled with the identity that produced it.

Variant — fast permission summary and consolidated candidates 
nxc smb TARGET -u USER -p PASSWORD --shares
enum4linux-ng -A TARGET

NetExec (nxc) is the current command name on recent Kali releases; older material may use crackmapexec. These tools consolidate candidates. Confirm useful shares and files with smbclient or native access.

Variant — protocol, signing and time clues 
nmap -p 139,445 --script smb-protocols,smb2-security-mode,smb2-time TARGET

Signing and dialect results affect later relay/exploit decisions but are not vulnerabilities by themselves. The older smb-os-discovery script depends on SMBv1 behavior and may not identify modern hosts reliably.

Variant — Windows built-ins 
net view \\TARGET /all
Get-ChildItem \\TARGET\SHARE
Get-Content \\TARGET\SHARE\FILE
