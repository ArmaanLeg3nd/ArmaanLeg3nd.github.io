Discover attack surfaces

Strategy map | Master Notes | Operational index | Cheatsheets

Discovery establishes reachable behavior from a particular source. Keep host discovery, TCP coverage, UDP coverage and application identity separate; each produces different evidence.

Speedrun blocks: 1; revisit after new routes or hosts. Documented methods: 7.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Confirm the source route

Run from the machine that will send the scan. Keep the assigned scope explicit.

ip addr
ip route get TARGET
nmap -sn SUBNET -oA host-discovery
  • If A route selects the expected interface/source: Reachability still needs a probe; a route lookup alone is not a live host. → Discover TCP ports with SYN or connect scans.
  • Otherwise: No response from host discovery: test the assigned host without assuming it is offline. → Discover TCP ports with SYN or connect scans.

Build a TCP port list with Nmap

The command below scans all TCP ports with SYN privileges. Create the scans output directory first; use the complete connect-scan variant when unprivileged. Keep the fast initial pass distinct from full coverage.

sudo nmap -sS -n -p- -oA scans/tcp-all TARGET
  • If An open TCP port: Run focused service detection on the discovered ports, including nonstandard ones. → Identify applications and validate selected NSE checks.
  • Otherwise: Only TCP was checked: investigate UDP when the objective or DNS/SNMP/RPC clues call for it. → Probe UDP and resolve ambiguous silence.

Identify the responding application

Keep the endpoint and raw service output; choose the matching client from its response.

nmap -Pn -sV -p PORTS TARGET -oA selected-services
nmap --script-help SCRIPT_NAME
  • If SMB/RPC responds: Check anonymous or known-identity share access. → Enumerate SMB/RPC shares, files and identities.
  • If An HTTP response or redirect: Resolve the correct scheme and hostname before directory discovery. → Establish scheme, host, redirects and request state.
  • If An unrecognized listener: Send a protocol-specific probe instead of choosing an exploit by port number. → Discriminate unknown listeners and use scanner alternatives.
  • Otherwise: Results conflict with client behavior: rebuild the endpoint queue from confirmed responses. → Validate uncertain results and rebuild the service queue.

Discovery workflow

Start with an assigned address/list and your actual source interface; no open service is assumed.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Confirm the source interface, route and host-discovery limitations: Validate the source path and discover hosts.
  2. Separate initial TCP selection, full TCP coverage and UDP investigation: Discover TCP ports with SYN or connect scans; Probe UDP and resolve ambiguous silence.
  3. Establish application evidence on discovered listeners, including nonstandard ports: Identify applications and validate selected NSE checks; Discriminate unknown listeners and use scanner alternatives.
  4. Save the endpoint queue and revisit it after a new identity or route: Validate uncertain results and rebuild the service queue.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Source and reachability: Validate the source path and discover hosts, Enumerate reachable endpoints from a Windows source.
  • Transport coverage and application identity: Discover TCP ports with SYN or connect scans, Probe UDP and resolve ambiguous silence, Identify applications and validate selected NSE checks, Discriminate unknown listeners and use scanner alternatives.
  • Evidence and re-enumeration: Validate uncertain results and rebuild the service queue.

Validate the source path and discover hosts

Blocks: 1; revisit after new routes or hosts. Operational procedure | Quick sheet

1. Purpose and result

A source-qualified reachable-host list and a defensible discovery limitation.

2. Recognition clues

No response, a new subnet, or uncertainty about the interface and route.

Find the clue from your starting access

Where to investigate: From the assessment host inspect the assigned interface and the route to the exact target before interpreting silence.

Discovery action — reference example:

ip addr
ip route get TARGET
nmap -sn SUBNET -oA host-discovery

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

TARGET via VPN_GATEWAY dev tun0 src SOURCE_IP
Nmap scan report for HOSTNAME (TARGET)
Host is up

Recognize this detail: The route names the intended interface/source; a responder is evidence from that source, not a global reachability claim.

Still missing before method selection: Check scope, target state and whether host-discovery probes are permitted by this path.

Outcome after checkingExample and next decision
Enabled after validationThe assigned route is correct and the selected application responds: proceed to service coverage.
Ruled out in this contextThe route points outside the assigned VPN: repair that route before evaluating the target.
InconclusiveNo discovery response but a plausible route exists: the host may filter probes; test a justified selected port.

If you do not yet have this clue: start with this topic's discovery workflow.

3. Prerequisites

Starting access: An explicitly assigned address or host list and a known source position. Required conditions: Correct VPN/interface and explicit scope; discovery probes must be compatible with the path.

4. Discover and verify prerequisites

ip addr
ip route get TARGET
nmap -sn SUBNET -oA host-discovery

5. Why it works

Discovery probes identify responders; silence can be caused by filtering. A known assigned host can still require a port scan that skips discovery.

6. Execute and choose variants

Purpose: Confirm the source path and discover explicitly assigned hosts before spending time on port coverage.

1. Check the path

From the target's working folder:

mkdir -p scans
ip -br addr
ip route get TARGET

Read: selected interface/source address. A route lookup does not prove reachability.

Variants — discover one host, a host list or a subnet
Host discovery

One host:

nmap -sn -n -oA scans/host TARGET

Assigned list: put IPs in targets.txt, one per line.

nmap -sn -n -iL targets.txt -oA scans/hosts

Explicitly assigned subnet:

nmap -sn -n -oA scans/subnet SUBNET

No response does not establish that a host is offline. A list of assigned hosts does not imply the surrounding subnet is in scope.

7. Worked example — hypothetical

Observation: a known host is absent from the ping sweep. Test: confirm the route and scan its selected application port with discovery skipped. Illustrative output: TCP/443 is open. Interpretation: discovery missed a live service; retain the host and enumerate HTTPS.

8. Verify the result

Record source address/interface, route and the exact responding endpoint; a missing ping response does not prove a host is down.

9. Failure and fallback

No route or wrong VPN interface is an environment failure. If only discovery is blocked, use the known-host TCP method; a SOCKS path requires a compatible connect-based client.

10. Next transitions

Discover TCP ports with SYN or connect scans; Probe UDP and resolve ambiguous silence; Relay a single TCP service through a fixed forward; Enumerate reachable endpoints from a Windows source.

Enumerate reachable endpoints from a Windows source

Blocks: 1; revisit after new routes or hosts. Operational procedure | Quick sheet

1. Purpose and result

Selected TCP reachability from the Windows network position.

2. Recognition clues

The useful vantage point is a Windows host without Nmap.

Find the clue from your starting access

Where to investigate: From the Windows foothold inspect interfaces/routes, then check an assigned internal host's selected service ports.

Discovery action — reference example:

Get-NetIPConfiguration
Get-NetRoute -AddressFamily IPv4
Test-NetConnection TARGET -Port 445

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

InterfaceAlias   : ADAPTER
SourceAddress    : SOURCE_IP
RemotePort       : 445
TcpTestSucceeded : True

Recognize this detail: The service is reachable from this Windows source; this can reveal a useful vantage point unavailable from Kali.

Still missing before method selection: Confirm application/authentication and whether a forward or a native client can use that route.

Outcome after checkingExample and next decision
Enabled after validationA protocol request works from this source: choose an authorized service client or suitable tunnel.
Ruled out in this contextThe selected service is conclusively closed from this source: choose another observed endpoint.
InconclusiveTcpTestSucceeded False with uncertain routing/firewall does not prove the host is down.

If you do not yet have this clue: start with Validate the source path and discover hosts.

3. Prerequisites

Starting access: An explicitly assigned address or host list and a known source position. Required conditions: A permitted Windows shell, explicit target list and built-in networking support.

4. Discover and verify prerequisites

Get-NetIPConfiguration
Get-NetRoute -AddressFamily IPv4
Test-NetConnection TARGET -Port PORT

5. Why it works

A local TcpClient or Test-NetConnection uses the host's route and firewall context. Results from Kali do not substitute for reachability from this source.

6. Execute and choose variants

Purpose: Test TCP reachability from a Windows host when source position or available tooling matters.

Test one TCP port from the Windows source host:

Test-NetConnection -ComputerName TARGET -Port PORTS

Read: TcpTestSucceeded, source and destination addresses. Use one number for PORTS. Failure does not distinguish a closed port, filtering or a path problem.

Variants — scan ports 1-1024 or a selected port list
Scan a low-port range
1..1024 | % {echo ((New-Object Net.Sockets.TcpClient).Connect("DC_IP", $_)) "TCP port $_ is open"} 2>$null
Check a selected port list

The example list can be changed to the endpoints of interest.

22,80,443,445,3389 | % {echo ((New-Object Net.Sockets.TcpClient).Connect("TARGET", $_)) "TCP port $_ is open"} 2>$null

$_ is the current port; errors are hidden. No printed result does not prove every port is closed. Results reflect the Windows host's access and the stated port selection.

7. Worked example — hypothetical

Observation: Kali cannot reach an internal WinRM endpoint. Test: check TCP/5985 from the Windows foothold. Illustrative output: TcpTestSucceeded is True. Interpretation: a new route/source exists; choose a forward or run an authorized native client there.

8. Verify the result

Associate each result with the actual Windows source and selected port; do not claim UDP or full-port coverage.

9. Failure and fallback

A false result may be routing, filtering or service absence; use route and listener evidence before deciding the service is down.

10. Next transitions

Discover pivot interfaces, routes and internal service context; Use WinRM, WinRS or PowerShell remoting; Validate uncertain results and rebuild the service queue.

Discover TCP ports with SYN or connect scans

Blocks: 1; revisit after new routes or hosts. Operational procedure | Quick sheet

1. Purpose and result

A saved TCP port-state inventory with explicit coverage.

2. Recognition clues

An assigned host needs an initial service queue or full TCP coverage.

Find the clue from your starting access

Where to investigate: After path validation, compare a first TCP pass with explicit full-port coverage; record skipped discovery or privilege limitations.

Discovery action — reference example:

nmap -Pn -sT --top-ports 1000 TARGET -oA tcp-initial
nmap -Pn -sT -p- TARGET -oA tcp-full

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Initial selection: 22/tcp open ssh; 80/tcp open http
Full selection also: 18080/tcp open unknown

Recognize this detail: The high listener exists outside the first selection; its application label remains provisional.

Still missing before method selection: Confirm scan completion, source, errors and application behavior on each interesting port.

Outcome after checkingExample and next decision
Enabled after validationA focused connection and application response confirm the listener: queue its service.
Ruled out in this contextThe earlier result cannot be reproduced after a completed focused check: retire that stale listener hypothesis.
InconclusiveFiltered ports or interrupted scans leave coverage/reachability unresolved; save the limit and choose a focused check.

If you do not yet have this clue: start with Validate the source path and discover hosts.

3. Prerequisites

Starting access: An explicitly assigned address or host list and a known source position. Required conditions: SYN scanning needs raw-packet privileges; connect scanning needs OS TCP connections; specify selected versus full port coverage.

4. Discover and verify prerequisites

nmap -Pn -sT --top-ports 1000 TARGET -oA tcp-initial
nmap -Pn -sT -p- TARGET -oA tcp-full

5. Why it works

SYN and connect scans infer reachability differently but both cover only their selected ports. A common-port scan is a prioritization pass, not full TCP coverage.

6. Execute and choose variants

Purpose: Get quick leads, complete TCP coverage, and adapt scan type, discovery handling, timing and output to the access path.

2. Get initial TCP results
sudo nmap -sS -n -oA scans/tcp-initial TARGET

Coverage: 1,000 common TCP ports. Review scans/tcp-initial.nmap in a text editor.

Variants — host list, connect scan or selected ports
Initial view: 1,000 common ports

Assigned host list, SYN scan:

sudo nmap -sS -n -iL targets.txt -oA scans/tcp-initial-list

One host, connect scan without raw-packet privileges:

nmap -sT -n -oA scans/tcp-connect TARGET

Default coverage is the common-port selection, not ports 1-1000.

Selected ports or a range

One host: replace PORTS with, for example, 25,43 or 1-1024.

sudo nmap -sS -n -p PORTS -oA scans/tcp-selected TARGET

Find relevant services across assigned hosts:

sudo nmap -sS -n -p PORTS -iL targets.txt -oA scans/tcp-service-sweep

A focused service sweep is not a full port map.

3. Complete TCP coverage
sudo nmap -sS -n -p- -oA scans/tcp-all TARGET

Coverage: TCP 1-65535. Investigate useful initial results while this runs.

Variants — connect scan, blocked discovery, timing and progress
All TCP ports: 1-65535

Connect scan:

nmap -sT -n -p- -oA scans/tcp-all-connect TARGET

Inspect additional endpoints before narrowing the investigation. TCP coverage says nothing about UDP.

Discovery skips a running target

Recheck relevant ports with response reasons:

sudo nmap -sS -n -Pn --reason -p PORTS -oA scans/tcp-recheck TARGET

Proceed with full TCP coverage despite failed discovery:

sudo nmap -sS -n -Pn -p- -oA scans/tcp-all-no-discovery TARGET

-Pn assumes online status; inspect actual responses. It does not fix routing. Use -sT without sudo if ordinary TCP connections are needed.

Timing and progress

Full TCP with normal timing and periodic progress:

sudo nmap -sS -n -p- -T3 --stats-every 30s -oA scans/tcp-normal TARGET

Faster timing on a stable path:

sudo nmap -sS -n -p- -T4 --stats-every 30s -oA scans/tcp-faster TARGET

-T3 is normal timing; -T4 is more aggressive. Periodic progress changes display, not coverage. Recheck decisive results if loss or filtering makes observations uncertain.

TCP-only access through a SOCKS proxy

Use ordinary connect calls when a previously established proxy is the only route. This is a bounded first view, not complete TCP coverage:

proxychains nmap -sT -Pn -n --top-ports 100 -oA scans/tcp-proxy-top100 TARGET

proxychains cannot turn SYN probes or UDP into proxied TCP connections. -Pn avoids discovery probes that may not traverse the proxy. Confirm the proxy route first, preserve the 100-port limit, and expand with another connect scan only when scope and path permit it.

7. Worked example — hypothetical

Observation: the initial scan exposes SSH and HTTP. Test: finish full TCP selection. Illustrative output: an additional management service appears on a high port. Interpretation: add it to the queue before committing to a web-only path.

8. Verify the result

Retain the selected port set, source context, completion/errors and raw output; follow open ports with focused application evidence.

9. Failure and fallback

Filtered is not closed. Through SOCKS use supported TCP-connect behavior and skip unsupported raw discovery/UDP; if results conflict, compare from the actual source.

10. Next transitions

Identify applications and validate selected NSE checks; Enumerate SMB/RPC shares, files and identities; Establish scheme, host, redirects and request state.

Probe UDP and resolve ambiguous silence

Blocks: 1; revisit after new routes or hosts. Operational procedure | Quick sheet

1. Purpose and result

UDP responders and documented open/filtered uncertainty.

2. Recognition clues

TCP enumeration is incomplete for the objective or DNS/SNMP/RPC clues suggest UDP.

Find the clue from your starting access

Where to investigate: Inspect discovery results and DNS/SNMP/RPC clues, then probe a separate bounded UDP selection from the same source.

Discovery action — reference example:

sudo nmap -Pn -sU --top-ports 20 --reason TARGET -oA udp-initial

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

161/udp open|filtered snmp no-response
53/udp open domain udp-response

Recognize this detail: A DNS response confirms a UDP application; open|filtered SNMP silence is a candidate requiring a correctly formatted request.

Still missing before method selection: Check accepted service parameters, response identity and possible ICMP rate limiting.

Outcome after checkingExample and next decision
Enabled after validationA service-native request returns the expected OID/record: enumerate that application.
Ruled out in this contextAn explicit port-unreachable response rules out that UDP endpoint for this source/time.
InconclusiveSilence can mean open or filtered; use a justified application-aware probe rather than declaring either.

If you do not yet have this clue: start with Validate the source path and discover hosts.

3. Prerequisites

Starting access: An explicitly assigned address or host list and a known source position. Required conditions: Raw-packet access and UDP reachability from the real source; bounded or full selection must be explicit.

4. Discover and verify prerequisites

sudo nmap -Pn -sU --top-ports 20 --reason TARGET -oA udp-initial
sudo nmap -Pn -sU -sV -p 53,161 TARGET -oA udp-focused

5. Why it works

A UDP service may ignore an empty probe; ICMP errors and application responses distinguish states. Silence alone cannot distinguish open from filtered.

6. Execute and choose variants

Purpose: Sample UDP separately, preserve ambiguous states, and expand only when the objective or evidence warrants it.

5. Check UDP separately
sudo nmap -sU -n --top-ports 20 -oA scans/udp-top20 TARGET

Limit: this is a sample. open|filtered remains inconclusive; expand when evidence or the objective warrants it.

Variants — larger sample, selected ports, application probes and TCP + UDP
Common-port samples

Expand to 100 common ports when more coverage is warranted:

sudo nmap -sU -n --top-ports 100 -oA scans/udp-top100 TARGET

These are samples. open|filtered is inconclusive; TCP results cannot fill UDP gaps.

Selected ports

Check a relevant UDP port/list:

sudo nmap -sU -n -p PORTS -oA scans/udp-selected TARGET

Add application probes to resolve a useful candidate:

sudo nmap -sU -n -sV -p PORTS -oA scans/udp-detail TARGET

A reply can resolve ambiguity; no reply can leave it inconclusive. If discovery skips an assigned running host, add -Pn with the same limitations as TCP.

Full UDP coverage when the objective justifies the cost
sudo nmap -sU -n -p- --stats-every 60s -oA scans/udp-all TARGET

This selects UDP ports 1-65535 and may take a long time because silence requires waiting and ICMP errors may be rate-limited. It is the coverage-expansion option, not a universal first command. Continue service work in parallel and preserve the result if the scan cannot finish.

Combined TCP/UDP selection

Example selection: change the TCP (T:) and UDP (U:) lists for the actual question.

sudo nmap -sS -sU -n -p T:22,80,445,U:53,123,161 -oA scans/tcp-udp TARGET

The port lists are examples, not complete coverage. UDP waiting can extend the combined scan.

Use an application response for a confirmed service; document unresolved silence, coverage and ICMP rate-limit effects.

9. Failure and fallback

Do not translate UDP silence into a closed service. Retry a focused application-aware probe or a different permitted vantage point.

Light mode tries fewer uncommon probes and can miss an identity that the default intensity finds. Use the default first unless a concrete constraint justifies the tradeoff.

5. Why it works

6. Execute and choose variants

Use when: Nmap remains the interpretation baseline, but a faster TCP discovery pass or a bounded web-server check is useful. These tools generate candidates; Nmap/manual protocol checks confirm them.

RustScan: fast TCP discovery, Nmap interpretation

Prerequisite: RustScan and Nmap on Kali; direct TCP reachability. Coverage: only the explicit TCP range. Decisive output: a discovered port that Nmap can reproduce and identify.

rustscan -a TARGET -r 1-65535 --ulimit 5000 -- \
  -Pn -sV -sC -oA rustscan-followup

If the target or network becomes unstable, lower concurrency rather than trusting an empty result. RustScan does not replace UDP work and does not prove that closed/filtered ports were tested with the same semantics as Nmap.

Bounded first 1,000 TCP ports 
rustscan -a TARGET -r 1-1000 --ulimit 5000 -- \
  -Pn -sV -sC -oA rustscan-1000

Use only for a quick selection. It is not full TCP coverage and is not equivalent to Nmap's default top-1,000 selection.

Masscan: raw-packet discovery, then validation

Prerequisite: root/raw-packet access and a directly routed target. Choose it: for a large authorized address/port space where discovery speed matters. Failure cue: high loss or inconsistent results at the chosen rate.

sudo masscan TARGET -p1-65535 --rate 500 -oL masscan-open.txt

Treat each hit as a candidate and recheck with Nmap:

PORTS=$(awk '$1 == "open" && $2 == "tcp" {print $3}' masscan-open.txt \
  | sort -nu | paste -sd,)
test -n "$PORTS" && sudo nmap -Pn -sV -sC -p "$PORTS" TARGET -oA masscan-verified

Masscan's raw-packet model is not suitable through a TCP SOCKS proxy. A rate that overwhelms the path can create false negatives and disrupt the lab; record the rate with the result.

NSE candidate checks

Inspect a script before selecting it:

nmap --script-help SCRIPT_NAME
grep -i 'SCRIPT_NAME' /usr/share/nmap/scripts/script.db

Run a named script against a confirmed service/port:

nmap -Pn -sV --script SCRIPT_NAME -p PORT TARGET -oN nse-SCRIPT_NAME.txt

Nikto: bounded web-server candidate generation

Prerequisite: an identified HTTP(S) endpoint. Choose it: after manual baselining to identify common files, headers and server misconfiguration candidates. Decisive output: a finding manually reproduced with the same host, path and authentication context.

5. Why it works

A TCP connection proves transport reachability, not successful protocol authentication or useful rights. Re-enumeration is required when identity or route changes.

6. Execute and choose variants

Purpose: Resolve uncertainty that affects a decision, preserve coverage limits, and turn scan output into a service-enumeration queue.

6. Resolve a result that changes your next action

Keep source, destination, transport and port consistent when comparing results. Revisit relevant checks after a new route, foothold or identity changes access.

Variants — Netcat verification, response reasons and readable output
Netcat connection check

One TCP port: replace PORTS with one number.

nc -nv -w 3 -z TARGET PORTS

Short port range: replace PORTS with a range such as 3388-3390.

nc -nvv -w 3 -z TARGET PORTS

Success establishes TCP connection acceptance; refusal and timeout differ. The second form gives more verbose output. A three-second wait may be insufficient on a slow path.

Output and diagnostics

Readable text only, with verbose output and port-state reasons:

sudo nmap -sS -n -v --reason -p PORTS -oN scans/tcp-check.txt TARGET

Open saved .nmap or .txt output in a text editor. -oA writes .nmap, .gnmap and .xml; -oN writes only normal text. Use a different output prefix when retaining another run.

7. Build the service queue

Open the saved .nmap files in a text editor. For every useful endpoint, capture one line with this structure:

SOURCE -> TARGET | tcp/udp PORT | OBSERVED STATE | APPLICATION EVIDENCE | COVERAGE LIMIT | NEXT TEST

Next: carry the complete endpoint tuple into Stage 02 service enumeration and choose the cheapest protocol-aware test that can change your understanding or access. Keep an explicit return item for incomplete TCP, UDP or application coverage.

Interpretation cues — preserve what the scan actually established
  • open establishes a reachable endpoint from the scan source; it does not establish a vulnerability or usable authentication.
  • closed records an explicit rejection in that context. Move on unless later evidence changes the route, source or target state.
  • filtered leaves the listener state unresolved because filtering, loss or the path prevented classification.
  • unfiltered means the selected probe reached the port but could not determine whether it was open or closed; use a scan type that can answer the required question.
  • UDP open|filtered is inconclusive. A useful protocol probe may reduce uncertainty, but another silence can remain inconclusive.
  • closed|filtered is also an explicit ambiguity. Preserve it unless resolving the distinction changes the next action.
  • A port-based service label is a clue. Use application evidence before treating product, version, operating system or machine role as confirmed.
  • Record the exact target, transport, selected ports and source position. A successful narrow scan does not cover untested ports, the other transport or another network position.
8. Prioritize and know when to rescan

Rank candidates by the cheapest test likely to produce access, credentials, sensitive information or a decisive prerequisite. Prefer observed application behavior over conventional port numbers. Keep at least one return item for incomplete coverage so an attractive early service does not erase the rest of the map.

Re-run network discovery after a new source host, route, tunnel or target restart. Re-enumerate a service after a new credential or identity. Inspect local listeners after a foothold. Recheck a previous result when the source, target state, port selection or network conditions changed—not simply because the first attack failed.

Observation: one scan calls a port filtered while Netcat connects. Test: repeat the focused scan and speak the application protocol. Illustrative output: a service banner returns. Interpretation: keep the application evidence and investigate timing/source differences.

8. Verify the result

Record which layer was demonstrated: transport, application, authentication, read/write or execution.

9. Failure and fallback

Connection success with no useful response needs a protocol-aware test; repeated identical failures without new evidence do not justify repeating the same path.
