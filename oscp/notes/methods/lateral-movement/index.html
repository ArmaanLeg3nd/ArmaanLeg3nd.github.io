    Strategy map | Master Notes | Operational index | Cheatsheets

    Select credential type → accepted authentication → reachable service → service authorization → execution effect. Hash/ticket use is an authentication dimension; SMB, tasks, WMI, WinRM and RDP are different access mechanisms.

    Speedrun blocks: 12; consumes routes from 13. Documented methods: 9.

    Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

    6.4.4.1 First pass: tools and findings

    Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

    6.4.4.1.1 Test the destination from the real source

    A working password on one service does not establish execution permission on another host.

    nmap -Pn -sT -p 135,445,3389,5985,5986 TARGET
getent hosts TARGET_HOST
    • If WinRM is reachable and the account has endpoint rights: Use the WinRM procedure and verify the resulting token. → Use WinRM, WinRS or PowerShell remoting.
    • If SMB/RPC is reachable and service-control rights are confirmed: Use the service-execution procedure with a separate output path. → Execute through uploaded service creation using PsExec.
    • Otherwise: Only the listener is reachable: inspect actual endpoint authorization before selecting an execution tool. → Select password, NT hash, key-to-ticket or ticket authentication.

    6.4.4.1.2 Match password, hash, key or ticket to the client

    Use the existing Impacket/NetExec protocol-specific examples; do not treat successful authentication as remote execution.

    klist
getent hosts TARGET_HOST
date -u
    • If Accepted authentication plus remote service rights: Check share/SCM permissions and output reachability. → Execute through uploaded service creation using PsExec.
    • If WMI/task rights with RPC/DCOM connectivity: Check the exact namespace/task authorization and output channel. → Execute through WMI or native CIM over DCOM.
    • Otherwise: The artifact is rejected: recheck identity scope, material format, service name and transport. → Classify the artifact and its identity context.

    6.4.4.2 Discovery workflow

    Start with material tied to a known identity and a destination candidate; neither valid authentication nor remote execution rights are assumed.

    Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

    1. Check the destination from the actual source, including dynamic RPC and names: Match route, destination service and effective authorization.
    2. Classify password, NT hash, long-term key or service-scoped ticket: Select password, NT hash, key-to-ticket or ticket authentication.
    3. Match effective service/task/WMI authorization to its separate output path: Execute through uploaded service creation using PsExec; Execute commands through service command lines and SMB output; Execute through remote Task Scheduler; Execute through WMI or native CIM over DCOM.
    4. Check endpoint or remote-interactive rights for WinRM/RDP and verify the resulting token: Use WinRM, WinRS or PowerShell remoting; Obtain an authorized RDP interactive session.

    PowerView examples require a reviewed compatible script in the current authenticated directory context. Check the loaded copy rather than mixing legacy/fork parameter names; the directory-mapping entry includes native, ADSI and LDAP alternatives.

    Import-Module .\PowerView.ps1
Get-Command -Module PowerView

    Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

    6.4.4.3 Method families

    • Route, authorization and authentication material: Match route, destination service and effective authorization, Select password, NT hash, key-to-ticket or ticket authentication.
    • Service and scheduled-task execution: Execute through uploaded service creation using PsExec, Execute commands through service command lines and SMB output, Execute through remote Task Scheduler.
    • Management protocol execution: Execute through WMI or native CIM over DCOM, Execute through an authorized DCOM application object, Use WinRM, WinRS or PowerShell remoting.
    • Interactive access: Obtain an authorized RDP interactive session.

    6.4.4.13.6 Execute and choose variants

    Check the installed binary name:

    command -v xfreerdp3 || command -v xfreerdp

    Password:

    xfreerdp3 /v:TARGET_HOST /d:DOMAIN /u:USER /p:'PASSWORD' /cert:ignore /dynamic-resolution +clipboard

    Older packages may expose the same syntax through xfreerdp.

    NT hash:

    xfreerdp3 /v:TARGET_HOST /d:DOMAIN /u:USER /pth:NT_HASH /cert:ignore /dynamic-resolution

    FreeRDP's /pth uses Restricted Admin mode. The target must support/permit that mode and the identity must be an administrator; ordinary Remote Desktop Users membership is not sufficient for Restricted Admin. Password-based RDP instead needs the Remote Desktop service, NLA compatibility and the effective “Allow log on through Remote Desktop Services” right without a deny override.

    Native client:

    mstsc.exe /v:TARGET_HOST
mstsc.exe /restrictedAdmin /v:TARGET_HOST

    Ordinary RDP can place reusable user credentials in the destination's LSASS. Restricted Admin avoids sending those reusable credentials but prevents ordinary onward access as that user; treat the resulting session's network identity separately.

    Purpose: use a validated identity with Remote Desktop logon rights to establish a Windows desktop and verify the resulting source position.

    6.4.4.13.6.1.1 Baseline: prompt for the password

    xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /dynamic-resolution /cert:ignore

    Local and domain accounts with the same username are different identities. Make the intended context explicit when results differ.

    6.4.4.13.6.1.1.2 Variant — authentication only 
    xfreerdp3 /v:TARGET /u:USER /d:DOMAIN /auth-only /cert:ignore

    6.4.4.13.6.1.1.3 Variant — explicit password 
    xfreerdp3 /v:TARGET /u:USER '/p:PASSWORD' /dynamic-resolution /cert:ignore

    Failure cues: a certificate warning is not a credential result.
