Map Active Directory attack paths

Strategy map | Master Notes | Operational index | Cheatsheets

Build identity, object-right, host-access and session maps. A graph relationship is a candidate until its effective permission, destination and current state are checked.

Speedrun blocks: 10; Block 13 route fundamentals first. Documented methods: 7.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Resolve domain, DC, DNS and clock first

Use the current domain identity or the supported query context; wrong naming/transport can look like a bad password.

whoami /all
whoami /upn
nltest /dsgetdc:DOMAIN
w32tm /query /status
  • If Domain/DC preflight works: Enumerate users/groups/SPNs and collect supported directory relationships. → Enumerate directory objects with native, LDAP and PowerView approaches.
  • Otherwise: KDC timeout, name failure or skew: repair that dependency before judging credentials. → Establish domain identity, DC, DNS, time and route.

Collect a BloodHound directory baseline with SharpHound

Use a collector compatible with the BloodHound version. DCOnly is a directory baseline, not proof of all host/session edges.

.\SharpHound.exe --CollectionMethods DCOnly --OutputDirectory .\bh --ZipFileName domain-dconly.zip
  • If A useful object-control edge: Resolve the controlled trustee, target object and effective ACE. → Validate effective directory-object control.
  • If A host/session edge: Check destination rights and session freshness independently. → Validate host access and volatile session candidates.
  • If An account with an SPN: Check the actual account/SPN and ticket-request conditions. → Identify service accounts and SPNs worth investigating.
  • Otherwise: Collection is blocked or incomplete: query the relevant objects manually. → Enumerate directory objects with native, LDAP and PowerView approaches.

Discovery workflow

Start with a known domain identity or a directory query context; useful group, object-right and session edges are not assumed.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Resolve identity, realm, DC, DNS, clock and route first: Establish domain identity, DC, DNS, time and route.
  2. Enumerate objects, group nesting and relevant shares with a supported client: Enumerate directory objects with native, LDAP and PowerView approaches; Read domain shares, SYSVOL and NETLOGON for useful artifacts.
  3. Associate SPNs and effective ACEs with actual accounts and object types: Identify service accounts and SPNs worth investigating; Validate effective directory-object control.
  4. Check host-specific rights and session freshness, then validate graph paths edge by edge: Validate host access and volatile session candidates; Collect focused BloodHound data and validate an attack path.

PowerView examples require a reviewed compatible script in the current authenticated directory context. Check the loaded copy rather than mixing legacy/fork parameter names; the directory-mapping entry includes native, ADSI and LDAP alternatives.

Import-Module .\PowerView.ps1
Get-Command -Module PowerView

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Domain context and directory objects: Establish domain identity, DC, DNS, time and route, Enumerate directory objects with native, LDAP and PowerView approaches.
  • Artifacts and service identities: Read domain shares, SYSVOL and NETLOGON for useful artifacts, Identify service accounts and SPNs worth investigating.
  • Effective rights, host access and path ranking: Validate effective directory-object control, Validate host access and volatile session candidates, Collect focused BloodHound data and validate an attack path.

Establish domain identity, DC, DNS, time and route

Blocks: 10; Block 13 route fundamentals first. Operational procedure | Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A verified domain context and working directory/authentication preflight.

2. Recognition clues

Domain credentials or a domain-joined foothold.

Find the clue from your starting access

Where to investigate: Start with the session identity and known credential scope; discover the realm/DC and inspect DNS, time and routes.

Discovery action — reference example:

whoami /all
whoami /upn
nltest /dsgetdc:DOMAIN
w32tm /query /status

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

UPN: USER@DOMAIN
DC: \\DC_HOST
Domain name: DOMAIN
Clock source/status: inspect

Recognize this detail: The named realm/DC and actual identity establish where directory/authentication checks must run.

Still missing before method selection: Check DC/service reachability, resolver/SPN naming and clock compatibility, not merely the password.

Outcome after checkingExample and next decision
Enabled after validationA normal bind/ticket request works in the intended realm: continue domain mapping.
Ruled out in this contextThe credential belongs only to the target-local account: reject the assumed domain identity.
InconclusiveDC lookup/time failure leaves domain authentication untested.

If you do not yet have this clue: start with Validate known passwords and context-specific reuse.

3. Prerequisites

Starting access: A known domain identity or a directory endpoint that permits the selected anonymous query. Required conditions: Correct realm/domain and account qualification; reachable DC/services, usable DNS and acceptable clock skew.

4. Discover and verify prerequisites

whoami /all
whoami /upn
nltest /dsgetdc:DOMAIN
w32tm /query /status

5. Why it works

Local process identity, network credential context and domain naming are separate. Kerberos depends on service names, time and KDC connectivity in addition to a valid password.

6. Execute and choose variants

Domain-joined Windows source
whoami /all
echo %USERDNSDOMAIN%
echo %USERDOMAIN%
echo %LOGONSERVER%
nltest /dsgetdc:DOMAIN
nltest /dclist:DOMAIN
w32tm /query /status

[System.DirectoryServices.ActiveDirectory.Domain]::GetCurrentDomain()
Resolve-DnsName -Type SRV _ldap._tcp.dc._msdcs.DOMAIN
Resolve-DnsName -Type SRV _kerberos._tcp.DOMAIN

Decisive output: domain FQDN, DC FQDN/IP, current user SID/groups, DNS SRV answers and a plausible time source. USERDOMAIN can be a NetBIOS label; prefer the DNS domain for LDAP/Kerberos.

Kali/off-domain source
dig +short SRV _ldap._tcp.dc._msdcs.DOMAIN @DC_IP
dig +short SRV _kerberos._tcp.DOMAIN @DC_IP
nxc smb DC_IP -d DOMAIN -u USER -p 'PASSWORD'
ldapsearch -x -LLL -H ldap://DC_HOST:389 -s base -b '' \
  defaultNamingContext configurationNamingContext rootDomainNamingContext dnsHostName

RootDSE is a directory-server metadata object. Reading it can reveal naming contexts even when anonymous subtree searches are denied. Convert corp.example to DC=corp,DC=example; do not guess the base DN when RootDSE can supply it.

Remote Windows session and double-hop caveat 
whoami /all
klist
dir \\DC_HOST\SYSVOL

A supplied credential may create the remote session without being delegated onward to the DC. If local identity commands work but access to a second host fails, distinguish a WinRM/PowerShell remoting credential-delegation problem from invalid credentials. An interactive RDP session, explicit credentials, /netonly network credentials or an off-domain LDAP client may create a different context; always record which identity is used locally and over the network.

IDENTITY MAP: USER/COMPUTER -> DIRECT + NESTED GROUPS -> DIRECTORY RIGHTS
HOST MAP:     COMPUTER -> OS/ROLE -> LOCAL/REMOTE-ACCESS RIGHTS -> SESSIONS
ROUTE MAP:    SOURCE -> DNS/KDC/DC/HOST -> REQUIRED PORT/SERVICE
LEAD MAP:     EVIDENCE -> HYPOTHESIS -> MINIMUM VALIDATION -> NEXT BLOCK

Authentication, authorization, reachability and session presence are independent. A valid LDAP bind does not prove share access; SMB administration on one host does not prove directory privilege; a session edge does not prove retrievable credentials.

AS-REQ/AS-REP: user proves knowledge of long-term key -> receives TGT
TGS-REQ/TGS-REP: TGT requests SERVICE/HOST -> receives service ticket
AP-REQ: client presents service ticket -> service authenticates client
AUTHORIZATION: target service still evaluates the represented identity/claims

Before changing credentials or tools:

getent hosts DC_HOST
nc -nvz DC_IP 88
date -u

w32tm /query /status
klist

Record domain FQDN/realm, DC FQDN/IP, source DNS, current time, KDC route and exact target SPN. IP connectivity does not replace hostname/SPN correctness.

7. Worked example — hypothetical

Observation: a valid domain password fails in a ticket-based client. Test: inspect DC naming, DNS, route and time. Illustrative output: the KDC is unreachable through the current route. Interpretation: fix transport before judging the credential.

8. Verify the result

Record represented identity, realm, selected DC, resolver, clock and real source route.

9. Failure and fallback

Wrong domain, KDC timeout, clock skew and account denial are distinct failures. Do not repeatedly change passwords to fix a route problem.

Enumerate directory objects with native, LDAP and PowerView approaches

Blocks: 10; Block 13 route fundamentals first. Operational procedure | Operational procedure | Operational procedure | Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

User, group, computer, trust and policy relationships for attack-path hypotheses.

2. Recognition clues

A directory bind or domain-joined identity can read relevant objects.

Find the clue from your starting access

Where to investigate: Use the available built-in/LDAP interface from the verified domain context; inspect one useful user/group before broad graph assumptions.

Discovery action — reference example:

net user USER /domain
net group "GROUP" /domain

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Account: USER
Global group memberships: GROUP
Group members: CONTROLLED_USER

Recognize this detail: Account/group membership supplies a relationship to investigate; nested membership and effective destination rights remain separate.

Still missing before method selection: Verify object SID/type, nesting and the exact right granted to that principal.

Outcome after checkingExample and next decision
Enabled after validationThe membership resolves to a currently effective object/service right: follow that route.
Ruled out in this contextThe same-named group belongs to another domain or grants no intended right: reject the assumed relationship.
InconclusivePartial visibility or nesting not yet expanded leaves effective membership unresolved.

If you do not yet have this clue: start with Establish domain identity, DC, DNS, time and route.

3. Prerequisites

Starting access: A known domain identity or a directory endpoint that permits the selected anonymous query. Required conditions: Correct search base and authentication transport; object/attribute visibility and compatible local utilities.

4. Discover and verify prerequisites

net user /domain
net group /domain

5. Why it works

Tools expose the same directory through different interfaces. Group nesting, object types, primary groups and protected attributes affect how relationships translate into effective rights.

6. Execute and choose variants

net user /domain
net user USER /domain
net group /domain
net group "Domain Admins" /domain
net group "GROUP" /domain
net accounts /domain
nltest /domain_trusts /all_trusts

These commands are broadly available but provide partial views. Expand interesting users and groups individually, trace nested groups rather than assuming memberOf is complete, and retain SIDs when names can collide across domains.

Get-AD* cmdlets require the RSAT ActiveDirectory module. Its absence on a client is normal; use ADSI, LDAP, PowerView or an off-domain client.

$root = [ADSI]'LDAP://RootDSE'
$base = [ADSI]("LDAP://" + $root.defaultNamingContext)
$searcher = New-Object System.DirectoryServices.DirectorySearcher($base)
$searcher.PageSize = 1000
$searcher.PropertiesToLoad.AddRange(@('samaccountname','userprincipalname','objectsid','memberof','serviceprincipalname','description','useraccountcontrol','pwdlastset','lastlogontimestamp'))
$searcher.Filter = '(&(objectCategory=person)(objectClass=user))'
$searcher.FindAll() | ForEach-Object { $_.Properties }

Change only the filter and requested attributes for another object class:

# Groups
$searcher.Filter = '(objectCategory=group)'
$searcher.PropertiesToLoad.Clear()
$searcher.PropertiesToLoad.AddRange(@('samaccountname','objectsid','member','grouptype','description'))
$searcher.FindAll() | ForEach-Object { $_.Properties }

# Computers
$searcher.Filter = '(objectCategory=computer)'
$searcher.PropertiesToLoad.Clear()
$searcher.PropertiesToLoad.AddRange(@('dnshostname','operatingsystem','operatingsystemversion','serviceprincipalname','useraccountcontrol','lastlogontimestamp'))
$searcher.FindAll() | ForEach-Object { $_.Properties }

PageSize = 1000 asks for paged results; without paging, the server's result-size limit can silently produce an incomplete inventory. LDAP filters are data selection, not proof of access or exploitability.

Discover the naming context
ldapsearch -x -LLL -H ldap://DC_HOST:389 -s base -b '' \

ldapsearch -x -LLL -H ldap://DC_HOST:389 -D 'USER@DOMAIN' -W \
  -E pr=1000/noprompt -b 'DC=DOMAIN,DC=TLD' \
  '(objectCategory=group)' sAMAccountName objectSid member groupType description

ldapsearch -x -LLL -H ldap://DC_HOST:389 -D 'USER@DOMAIN' -W \
  -E pr=1000/noprompt -b 'DC=DOMAIN,DC=TLD' \

SPNs, trusts and GPO/OU context 
# SPN-bearing accounts: mapping only; do not request tickets in this block.
ldapsearch -x -LLL -H ldap://DC_HOST:389 -D 'USER@DOMAIN' -W \
  -E pr=1000/noprompt -b 'DC=DOMAIN,DC=TLD' \
  '(&(objectCategory=person)(objectClass=user)(servicePrincipalName=*))' \
  sAMAccountName servicePrincipalName memberOf userAccountControl pwdLastSet

# Trusted-domain objects
ldapsearch -x -LLL -H ldap://DC_HOST:389 -D 'USER@DOMAIN' -W \
  -b 'DC=DOMAIN,DC=TLD' '(objectClass=trustedDomain)' \
  cn securityIdentifier trustDirection trustType trustAttributes

# OUs and GPO containers; correlate links before inferring host effect.
ldapsearch -x -LLL -H ldap://DC_HOST:389 -D 'USER@DOMAIN' -W \
  -E pr=1000/noprompt -b 'DC=DOMAIN,DC=TLD' \
  '(|(objectClass=organizationalUnit)(objectClass=groupPolicyContainer))' \
  distinguishedName displayName name gPLink gPOptions

Still missing before method selection: Resolve the ACE's trustee and group nesting, target object class, GUID and inheritance/deny scope. For password reset, group writes or DACL changes open that exact operation's procedure and check its additional conditions before modifying anything.

Outcome after checkingExample and next decision

3. Prerequisites

Starting access: A known domain identity or a directory endpoint that permits the selected anonymous query. Required conditions: Effective trustee membership, target object/type, inheritance/deny behavior and the exact permitted operation.

4. Discover and verify prerequisites

Get-DomainObjectAcl -Identity TARGET_OBJECT -ResolveGUIDs

5. Why it works

Object rights are operation-specific. GenericWrite on a user is not a universal password-reset right; inherited ACEs and protected objects can change applicability.

6. Execute and choose variants

Get-DomainObjectAcl -Identity TARGET_OBJECT -ResolveGUIDs |
  Where-Object { $_.ActiveDirectoryRights -match 'GenericAll|GenericWrite|WriteDacl|WriteOwner|ExtendedRight|WriteProperty|Self' } |
  Select-Object ObjectDN,IdentityReference,ActiveDirectoryRights,ObjectAceType,AceType,IsInherited,InheritanceType

4. Discover and verify prerequisites

whoami /groups
net localgroup Administrators

5. Why it works

Local admin, RDP, WinRM and share-read relationships grant different capabilities. A historical session does not guarantee current credential material or the right to read it.

6. Execute and choose variants

Find-LocalAdminAccess

nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD'
nxc smb TARGET -d DOMAIN -u USER -p 'PASSWORD' --shares

Find-LocalAdminAccess is a broad candidate generator and can be noisy or blocked by firewall/RPC controls. Validate a selected host with the service you may actually use. NetExec's (Pwn3d!) indicates administrative SMB context according to that tool; it does not establish RDP, WinRM, WMI/DCOM or directory rights. RDP, WinRM, SMB/service control and WMI/DCOM each have different ports, services, policies and authorization.

Get-NetSession -ComputerName COMPUTER -Verbose
Get-NetLoggedon -ComputerName COMPUTER

PsLoggedOn.exe \\COMPUTER

Get-NetSession relies on workstation/session enumeration APIs that modern Windows may restrict. PsLoggedOn combines Registry profile evidence with NetSessionEnum; remote Registry access and sufficient rights are relevant, and querying can itself create a network-session entry. Therefore:

  • empty/denied is inconclusive, not proof of no users;
  • a session is a time-sensitive observation, not a durable ACL;
  • a session matters only if the current identity can reach/control that host and a later credential/ticket technique applies;
  • session presence does not prove credentials are resident, accessible or reusable.

7. Worked example — hypothetical

Observation: a graph marks a user as able to RDP to a host. Test: validate the reachable RDP service and effective logon right. Illustrative output: RDP works but remote service creation is denied. Interpretation: retain the actual access form and inspect that host's new opportunities.

8. Verify the result

Record the destination-specific successful action and freshness/limits of session evidence.

9. Failure and fallback

Collection denial is not proof that no sessions exist; a valid credential is not proof of every host-access method.

10. Next transitions

Obtain an authorized RDP interactive session; Use WinRM, WinRS or PowerShell remoting; Obtain accessible live logon-session credential material.

4. Discover and verify prerequisites

SharpHound.exe --help

5. Why it works

BloodHound models collected relationships, which may be stale or incomplete. Directory-only collection and host/session collection answer different questions and have different contact/rights requirements.

6. Execute and choose variants

Current SharpHound CE

Low-noise directory baseline that avoids contacting every workstation:

.\SharpHound.exe --CollectionMethods DCOnly --OutputDirectory .\bh --ZipFileName domain-dconly.zip

Add host facts only when they can answer the next question:

.\SharpHound.exe --CollectionMethods LocalGroup --ComputerFile .\candidate-hosts.txt --OutputDirectory .\bh --ZipFileName candidate-localgroups.zip
.\SharpHound.exe --CollectionMethods Session --ComputerFile .\candidate-hosts.txt --Loop --LoopDuration 00:10:00 --OutputDirectory .\bh --ZipFileName candidate-sessions.zip

SharpHound with no collection flag uses its broader default, including directory data plus local-group/session attempts. All performs every supported method; it is not the first response to an unanswered narrow question. Import the output ZIP into a compatible BloodHound CE deployment and verify node/edge counts and ingestion errors.

Collector variants and compatibility 
# Inspect the actual collector before using copied syntax.
.\SharpHound.exe --help

# Community Linux collector; flags and output compatibility vary by release.
bloodhound-python --help
bloodhound-python -u USER -p 'PASSWORD' -d DOMAIN -ns DC_IP -dc DC_HOST -c All --zip

Use the collector version intended for the BloodHound deployment. bloodhound-python, legacy SharpHound PowerShell and current SharpHound CE are alternatives with different schemas/features, not interchangeable command spellings.

Analyze in this order
  1. Mark only identities/hosts actually controlled. A low-privilege session on a host does not make the host itself fully owned.
  2. Inspect the controlled principal's direct and nested group memberships and outbound object-control edges.
  3. Inspect reachable computers where it has local admin, RDP, WinRM/DCOM or other applicable rights.
  4. Inspect high-value goals and shortest paths only as hypothesis generation.
  5. Classify each selected edge:
    • directory/static-ish: group, ACL, GPO, OU, trust;
    • host-derived: local group or user right;
    • volatile: session;
    • route-dependent: the required host/service must be reachable now.
  6. Reproduce the minimum important relationship manually before handing it to Block 11 or 12.
ID | CONTROLLED PRINCIPAL | RELATIONSHIP | TARGET | SOURCE EVIDENCE
   | EFFECTIVE? | ROUTE/SERVICE | VOLATILITY | EXPECTED TRANSITION
   | MINIMUM VALIDATION | STATUS | NEXT BLOCK

Rank candidates by:

  1. confidence that the relationship is effective;
  2. deterministic value of the resulting identity/access;
  3. route and service availability;
  4. stability versus volatile session timing;
  5. reversibility and impact;
  6. number of unsupported assumptions.

Prefer a validated readable share/credential clue or direct object right over a multi-edge path built from stale sessions and unreachable hosts.

7. Worked example — hypothetical

Observation: collection finds a short path from a controlled group to a privileged account. Test: validate each effective ACL and destination service edge manually. Illustrative output: one edge is stale. Interpretation: reject that chain and rank another with current evidence.

8. Verify the result

Validate every useful edge against current directory/host evidence and identify the transition each one enables.

9. Failure and fallback

Collector/version incompatibility and partial data are tool/visibility failures. They do not prove the environment lacks a path.

10. Next transitions

Validate effective directory-object control; Validate host access and volatile session candidates; Maintain state and select the next evidence-producing test.
