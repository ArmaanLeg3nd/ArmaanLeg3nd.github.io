    6.1.3 Reach internal services

    Strategy map | Master Notes | Operational index | Cheatsheets

    A tunnel moves traffic; it does not grant destination authorization. Draw listener location, connection initiator, remote destination, DNS resolution and return path separately.

    Speedrun blocks: 13; study fundamentals before 10–12. Documented methods: 16.

    Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

    6.1.3.1 First pass: tools and findings

    Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

    6.1.3.1.1 Enumerate what the pivot can actually reach

    Run route/listener checks on the pivot itself; do not infer its access from the attacker machine.

    ip addr
ip route
ss -lntup
    • If One internal TCP endpoint is reachable from the pivot: Draw the local/pivot listener and initiator before choosing a fixed forward. → Forward a selected service through an SSH client-side listener.
    • If Several internal services need proxy/routed access: Match the client protocol to SOCKS or a TUN route. → Provide SOCKS access through SSH dynamic forwarding.
    • Otherwise: The pivot cannot reach the destination: fix that leg before adding a tunnel. → Discover pivot interfaces, routes and internal service context.

    6.1.3.1.2 Use SSH forwarding for the required direction

    Use this when the attacker can SSH to a pivot that can reach the destination; remote forwarding reverses the listener placement.

    ssh -N \
  -L 127.0.0.1:LOCAL_PORT:INTERNAL_HOST:INTERNAL_PORT \
  -p SSH_PORT USER@PIVOT \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3
    • If The forwarded service responds through the listener: Re-enumerate that destination with the matching service client. → Identify applications and validate selected NSE checks.
    • If Only the pivot can initiate the tunnel connection: Select the reverse/listener arrangement deliberately. → Expose an SSH-client-side destination through a server-side remote listener.
    • Otherwise: The listener exists but the app fails: test destination reachability and DNS through the chosen path. → Preserve DNS, Kerberos names and time across a pivot.

    6.1.3.1.3 Use Ligolo for a justified routed requirement

    Use the version-specific agent/proxy procedure and route setup. A tunnel session alone is not a working destination route.

    ./proxy -selfcert -laddr 0.0.0.0:LIGOLO_PORT
    • If The selected subnet is routed and the destination responds: Re-run service discovery from that new position. → Identify applications and validate selected NSE checks.
    • If Delivery works but the payload callback fails: Build and verify the separately needed return/callback path. → Build the callback and delivery routes separately from the attack route.
    • Otherwise: Route/session setup fails: inspect the route, interface privileges and each connection leg. → Discover pivot interfaces, routes and internal service context.

    6.1.3.2 Discovery workflow

    Start from the pivot's current shell/process or accepted SSH access; another reachable subnet and an operational tunnel are not assumed.

    Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

    1. Inspect pivot interfaces, routes, local listeners and destination reachability: Discover pivot interfaces, routes and internal service context.
    2. Draw listener location and connection initiator before fixed or SSH forwarding: Relay a single TCP service through a fixed forward; Forward a selected service through an SSH client-side listener; Expose an SSH-client-side destination through a server-side remote listener.
    3. Choose proxy versus routed access according to the real client/protocol requirements: Provide SOCKS access through SSH dynamic forwarding; Use ProxyChains, native SOCKS clients and SSH jump paths appropriately; Route a selected internal subnet through Ligolo-ng.
    4. Validate names, KDC access and the separately required delivery/callback route: Preserve DNS, Kerberos names and time across a pivot; Build the callback and delivery routes separately from the attack route.
    5. For additional hops test each leg before chaining the final application: Compose multiple pivots and validate every connection leg.

    Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

    6.1.3.3 Method families

    • Network position and fixed relays: Discover pivot interfaces, routes and internal service context, Relay a single TCP service through a fixed forward.
    • SSH listener direction and proxy access: Forward a selected service through an SSH client-side listener, Provide SOCKS access through SSH dynamic forwarding, Expose an SSH-client-side destination through a server-side remote listener, Expose a server-side SOCKS proxy through remote dynamic SSH forwarding, Use ProxyChains, native SOCKS clients and SSH jump paths appropriately.
    • Transparent and Windows forwarding: Route a selected subnet through sshuttle, Forward from Windows with OpenSSH, Plink or Netsh.
    • Alternative carriers and routed agents: Use a reverse Chisel SOCKS or fixed TCP tunnel, Use forward Chisel SOCKS and version-supported UDP routing, Route a selected internal subnet through Ligolo-ng, Conditional: tunnel through controlled DNS infrastructure.
    • Names, return paths and multiple hops: Preserve DNS, Kerberos names and time across a pivot, Build the callback and delivery routes separately from the attack route, Compose multiple pivots and validate every connection leg.

    6.1.3.20.5 Why it works

    Each additional hop introduces another initiator/listener/destination path. A connected second agent does not prove that the final application or callback crosses every leg.

    6.1.3.20.6 Execute and choose variants

    For every additional hop, write another complete segment:

    Kali -> tunnel A -> PIVOT_A -> tunnel B -> PIVOT_B -> INTERNAL_HOST:PORT

    Rules:

    • validate one hop before adding the next;
    • avoid overlapping local/VPN/internal routes;
    • use unique listener and SOCKS ports;
    • record which session owns each route;
    • ensure the deeper agent/client can reach the upstream listener;
    • re-evaluate DNS and callback direction at every hop;
    • prefer a routed method for several deep services instead of stacking many opaque wrappers.

    An upstream tunnel failure invalidates every deeper observation. Do not troubleshoot target credentials until the complete path is restored.

    6.1.3.20.7 Worked example — hypothetical

    Observation: the first pivot reaches the second host but not its internal subnet. Test: verify the second host's route, then the selected service on each leg. Illustrative output: one forward points to the wrong loopback. Interpretation: fix that leg and retain the working first hop.

    6.1.3.20.8 Verify the result

    Validate each hop with an application-aware test before chaining the final client.

    6.1.3.20.9 Failure and fallback

    Avoid rebuilding every tunnel after one failure. Isolate the first broken leg and preserve working state.
