Escalate privileges on Linux

Strategy map | Master Notes | Operational index | Cheatsheets

For each candidate prove controlled object → effective permission → privileged consumer → execution identity → trigger → effect. Enumeration tools suggest candidates; they do not establish that chain.

Speedrun blocks: 8. Documented methods: 16.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Identify the session, then run LinPEAS early

After checking id, architecture and shell availability, transfer a trusted reviewed LinPEAS copy using the transfer procedure. The sh invocation does not need an executable bit. Save output; use the local -h before selecting optional flags.

id
uname -m
command -v bash python3
ls -ld /tmp

sh ./linpeas.sh | tee linpeas.txt
  • If sudo/NOPASSWD or an allowed binary: Run sudo -l and compare run-as, exact path and permitted arguments with the chosen escape. → Use an allowed sudo operation to cross a privilege boundary.
  • If A root-owned SUID binary: Check the exact file, mount flags and its available privileged operation. → Use a SUID or SGID program's exposed privileged primitive.
  • If A useful file capability: Match the capability to the exact executable operation and mount. → Use a file capability that enables a specific privileged operation.
  • If A password, key or application config: Read the source file and identify which account/service it belongs to. → Recover credentials from Linux user, service and process trails.
  • Otherwise: LinPEAS cannot run or shows no usable finding: use the native identity/permissions checks; quiet output does not prove no escalation. → Establish Linux state and choose an escalation candidate.

Check sudo rules against the actual binary

Use only the operation permitted by the entire rule. Select the matching GTFOBins mode/build instead of trying every example.

sudo -n -l 2>&1
sudo -l
  • If (root) NOPASSWD permits a useful interpreter/helper: Check argument restrictions and privilege retention, then use that exact permitted invocation. → Use an allowed sudo operation to cross a privilege boundary.
  • If LD_PRELOAD is explicitly permitted/preserved: Verify a dynamically linked allowed program and the variable-setting permission. → Load a controlled library through a permitted sudo environment.
  • Otherwise: No useful sudo rule: check SUID/SGID and capabilities; do not keep trying sudo payloads. → Use a SUID or SGID program's exposed privileged primitive.

Catch short-lived root jobs with pspy

Use a reviewed binary matching the target architecture; keep it running long enough to observe the suspected schedule. Stop after collecting the needed events.

./pspy64
  • If UID=0 repeatedly invokes a script under /opt or another path: Check the script and each parent with namei/stat/getfacl, then identify the schedule/trigger. → Control a script, binary or configuration consumed by a privileged job/service.
  • If A privileged job invokes a helper without an absolute path: Inspect the real PATH and a writable directory searched first. → Hijack an unqualified helper through controlled PATH resolution.
  • Otherwise: No event was observed: inspect cron/timers/services directly rather than assuming no privileged job exists. → Control a script, binary or configuration consumed by a privileged job/service.

Test SUID/capability findings manually

Use native discovery alongside the tool output; a flagged executable is only useful if it retains a relevant privilege.

find / -xdev -type f -perm -4000 -ls 2>/dev/null
find / -xdev -type f -perm -2000 -ls 2>/dev/null
findmnt -T /PATH/TO/BINARY
  • If A root-owned SUID program exposes a usable operation: Check nosuid, exact build and effective identity after that operation. → Use a SUID or SGID program's exposed privileged primitive.
  • If An executable has a useful file capability: Check the named capability and its effective operation under this mount. → Use a file capability that enables a specific privileged operation.
  • If A root-consumed file/parent is writable: Validate the real consumer and trigger before modification. → Prove effective file, directory, ACL and mount control.
  • Otherwise: No useful privileged executable: return to secrets, scheduled consumers, mounts and local-only services. → Recover credentials from Linux user, service and process trails.

Discovery workflow

Start with a low-privileged Linux command channel. No sudo rule, writable privileged script or usable SUID binary is assumed.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. Establish effective IDs/groups, mounts, processes and exact sudo rules: Establish Linux state and choose an escalation candidate.
  2. Follow readable application/history/process artifacts into typed credentials: Recover credentials from Linux user, service and process trails.
  3. Inspect sudo/SUID/capabilities and prove effective object/parent permissions: Use an allowed sudo operation to cross a privilege boundary; Use a SUID or SGID program's exposed privileged primitive; Use a file capability that enables a specific privileged operation; Prove effective file, directory, ACL and mount control.
  4. Identify each job/service's real identity, consumed path and trigger; only then examine resolution abuse: Control a script, binary or configuration consumed by a privileged job/service; Hijack an unqualified helper through controlled PATH resolution; Turn wildcard-expanded filenames into privileged command options; Control a privileged program's shared-library resolution.
  5. Investigate daemon/mount/software candidates against their exact conditions: Use privileged group, daemon or container-management control; Exploit a permission-backed mount, NFS mapping or local service; Select an evidence-matched Linux software or kernel exploit.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

  • Daemon, mount and software routes: Use privileged group, daemon or container-management control, Exploit a permission-backed mount, NFS mapping or local service, Select an evidence-matched Linux software or kernel exploit.

Prove effective file, directory, ACL and mount control

Blocks: 8. Operational procedure | Quick sheet

1. Purpose and result

A validated controlled object suitable for a specific execution or credential chain.

2. Recognition clues

A root-consumed file or directory appears writable.

Find the clue from your starting access

Where to investigate: From a real privileged script/binary/configuration path inspect every parent, ACL and effective mount before assuming control.

Discovery action — reference example:

namei -l /PATH/TO/OBJECT
getfacl -p /PATH/TO/OBJECT /PATH/TO/PARENT
findmnt -T /PATH/TO/OBJECT

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

file: root-owned, not directly writable
parent: current group has write+execute
mount: rw

Recognize this detail: Parent replacement can provide a control primitive even when the existing file's write bit is absent.

Still missing before method selection: Run namei -l, stat and getfacl on the exact path and its parents, then findmnt -T for ro/noexec/nosuid. Check the identity and trigger of the process that uses this path; write permission alone is not execution.

Outcome after checkingExample and next decision
Enabled after validationThe precise object can be replaced and is consumed under a higher identity: choose that control path.
Ruled out in this contextParent/file rights do not grant the needed operation: reject that proposed write.
InconclusiveAn ACL listing without effective trustee/mount context leaves control unresolved.

If you do not yet have this clue: start with Establish Linux state and choose an escalation candidate.

3. Prerequisites

Starting access: A verified Linux foothold with a known effective UID, groups and filesystem context. Required conditions: Effective access through every parent/ACL and mount; a privileged consumer and trigger are identified separately.

4. Discover and verify prerequisites

namei -l /PATH/TO/OBJECT
getfacl -p /PATH/TO/OBJECT /PATH/TO/PARENT
findmnt -T /PATH/TO/OBJECT

5. Why it works

Directory write plus traversal can allow replacement without direct file write. ACLs, sticky directories, immutable attributes and mount options can change the effective operation.

6. Execute and choose variants

namei -l /PATH/TO/OBJECT
stat /PATH/TO/OBJECT /PATH/TO/PARENT
getfacl -p /PATH/TO/OBJECT /PATH/TO/PARENT 2>/dev/null
findmnt -T /PATH/TO/OBJECT -o TARGET,SOURCE,FSTYPE,OPTIONS

Directory write+execute can permit replacement even when the file is not writable. ACLs can add/remove effective access. nosuid defeats SUID/SGID and file-capability effects; noexec blocks direct execution; ro blocks changes.

Discover writable objects, then prioritize root-owned configuration, scripts, binaries and parents under /etc, /opt, /usr/local, application paths and service working directories:

find / -xdev -type f -writable -ls 2>/dev/null
